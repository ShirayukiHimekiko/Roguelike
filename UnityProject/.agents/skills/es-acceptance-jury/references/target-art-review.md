# 目标／美术陪审与视觉任务分工

前四节（T 本职、分工、第一问、新增特征）只在任务有视觉或风格目标时适用（有 `TARGET.md`，或用户点名了参照作品／画面）；非视觉任务不启用 T，F/A 照原规则。最后两节（投入上限、换人和图片）适用于所有多角色任务。

<a id="obligations-target"></a>
## 🟪T 目标／美术：本职

**做什么。** 每版打开 [参照｜当前版｜上一版] 并排图（同一主机位），对照用户点名的参照和 `TARGET.md`，回答一个问题：**这一版离用户要的更近了吗。** 审美和风格判断归 T，不归 A。T 是真实独立的陪审：自己创建、自己看图、自己给分，作者、统筹、F、A 都不能代写。

**评审前看图清单**
1. 参照三级：**主基准**＝点名作品实机图，主体占 40%+，UI 可框；**局部参照**＝裁出可学处，注明学什么/避什么；**补充参照**＝出处未核实，不作主基准、不顶替点名作品。标题不证身份；同图算一次；待评图/他人候选只当反例；HUD/技能特效不算目标特征。
2. 先描述后判断：主色、明暗块、高光条带还是光晕、泡沫成带还是碎点。
3. 同机位并排，缩至约 64px 宽比大关系，不像先改大关系。
4. 量色：`refgrab crops` 量目标与各候选同一区域，先看离目标多远，再互比。
5. 先拿不像的图校准；分不清就测量，注明“视觉判断不确定”。

**意见格式**（和 F/A 同一骨干，按 [呈现合同](message-style.md#user-facing) 原样展示）：

```text
**🟪T 目标／美术／当前状态 【📈 本波推进增益：原整数】**（适用范围）
主事件：原主事件
离用户的判断句：更近／没变／更远——依据（并排图哪一处）
要新增的特征：至少一条（是什么、在画面哪里、可参考的技法）
看到什么／差在哪／下一步改什么
🔎考虑到｜用户需求偏移：参照集合是否仍是用户点名的对象；有没有未经用户确认的目标变更
🔎考虑到｜真实的视觉理解：亲看的是哪几张图、哪个机位、看了整体还是局部
```

- **第一句固定回答 [陪审第一问](#first-question)**，再写别的。
- **至少一条“要新增的特征”**，按 [新增特征](#feature-add)。
- **分数**：−100 到 +100 的整数，未核实给负分，缺分记 −1，主机位没有可见变化不给正分，全部按 [原增益](coordination.md#wave-gain)。
- **否决**：这是从 A 的品质否决里**转移**过来的审美部分，不是新增的一道门。画面离用户要的风格有已证差距，由 T 按 [超级 P0](review-standard.md#quality-blocking) 阻断依赖它的采用和交付，只能由 T 本人或合法的同职责接任者关闭。启用 T 的任务里，A 不再就审美单独开 P0；A 对技术品质（伪影、供给、性能、代价）的否决不变，F 的否决不变。同一件事只由一个职责卡，F/A 的通过也不能抵掉 T 的否决。
- **只读本节**，读完就去看图。每版看一次；技术问题由 A 出意见，T 不代判、不查引擎源码。
- 参照集合和用户点名的对象不一致时，意见里必须写明“当前参照不是用户点名的对象”，并请统筹去问用户。

<a id="role-split"></a>
## 视觉／风格任务里谁做什么

| 角色 | 做什么 | 不做什么 | 投入 |
| --- | --- | --- | --- |
| 统筹（主交流AI） | 核对 `INTENT.md` 里用户的判断句（作者写），向用户回读理解，守预算，派发和对用户展示 | **不制作、不找参照、不定美术方向、不批准目标变更**；只传文件路径，不转发大段内容 | 不超过作者 |
| 作者（工作AI） | 找参照、写 `TARGET.md`、制作、出并排图 | 不自评通过 | 总投入一半以上 |
| 🟪T 目标／美术 | 每版回答“离用户要的更近了吗”，给要新增的特征 | 不查引擎源码，不改目标 | 每版一次 |
| 🔶A 架构／技术生态／可玩性 | 方案评估和里程碑给本人意见；某一版有技术品质或正确性问题（伪影、错位、性能、供给），就在同一波和 T 各自出意见；定位用逐层开关二分，修完退出 | **不判断好不好看，不就审美开 P0**；只核技术供给、伪影和代价 | 有技术问题的那一波 |
| 🟦F 进度／功能 | 里程碑（第一版完整画面、交付前）各跑一次普通用户路径：从打开到看到结果 | 不兼任迁移消费者，不出题，不制作 | 里程碑各一次 |
| 迁移消费者 | 主作品通过后，由一个**新启动**、只读 Skill 的 AI 做第二个需求，检验 Skill 能不能迁移 | 主作品没通过前不启动；题目只来自用户原话，原话没有就不做 | 主线通过后 |

**目标变更只能由用户确认。** 参照集合、特征清单或范围要变，统筹把“原来是什么、想改成什么、为什么”发给用户；用户确认前照原目标做。任何 AI（统筹、作者、F、A、T）都不能批准目标变更，也不能悄悄执行。

F/A 的名称、格式和否决权不变；方案评估仍要 F/A 对同一版本明确认可。F 在里程碑之间发现的已成立否决照常有效。

**T 和 A 同一波各管一半。** T 只接管审美；技术品质和正确性仍归 A，A 的意见和否决不因启用 T 而消失。一版里既有风格差距又有技术问题（例如主机位水色不对、俯视有噪斑），T 和 A 各出一块意见，各自给分。“主线优先”只决定作者这一波先推哪条差距，不等于技术问题没人管：技术问题进待办时，A 的意见里写明“由 A 跟踪，交付前 A 核回”；会破坏正确性、保存或交付的照常立即阻断。同一件事只由一个职责卡：审美归 T，技术归 A。

给用户的阶段消息照 [呈现入口](message-style.md#user-facing)：事件标题开头，本波实际参与的每个职责（工作AI、出意见的 T/A/F、主交流AI）各一块原分，不只放 T 一块。

<a id="first-question"></a>
## 陪审第一问

每位陪审（T、F、A）在视觉／风格任务里写意见时，第一句先回答：**这一版离用户的判断句更近了吗？** 判断句取用户原话（学习 Skill 的 `INTENT.md` 第 3 条就是它）；没有现成的，就从用户原话写一句并标明出处。

T 再补一句路线判断：差距最大的那条特征，在作者现在的做法里有没有对应的做法（看学习 Skill `TARGET.md` 的路线表）。没有，或连续两版“没变／更远”，直接写“建议换做法”，并给出一个风格化的候选做法。

回答“没有”时，本人其余的技术意见一律降为待办：不占下一波的主投入，每轮统一交一次。例外：会破坏正确性、保存或交付的问题仍立即交；已经成立的否决不因此撤销；分数照样要给。

<a id="feature-add"></a>
## 每条品质意见至少写一条要新增的特征

只列缺陷，作者只能修被指出的东西。所以每条品质意见（T 必须，F/A 涉及画面或体验时也要）至少写一条**要新增的特征**：它是什么、应出现在画面哪里、用户点名的参照里在哪能看到、可以用什么技法做。只写“不好”“不像”的意见不算完成本职，统筹要求同波补上。

<a id="oversight-budget"></a>
## 投入上限

监督方（统筹加全部陪审）合计投入不超过作者。超过时先砍：统筹改为只传路径不转发内容；陪审不重读规则、只读本职本阶段那一节；无关小问题攒到每轮统一交。不能靠砍掉评分、独立首判或否决来省。

<a id="role-swap"></a>
## 换人、全局配置和图片

- **全局配置变更只影响新启动的角色。** 有人改了 `AGENTS.md`、`config.toml` 或模型设定，正在工作的作者和陪审照常继续，不换人、不重读规则；只有用户明确要求，或服务端真的拒绝了当前模型，才换。改全局配置前先确认没有正在跑的任务或实验。
- **图片一律压缩后再进上下文**，防止请求超过上限（HTTP 413）。整图用长边约 1600 像素的 JPEG 或缩略图看整体；要看细节，从原图裁出局部再看。原图留在磁盘上作证据，不把多张原尺寸大图一次塞进对话。
- 确需换人时，交接照 [身份与启动](coordination.md#activation) 的原规则，换人不重置分数、预算和未闭。
