# 真实玩法：按本阶段检验玩家过程

游戏或用户明确要求可玩/互动体验时命中。只读方案时审方案是否足够指导制作，不运行未授权系统；实作/可玩声明则核真实宿主。对应 [16真实玩法](constraints/16-play.md)，命中后执行[专项扫描](candidate-scan.md)，不把代码清单当玩法证据。

<a id="play-target"></a>
## 玩家要完成什么

从用户当前目标、批准机制和阶段确定必要路径。列玩家进入、选择/动作、规则响应与可感知后果、当前阶段目标和继续/退出关系。可以是一局、一段交互或一个玩法机制，不一律要求完整胜败、奖励、存档、教程或商业发布。需求须先于作者实作确定；测试按钮做出的结果不能反推成用户规格。

<a id="play-chain"></a>
## 游戏流程：玩家可达局面与此刻世界

按[游戏流程贯穿区](game-workspaces.md#flow)判断场景和视角转换、玩家能否推进到当前证据，以及全部应有单位、建筑、UI此刻的位置、状态与关系。查询入口、条件和状态源用于证明这些结果；按钮可点、Scene已加载或业务提交不代流程正确。调试摆场只证明该摆场，不能冒真实玩家已可到达；合法预览、切镜和传送按有效设计保留。

<a id="rule-consequence"></a>
## 规则、选择与后果

核已经批准的资源、费用、冷却、命中、生产/成长、敌人行为、失败/目标推进等实际适用规则。玩家的选择应影响这些真实规则和可见后果，不能只有动效/日志或永远成功。输入、对象实例、经济和反馈要同源；同一操作不重扣/重生/重奖，发生已提交后表现失败要续原尾而非重新做业务。

不因缺一个机制就默认新建公共状态或大系统。先按[项目理解](project-understanding.md#necessity-before-dependency)核原规则、既有接法和任务责任。原版风格/旧版融合机制是需要落到操作、构图、时序和规则的规格；不能仅写“符合原版”，也不能用原版名义撤掉用户批准的新差异。

<a id="play-states"></a>
## 状态与后继

按本机制实际存在的正常、拒绝、Busy、取消、提交未知/提交后失败、暂停、退出及再次进入选择最可能推翻结论的合法顺序。没有的状态不新造状态机。查玩家能否辨认当前结果、采取允许下一动作；卡死或永久拒绝不能当安全修复。

当前局有存档/在途/多域状态时按真实共同责任保存恢复，旧合法状态不能改成新局/清档求通路；没有存档需求的本阶段不强增保存。真实暂停、镜头/展示进度与业务时间分别判断，恢复不能补跑不应推进的时间；归还与迟到回调不能穿到后继。

<a id="feel-and-presentation"></a>
## 可玩性：整体体验与可制作改法

按[可玩性贯穿区](game-workspaces.md#playability)结合游戏类型、玩家和实际内容判断挑战/应对、节奏、风格、流畅、机制融合及视听品质；发现问题追具体原因并给能改变体验的改法。G3核操作与关卡内容，G4核美术音画制作；事实和过程证据共用，不以局部通过签整体好玩，不靠删必要内容、慢放或静音修复。

<a id="play-evidence"></a>
## 能证明什么、下一波做什么

方案/资产/源码/组合编译/真实运行/连续使用/规则正确/体验/预算分别给证据范围。静态来源可以支持限定方案判断；玩法成立需实际授权运行或有效生产观察，工具失败不是游戏失败。已知失败与缺测分开，不因新增测试绿或正增益把原否决清掉。

下一波优先补实际阻断上述玩家过程的相关缺项，复用已成熟机制和资源、由明确接回者串起成果。首个少量单位可以定位链路，不能冒完整本关内容达标；无关全历史/全资源/全部系统不成为当前闭环永远的前置。本阶段全部必要结果已有适用证据、无相关新反证时结束精修；未闭责任保留，续作／改法沿[统一判据](must-read-work-priority.md#continue-or-change)，不反复按局部修复送验。
