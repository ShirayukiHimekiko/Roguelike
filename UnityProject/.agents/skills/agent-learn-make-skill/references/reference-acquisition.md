# 取参照、立目标：先知道“好”长什么样，再动手

视觉、动画、音频、UI、关卡等**要靠看/听判断品质**的学习或制作，开工时必读本页。纯代码或纯文字任务只在需要外部资料时读第 3 节。先按 [intent-and-drift](intent-and-drift.md) 写好 `INTENT.md`，`TARGET.md` 从它展开。

本页解决两个真实失败：
- 搜不到用户点名的参照，就悄悄换成搜得到的东西，目标从“原神/鸣潮级水体”变成“吉卜力静湖”。
- 只有“哪里不好”的缺陷清单，没有“好是什么样”的正向目标，于是每版都被打回、局修，越修越乱。

## 1. 四条硬规则

1. **用户点名的参照对象不可替换。** 用户说了原神、鸣潮、塞尔达，就为每一个取到实机画面。取不到时按第 3 节换来源；三个不同来源都失败，才可以停下来问用户要截图/视频/链接，并列出试过的来源和报错。不准自己换对象，不准用“风格相近”的东西顶替，不准不说。
   - 一次下载超时或一个工具报错，只说明这条路径不通：换图片来源，或者从实机视频截帧（`vdl --section` 再 `frames`），或者找官方视频、作品页，都算换路径。等待期间目标不降格，先做不依赖风格判断的准备。
   - 搜到的图，标题写着点名作品也不能直接收。按[看图方法的剔除规则](visual-judgment.md#ref-traps)亲看后再分档。
2. **没有 `TARGET.md` 不写第一行制作代码。** 格式见第 2 节。它是作者、陪审和用户共同的评判标准。**开工门槛是每个点名对象至少 1 张亲看过的实机图**，其余参照、视频和特征边做边补，不为凑齐参照而推迟第一张粗版。
3. **每一版出图都和参照并排看。** 用 `scripts/refgrab.py compare 参照 当前版 上一版` 生成一张图，先看这张图再下结论。工具失败或参照暂缺时，用用户给的或本地已有的参照，在结论里写明“缺 X 的参照，本次按 Y 对比”，照常推进，不停工。
4. **每轮开头写明推进 TARGET.md 哪一条差距。** 与这条无关的小修进待办清单，不占这一轮。

<a id="target-md"></a>
## 2. TARGET.md 怎么写

参照选得对不对、特征怎么看出来，按[看图方法](visual-judgment.md)第 1–6 节：每张标主基准、局部参照或补充参照，见[参照分档](visual-judgment.md#ref-tiers)。

放在工作区根目录。写给人看，白话。最少包含：

```markdown
# 目标：<用户原话里的对象>

## 参照（开工：每个点名对象至少 1 张实机图；之后补到 3 张左右 + 1 段实机视频）
| 编号 | 文件 | 来自 | 档 | 看什么 |
| R1 | refs/genshin/bing_004.png | 原神，HoYoLAB 玩家截图 | 主基准 | 近岸透底、青绿主色 |
| R2 | refs/vid/xxx.mp4 00:41–00:55 | 鸣潮 B 站实机 | 局部（只看浪头） | 浪花节奏；避开角色和技能特效 |

## 可检验特征（每张参照 3–5 条，必须能在截图上指出来、能量）
| 编号 | 特征 | 怎么量 / 怎么看 | 参照 | 候选技法 |
| F1 | 近岸到远处至少 3 个可区分色阶，近处青绿透底，远处偏深蓝 | 在水面取近/中/远 3 点吸色，色相或明度差明显 | R1 | 深度差驱动的颜色渐变 + 折射采样 |
| F2 | 岸线泡沫是实心白带，宽约画面高 1–2%，内缘硬、外缘碎 | 量像素宽度，放大看边缘 | R1 R3 | 深度差阈值 + 噪声破边 |
| F3 | 高光是横向断续条带，不是圆形光斑 | 看太阳反射区形状 | R2 | 拉伸的法线 + 阶梯化高光 |

## 技术正确性清单（阶段 A 必过，见第 4 节）
- 高视角 / 低掠角 / 移动相机下无错位倒影、无噪斑、无闪烁
- 深度/屏幕 UV/反射与场景物体对位
- 保存、重开、出包后效果一致

## 不做的事（写清理由）
```

要点：
- **开工版可以很短**：每个点名对象 1 张实机图、每张 1–3 条特征就能开工。之后每轮补参照和特征，补的时候按 [漂移检测](intent-and-drift.md#drift-check) 只增不换。
- 特征写**看得见的结果**，不写“氛围好”“高级感”这类判断词。
- 每条特征都要有候选技法。还不知道怎么做，就写“待查”，并把它列为下一轮查源的目标。
- 参照是视频时写清时间段。动态（波纹节奏、泡沫运动）必须看原速视频，截帧只用来做对比图。

<a id="style-source-quota"></a>
### 风格化目标：一半以上来源是风格拆解

新学某种风格（二次元、卡通、像素、某部作品的画风）时如下；已有有据的风格方法直接复用时，不重新凑配额。
- **来源里至少一半是风格本身的拆解**：作品截图逐层分析、美术或 TA 的分享、实机视频截帧。按第 3 节“别人怎么做的（拆解）”那一行去找。
- 工程教程只回答“怎么实现”，不回答“做成什么样”。写实或物理向的教程（如 GPU Gems 的物理水）可以借实现手法，但不能决定特征。
- **技术正确是底线，不是目标。** 正确但不像，等于没做。评一版时先用 `INTENT.md` 的判断句问“像不像”，再看对不对。
- 风格拆解一直找不到，按第 3 节换来源；仍找不到就写进回读消息请用户给，不拿技术教程顶替。

<a id="source-routing"></a>
## 3. 去哪找：来源路由（本机实测可用）

**固定调用写法**（PowerShell，路径加引号，不要省略 `-X utf8`）：

```text
python -X utf8 "<本 Skill 目录>\scripts\refgrab.py" <子命令> [参数]
```

开工先跑同目录的 `selfcheck.py`（离线，约 5 秒）：有任何一步失败就告诉用户，不要用坏掉的工具的输出做判断。再跑一次 `doctor`：它会列出依赖和每个来源当下能不能用，不能用的直接跳过。所有下载都会记进 `<输出目录>\manifest.jsonl`（来源、查询词、sha256、尺寸）。加 `--json` 可以拿到结构化结果，放在子命令前后都行。

**看退出码判断成败，不要只看有没有输出：**

| 退出码 | 意思 | 下一步 |
|---|---|---|
| 0 | 成功 | 继续 |
| 1 | 部分失败（stderr 写了哪几项） | 用已拿到的；缺的换来源 |
| 2 | 出错（stderr 第一行是“失败：原因”） | 按原因改参数或换来源，不要原样重试 |
| 3 | 没有结果 | 换更短的关键词、换中/英/日、换来源 |
| 4 | `refs` 有点名对象参照不足 | 按 `REFS.md` 写的下一步做 |

**第一条命令：取点名参照**

```text
refs "Genshin Impact=原神" "Wuthering Waves=鸣潮" "Zelda Tears of the Kingdom=塞尔达王国之泪" --topic water --need 4 --out refs
```

- `refs` 会依次换来源，直到每个对象都凑够张数；它会过滤小图和近重复图，按对象拼触表，并把每次尝试写进 `refs\REFS.md`。实测三部作品约 15 秒。
- **触表必须亲眼看。** 剔除同人图、滤镜图、多游戏对比拼图和无关图，剔除后不够就重跑同一条命令补齐。
- 看完就登记：`pick <图...> --subject 原神 --why "看到了什么" --out refs\selected`（选入，复制成 R1、R2…）或加 `--reject`（剔除）。它从 manifest 带上出处和 sha256，生成 `SELECTED.md`；TARGET.md 引用 R 编号。找不到出处的图会提示，用 `--src` 补。

| 我要找 | 先用 | 不行再用 |
|---|---|---|
| 某张图的原图（帖子、作品页） | `expand <HoYoLAB/米游社/Pixiv/B站链接> --out refs\x` | `page <链接> --js` 找图片地址 |
| 动态效果（波纹节奏、泡沫运动） | `video "鸣潮 海面 实机" --must 鸣潮,Wuthering`（标题不含作品名的标“疑似跑题”） → `vdl <链接> --section 00:40-00:52 --out refs\vid --json`（用输出的 `paths`，不猜文件名） → `motion <视频> --roi … --out refs\motion` | `frames <视频> --every 0.5 --sheet` 看静帧 |
| 别人怎么做的（拆解） | `research "genshin water shader breakdown" --pages 6 --out notes\water` | `video "原神 水面 shader 逆向" --src bilibili` → `expand <视频链接>` 看简介里的工程 |
| 可运行工程的源码 | `gh "stylized water unity URP"` → `gh-tree owner/repo --ext shader,hlsl`（免写正则，不怕 PowerShell 引号） → `gh-cat owner/repo 路径 --out src\x.shader` | `gh-dl owner/repo --out src`（整仓） |
| 只搜某个站 | `web "原神 水面 渲染" --site zhuanlan.zhihu.com` → `page <链接> --js --save notes\x.md` | `research … --site …` |
| 教程视频讲了什么 | `subs <视频链接> --out notes\subs`（YouTube 字幕可用；B 站 AI 字幕要登录，**先问用户**再加 `--cookies-from-browser edge`） | `vdl --section` + `frames` |
| GDC 讲稿 / 论文 PDF | `pdf <文件或URL> --out notes\x.md --pages 1-20` | `--images` 取插图（需 PyMuPDF，AGPL，只在本机用） |
| 引擎 API / 约定 | `page <docs.unity3d.com 对应版本页> --save notes\x.md` | 本地 PackageCache 源码 |
| 已下线页面 | `wayback <URL> --read` | — |

**把参照量成数字写进 TARGET.md。先框住水面，避开小地图、血条、字幕：**

```text
measure refs\原神\bing-en_00.jpg --roi "0.05,0.55,0.95,0.92" --grid 4x1 --palette 6
measure refs\原神\bing-en_00.jpg --line "0.5,0.6,0.5,0.8"        （竖线横穿岸线泡沫 → 亮带宽度占画面高的 % 和内外缘硬度）
motion  refs\vid\clip.mp4 --roi "0.05,0.55,0.95,0.92" --dur 8   （时间切片图 + 胶片条 + 帧间变化 + 主周期 + 移动方向/速度）
look    refs\原神\bing-en_00.jpg 当前.png 上一版.png --roi "0.05,0.55,0.95,0.92" --out cmp\board.png   （看图板：眯眼大关系 / 6 色分区 / 边缘软硬 + 饱和度、明度阶数、边缘锐度的差值）
crops   R1.png 当前.png --labels "R1|v3" --regions "近岸=0.05,0.7,0.4,0.95;远水=0.3,0.35,0.9,0.5" --out cmp\crops.png   （同名部位并排 + 中位色/HSV 差：说清“哪一块不像、差多少”）
```

构图不同时，`look --roi` 和 `crops --regions` 都可以用 `|` 给每张图各写一段（名字和顺序一致）。不用自己写 PIL 脚本裁图量色。

**数字 → 目标 → 参数，用同目录的 `numspec.py`**：`extract R1.png --feature T1 --regions "近岸=…;中段=…;远处=…" --line <近→远的线>` 把参照各区域的颜色记成 `SPEC.json`；`check 当前.png --regions …` 用感知色差（ΔE2000）给每条特征判 达到/接近/未达，输出可以直接贴给 `wavelog end` 的 `--status`；`steps` 数“近到远几个色阶”；`engine` 给出 Unity 的 Color（sRGB）和 Vector（线性）两种写法，以及色带贴图；`world --pct 1.5 --dist 20 --grazing 15` 把屏幕上量的泡沫宽度换成米。截图颜色已经包含光照和色调映射，只能当起始值，最后都以同机位截图 `check` 为准。

**任何参数（浮点、整数、开关、枚举，shader、组件字段、配置表列都算）不确定是什么意思，用同目录的 `paramap.py`**：先 `def 名 --kind float|int|bool|enum --means "以为它控制什么"`，每设一个值 `obs 名 值 --metric 结果=数 [--read 读回值] [--img 截图]`，再 `fit 名`。它会指出没作用（没接线或被覆盖）、方向和预期相反、阈值和饱和、哪些选项效果一样、保存值和生效值不一致；`pick 名 --want 结果=数` 只在观察过的范围里内插出该填多少。同一个值重复测一两次，它才估得出噪声。

**每波记账用同目录的 `wavelog.py`**（TARGET.md 写好后先 `baseline`）：`start N --push T1,T3` 开波并查漂移，`end N --main 主机位.png --ref R1.png --status T1=接近` 收波，它会判断主机位有没有可见变化、算不算前进、该不该停线；退出码 4 就按输出的“下一步”做。改之前拿不准原因，先 `try "判断" --predict "改了会看到什么"`，做完 `result`。

- 每次测量都会生成标注图（`原名_measure.png`）。打开看一眼，确认框住的是水面。
- 你看不了原速视频，`motion` 就是替代：时间切片图里斜条纹的斜率就是移动速度。先看胶片条，确认镜头没在移动；镜头移动时得到的速度是相对画面的，不能当成水的真实速度。
- 当前版用同样的参数和机位量一遍，两边的数字一比，就知道差多少。

已知不可用，不要反复撞：Google（429）、Reddit 和知乎的接口（403）、ArtStation 作品详情（Cloudflare 人机验证）、Danbooru、Shadertoy、Pexels。替代办法：ArtStation 用 `images --src artstation` 拿大图封面；必须过人机验证的页面，请用户手动保存。

**宿主没给联网搜索工具时，这个工具就是你的搜索。** 配置里写了 `web_search`，不代表你真的有搜索工具，先看自己的工具列表。

<a id="two-stage"></a>
## 4. 两段式首件：先技术基线，再美术

1. **阶段 A：搭对技术基线，限一波。** 用简单场景（单水面 + 几个测试物）把深度、屏幕 UV、反射、保存重开这些基础约定接对，只验 TARGET.md 的技术正确性清单：固定机位截高、低、掠角三张图，加一段移动相机录像。**阶段 A 只求正确，不求好看，最多一波**；过了就冻结这套约定，立即进入阶段 B，不在简单场景里打磨效果。
2. **阶段 B：完整作品里做美术。** 在冻结的管线上逐条实现 TARGET.md 的特征。每轮：出图 → 拼并排对比图 → 逐条标“达到 / 接近 / 未达” → 选差距最大的 3 条作为下一轮目标。查源、重现、判别实验只为这 3 条服务。每版是否算前进、何时停掉一条技术线，见 [什么算前进了一版](intent-and-drift.md#forward-progress)。

阶段 B 里又冒出技术伪影：先在完整作品里逐层关闭（反射 / 折射 / 焦散 / 泡沫…）二分定位；需要时可拉最小场景复现，但**最多一波**，修完必须回完整作品、用同一组机位重新出图复核。完整作品里没变好，就不算修好。

第一张完整的粗画面（可以很粗）要尽早出，开工后 30 分钟内应该有。它的作用是暴露真正的差距，不是交付。

## 5. 给别人看的东西怎么写

TARGET.md、评审意见、给用户的进度，都用普通开发者能直接读懂的中文：先说画面上看到了什么，再说和哪条特征差多少，最后说下一步改什么。不要用本 Skill 的内部术语；非用不可时，先用一句白话解释。
