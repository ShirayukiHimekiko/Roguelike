# 游戏生命周期实现外部调研与方案校正

2026-11-16 · 外部调研 + 评审稿

评审对象：[01-Project_B游戏生命周期分步实现方案](01-Project_B游戏生命周期分步实现方案.md)。本文只做核对、调研和实现思路建议，不改动该文档与代码。调研目标是把“大厅 → 开局 → 暂停/继续 → 结束/放弃 → 清理重开”这一段与外部成熟做法对齐，并指出 01 稿里会直接卡住实现的点。

## 0. 结论摘要

1. **方向成立**：应用级流程用有限状态机管理、加载走异步、结果值化、UI 只读快照，这些选择与主流做法一致（GameFramework、StarForce、Boss Room、Mirror 都这么做）。
2. **01 稿有 3 个 P0 级问题**：关闭顺序会踩 TEngine 的模块复活路径；`Singleton<GameManager>` 与“旧回报不得重建管理器”的验收自相矛盾；`UIModule` 没有窗口加载失败信号，导致“大厅装配失败”没有落点。
3. **01 稿还有 7 个 P1 级问题**：状态迁移归属自相矛盾、Loading 被藏在 StartGame 里、结果契约用词不统一、暂停语义含糊、事件系统前提不成立、句柄释放 API 未写清、目录/命名空间会与框架门面 `GameModule` 冲突。
4. **推荐实现**：6 状态（Lobby / Loading / Running / Paused / Finished / Exiting）+ 集中转移（`GameManager.Tick` 唯一决策，状态只做 Enter/Leave 副作用）+ GameApp 显式持有宿主（不用 Singleton）+ `RunOutcome` 值契约 + 显式、幂等的关闭顺序。
5. **不建议**：把 Loading 继续藏在 StartGame 里；用 `Singleton<T>` 承担“唯一实例”语义；依赖 `OnDestroy` 的触发顺序做收尾；暂停时改 `Time.timeScale`。

### 2.3 共性做法

1. **流程就是状态**：GameFramework/StarForce/TEngine 都把“启动、检查更新、加载、进游戏”做成流程状态，每个流程只做一件事，完成即切换。
2. **Loading 是独立阶段**：Shattered PD 直接给加载一个场景，MRTK 给场景加载独立 API，Mirror 明确注释“异步启动不可能同步完成”。把加载塞进“开始”状态里，等于把两种合法输入、两种失败出口混在一起。
3. **迁移集中**：Boss Room 的 `ConnectionManager.ChangeState` 是唯一迁移入口，状态对象只做 `Enter/Exit`；CSDN 的 `FiniteStateMachine.Transition` 也是集中式。01 让每个状态自己在 `OnUpdate` 里迁移，会出现“谁都能改状态”。
4. **异步结果带身份**：Mirror 用 mode + `loadingSceneAsync` 状态，UniTask 用 `CancellationToken`，Shattered PD 用 `Mode` + `thread` 判活。01 的 `RunId` 方向对，但只覆盖了“局”，没有覆盖“操作代次”（同一局内多次加载/重试）。
5. **结果是值，失败有出口**：Boss Room 的 `ConnectStatus`、Shattered PD 的错误回退、Mirror 的 offline/online 场景，都把“失败”当成一个正常分支。01 的 `LoadFailed` 只在样本加载上有，窗口加载没有。
6. **关闭顺序显式化**：Unity 公开的可靠钩子是 `quitting`/`wantsToQuit`，跨对象的 `OnDestroy` 顺序没有承诺；CSDN 的“Some objects were not cleaned up”就是反例。收尾必须是显式、幂等、可重入的。

### 3.2 问题清单

#### P0-1 关闭顺序会踩 TEngine 的模块/对象复活路径

**现象**：01 把业务释放放在 `ReleaseLogic`，而 `ReleaseLogic` 挂在 `[UpdateDriver]` 的 `OnDestroy` 上；player 下 `RootModule.OnDestroy` 也会触发 `ModuleSystem.Shutdown()`。两者都是 DontDestroyOnLoad 对象，销毁顺序不受控。

**证据**：

- `GameApp.Entrance` 调 `Utility.Unity.AddDestroyListener(ReleaseLogic)`，最终是 `UpdateDriver.MainBehaviour` 的 `OnDestroy` 事件（`GameApp.cs:32`、`UpdateDriver.cs:335-341`、`399-407`）。
- player 下 `RootModule.OnDestroy` 执行 `ModuleSystem.Shutdown()`（`RootModule.cs:162-167`，注意包在 `#if !UNITY_EDITOR` 里）。
- `ModuleSystem.Shutdown` 会调用每个模块的 `Shutdown`，其中 `UpdateDriver.Shutdown` 会 `Object.Destroy(_entity)`（`UpdateDriver.cs:24-37`）；`MainBehaviour.OnDestroy` 因此被延迟到帧末，可能晚于 `ModuleSystem.Shutdown` 完成。
- 一旦 `ReleaseLogic` 晚于模块清空：`GameModule.XXX` 会通过 `ModuleSystem.GetModule` **重新创建模块**（`ModuleSystem.cs:68-120`）；`SingletonSystem.DeInit` 和 `GameApp.RemoveDestroyListener` 会调用 `UpdateDriver.Remove*Listener`，而该方法内部 `_MakeEntity()` 会**重新创建 `[UpdateDriver]` GameObject**（`UpdateDriver.cs:192-200`、`288-299`；`SingletonSystem.cs:318-335`）。

**影响**：退出时新建模块/GameObject；`GameManager.OnRelease` 可能访问到已销毁的窗口、FSM 或资源模块；Editor（不执行 `ModuleSystem.Shutdown`）与 player 行为不一致，问题只在真机暴露。

**建议**：

1. 用 `Application.quitting`（或 `wantsToQuit` 做延迟退出）作为业务收尾入口，`AddDestroyListener` 只作为 Editor 兜底；两个入口共享一个 `_released` 幂等标记。
2. 收尾顺序固定，且**收尾后不再访问 `GameModule.*` / `SingletonSystem`**。
3. 在 player 加一条退出验证：退出前后 `[UpdateDriver]` 只有一个、无新建模块日志、无 `Log.Fatal`。

> 这条是项目级问题，影响的不止 01；但 01 既然要“应用释放先释放业务”，就必须先把入口和顺序定死。

#### P0-2 `Singleton<GameManager>` 与验收项“旧回报不能重建管理器”冲突

**现象**：01 把 `GameManager` 定义为 `Singleton<GameManager>`，同时验收里要求“应用销毁后旧回报不能重新创建管理器或打开业务窗口”。

**证据**：`Singleton<T>.Instance` 是懒创建：只要 `_instance == null` 就 `new T()` 并 `Retain`（`Singleton.cs:13-26`）。任何迟到的 UI 回调、加载回报、协程恢复，只要写的是 `GameManager.Instance`，就会把管理器重新创建出来。

**影响**：01 验收表最后一行“应用销毁”无法由结构保证；出现“退出后又冒出一个 GameManager/大厅窗口”的隐蔽问题。

**建议**：改成 `GameApp` 显式持有 `new GameManager()`（与执行手册的 `_gameManager = new GameManager()` 一致），不注册为全局单例；所有请求入口先校验 `RunId` 和 `IsReleased`。如果坚持 Singleton，至少提供 `TryGet` 且禁止在释放后走 `Instance`，并把这条写进代码评审红线。

#### P0-3 窗口加载失败没有信号，“大厅装配失败”没有落点

**现象**：01 要求“窗口打开成功且大厅就绪后启用开始按钮”“窗口装配失败记录地址和错误”，但现有 UI 模块不提供失败结果。

**证据**：

- `UIModule.ShowUIAsync` 返回 `void`，没有完成/失败回调（`UIModule.cs:250-253`）。
- `ShowUIAsyncAwait` 用 `Time.deltaTime` 轮询 `IsLoadDone`，最多 60 秒，然后**无条件返回窗口**（`UIModule.cs:338-364`）。
- `UIWindow.Handle_Completed` 在 `panel == null` 时直接 `return`，`IsLoadDone` 永远为 false（`UIWindow.cs:464-502`）。
- `ResourceModule.LoadGameObjectAsync` 对无效地址 `Log.Error` 后返回 `null`（`ResourceModule.cs:872-883`），不会抛异常。

**影响**：01 的“窗口装配失败”只能靠日志，无法驱动状态机；`StartGame` 没有“大厅加载失败”出口，窗口失败会卡在等待开始；如果暂停用 `Time.timeScale = 0`，`ShowUIAsyncAwait` 的 60 秒也永远走不完。

**建议**（按侵入性排序）：

1. 最小改 `UIWindow`：加载失败时设置 `LoadFailed` 标志并触发事件，`ShowUIAsyncAwait` 改 `Time.unscaledDeltaTime`，失败返回 null。
2. 给 `ShowUIAsync` 增加 `UniTask<bool>` 重载。
3. 01 期不走 `UIModule`，直接用 `GameModule.Resource.LoadGameObjectAsync` 自建窗口（不推荐：绕过窗口栈、层级、安全区）。

无论选哪个，01 的状态表都要补 `Lobby` 的失败出口（重试或 `ExitGame(LoadFailed)`）。

#### P1-4 状态迁移的“裁决者”自相矛盾

**现象**：01 §1 写“GameManager 裁决状态迁移”，§2.3 又写“状态类在自己的更新中调用受保护的 `ChangeState`”；执行手册的示例也是状态类自己迁移。

**影响**：两处都可能写迁移逻辑，出现“状态里判一次、GameManager 里再判一次”的双重迁移；5 个状态各自重复“收集加载完成、消费请求、判断出口”。

**建议**：状态只做 `OnEnter/OnLeave` 副作用；`GameManager.Tick()` 做唯一决策，返回下一个状态类型，状态基类统一执行：

```csharp
protected override void OnUpdate(IFsm<GameManager> fsm, float dt, float real)
{
    Type next = fsm.Owner.Tick(dt);
    if (next != null)
    {
        ChangeState(fsm, next);
    }
}
```

这样既满足 `ChangeState` 只能由状态类调用的 API 约束，又把决策集中到可测试的 `Tick`。

#### P1-5 Loading 被藏在 StartGame 里

**现象**：01 §1 用“同一状态用快照区分空闲与加载中”，§2.3 写“当前局资源就绪 → RunGame；放弃或装配失败 → ExitGame”。

**影响**：加载中有独立合法输入（放弃）、独立失败出口，本质就是一个状态；用 `IsLoading` 标志会让每个 handler 都要先判标志，`StartGame.OnEnter` 还要同时承担“开大厅”和“受理开局”两件事。

**建议**：拆成 `Lobby` 和 `Loading` 两个状态（见第 5 节），或者明确写成 `StartGame` 内的子状态机（HFSM）并给出子状态表。二选一，不要停留在“用快照区分”。

#### P1-6 结果契约用词不统一，`RunOutcome` 没有定义

**现象**：文档同时使用“自然结果”“`RunOutcome`”“离场原因”“离场结果”“离场通知”；§1 表里 `Completed/Abandoned/LoadFailed/Faulted` 被称为“离场原因”。

**影响**：实现时容易出现两个结果类型、两次发布、UI 读到旧值。

**建议**：定义一组值契约，全篇统一：

```csharp
enum ExitReason { Completed, Abandoned, LoadFailed, Faulted }

readonly struct RunOutcome
{
    public readonly int RunId;
    public readonly ExitReason Reason;
    public readonly int SampleProgress;
}
```

`ExitGame` 是 `RunOutcome` 的唯一发布点；`EndGame` 只冻结“已提交的自然结果”，不再发布第二种结果。

#### P1-7 暂停语义含糊，且与 `Time.timeScale` 有冲突

**现象**：01 写“暂停期间保持 `Time.timeScale`”，但没有说清是“保持为 1，不动它”还是“保持当前值”。

**证据**：`RootModule.PauseGame()` 会把 `GameSpeed` 置 0（`RootModule.cs:172-181`、`75-79`）；`GameTime.deltaTime = Time.deltaTime`（`GameTime.cs:48-49`）；`UIModule.ShowUIAsyncAwait` 用 `Time.deltaTime`。

**影响**：如果实现者顺手用 `PauseGame()`，UI 异步打开、`HideUI` 的定时器都会停；Fsm 仍然会收到 Update（unscaled 不为 0），状态机不会停，容易误判“暂停生效”。

**建议**：写死“暂停 = 逻辑暂停，不改 `Time.timeScale`，禁止调用 `RootModule.PauseGame()`”；验收加 `Time.timeScale == 1`；表现暂停交给 02 的帧驱动或动画参数。

#### P1-8 事件系统前提不成立

**现象**：01 写“模块间状态通知用 `GameEvent`，窗口用 `AddUIEvent` 管理订阅”。

**证据**：`GameApp.Entrance` 里 `GameEventHelper.Init()` 被注释（`GameApp.cs:27`），项目没有 Source Generator 的引用；`[EventInterface]`/`GameEvent.Get<T>()` 这条接口事件路径不可用。`GameEvent.Shutdown()` 存在（`GameEvent.cs:596-599`），但 01 没提。

**影响**：如果按 reference 的接口事件写，编译或运行不通过；非 UI 监听漏清理会留悬挂回调。

**建议**：01 期只用 int 事件 + 常量（或 string）；`GameManager` 用 `GameEventMgr` 持有监听并在 `OnRelease` 里 `Clear()`；退出末尾明确是否调用 `GameEvent.Shutdown()`。

#### P1-9 句柄释放 API 没写清

**现象**：01 只写“归还句柄”“释放句柄”。

**证据**：项目内统一用 `handle.Dispose()`（`ResourceModule.cs:860`、`905`；`ResourceModule.AssetObject.cs:53`；`AudioAgent.cs:327`）；`LoadAssetAsyncHandle` 失败不抛异常（`ResourceModule.cs:1179-1193`）。

**影响**：实现时可能调用不存在或不一致的 API；失败判定漏掉 `Status`；`TextAsset.text` 在 `Dispose` 后读取会出问题。

**建议**：写明 `handle.Dispose()`、`handle.Status == EOperationStatus.Failed`、先复制 `text` 再 `Dispose`，释放放在统一收尾路径（不要散落在各个 `if` 分支）。

#### P1-10 目录/命名空间会与框架门面 `GameModule` 冲突

**现象**：01 把新文件放在 `Assets/GameScripts/HotFix/GameLogic/Module/GameModule/`，并继续用 `GameModule.Fsm` 访问框架。

**证据**：`GameModule` 是全局类（`GameModule.cs:5`）；现有 `Module/**` 下的文件全部是 `namespace GameLogic`（11 处，如 `UIModule.cs:10`）。如果新文件按目录写成 `namespace GameLogic.Module.GameModule`，`GameModule.Fsm` 会被解析成命名空间，出现 CS0234/歧义。

**影响**：编译期就能炸，但排查成本高；即使这次绕开，后续也会反复踩。

**建议**：文档明确 `namespace GameLogic`；或把目录改成 `Module/GameFlow/`（执行手册用的是 `Flow/`），彻底避开同名。

#### P2-11 验收负例不足

建议补 6 条：

1. 大厅窗口地址无效 → 有明确失败提示，能重试或退出。
2. `OnEnter` 里抛异常 → FSM 不进入半初始化状态，能回到 Lobby 或明确报错。
3. `ExitGame` 清理过程中抛异常/卡住 → 有超时或兜底，不会永远停在退出态。
4. 暂停期间样本加载完成 → 句柄被释放，恢复后结果不重复消费。
5. 退出时仍有加载在途 → 句柄被释放，迟到回调不写任何 UI/状态。
6. `GameApp.Entrance` 被调用两次（热更重入）→ `ReleaseLogic` 只注册一次，释放只执行一次。

#### P2-12 身份字段与执行手册不一致

01 只有 `RunId`；执行手册写的是“`RunId + generation`”。建议统一：`RunId`（每局递增）+ `generation`（每次 Start/Load 递增），或者明确首期不需要 generation，并把执行手册一起改。

#### P2-13 `UIWindow` 的 prefab 约束没写

`UIWindow.Handle_Completed` 要求根节点有 `Canvas`，否则抛异常（`UIWindow.cs:484-488`）；`GraphicRaycaster` 用于交互。新增 `ProjectBLobbyUI.prefab` 时要把这条写进步骤，否则第一次打开就会抛。

## 4. 候选实现方案

### 方案 A（推荐）：6 状态 + 集中转移 + 显式宿主 + 值契约

- **状态**：`Lobby`、`Loading`、`Running`、`Paused`、`Finished`（原 EndGame）、`Exiting`（原 ExitGame）。
- **决策**：`GameManager.Tick()` 统一消费加载结果和请求，按转移表返回下一个状态；状态只做 `OnEnter/OnLeave` 副作用。
- **宿主**：`GameApp` 显式 `new GameManager()` 并持有，不用 `Singleton<T>`。
- **结果**：`RunOutcome` 值类型，`Exiting` 是唯一发布点。
- **收尾**：`Application.quitting` + `AddDestroyListener` 双入口，幂等；先业务后框架。
- **优点**：职责清晰；`Tick` 可单测；异步/失败有出口；与 02/03 的战斗 FSM 分层一致。
- **缺点**：比 5 状态多一个；要改 01 文档骨架；窗口失败信号需要小改 UI 模块（或接受只记日志）。
- **适配度**：高。

### 方案 B（KISS 备选）：枚举 + switch + 子阶段

- `GameFlowState` 枚举 + `LoadingPhase`，`GameManager.Update` 里 switch。
- **优点**：代码少、无 FSM 学习成本、单文件可读；适合 01 期演示。
- **缺点**：状态逻辑与数据集中在一个类，后续接战斗/局内窗口会膨胀；失去 TEngine FSM 的 enter/leave 钩子；与 02/03 风格不统一。
- **适配度**：中。只建议作为 01 的临时形态，不作为长期骨架。

### 方案 C（分层/双 FSM）：AppFlow + RunFlow

- `AppFlow`：Lobby / Loading / InRun / Exiting；`RunFlow`：Running / Paused / Finished。
- **优点**：解决“StartGame 内分空闲/加载”和“暂停属于局内而非应用”的语义；与 03 的战斗三状态自然衔接；避免状态数爆炸（gpp 的并行状态机）。
- **缺点**：两个 FSM 的同步、销毁顺序要额外约定；01 期收益有限。
- **适配度**：中高。建议 03 接战斗时再拆，01 先用 A。

### 方案 D（不推荐）：复用 Procedure FSM

- 把大厅/对局加到 `GameScripts/Procedure`，`GameManager` 退化为服务。
- **优点**：复用现有启动流程，无第二套 FSM。
- **缺点**：`Procedure` 在非热更程序集，业务流程要跨热更边界；启动流程与局流程生命周期不同；与项目“热更边界”约束冲突。
- **适配度**：低。

**推荐排序**：A > C > B > D。

## 5. 推荐方案落地设计

### 5.1 状态表

| 状态 | 进入时 | 受理 | 出口 |
| --- | --- | --- | --- |
| `Lobby` | 打开/复用大厅窗口；清空或保留上次结果（二选一写清）；无活动会话 | `Start`、`Quit` | 受理 Start → `Loading`；大厅加载失败 → `Exiting(LoadFailed)` |
| `Loading` | 分配 `RunId`；`SampleRunLoader.Begin(runId)` | `Abandon` | 加载成功 → `Running`；失败/放弃 → `Exiting(LoadFailed/Abandoned)` |
| `Running` | 恢复输入；`_session` 存在 | `Pause`、`Abandon`、`SampleComplete` | `Paused`、`Finished`、`Exiting` |
| `Paused` | 冻结样本推进 | `Resume`、`Abandon` | `Running`、`Exiting` |
| `Finished` | 冻结并展示 `RunOutcome(Completed)` | `Return` | `Exiting`（沿用已冻结结果） |
| `Exiting` | 关输入、撤销装配资格、停会话、清资源 | 无（只等待清理完成） | 清理完成 → `Lobby` |

### 5.2 值契约

```csharp
enum ExitReason { Completed, Abandoned, LoadFailed, Faulted }

readonly struct RunOutcome
{
    public readonly int RunId;
    public readonly ExitReason Reason;
    public readonly int SampleProgress;
}

readonly struct LoadResult
{
    public readonly int RunId;
    public readonly bool Success;
    public readonly string SampleId;
    public readonly string Error;
}

readonly struct GameSnapshot
{
    public readonly GameFlowState State;
    public readonly bool IsLoading;
    public readonly int RunId;
    public readonly int SampleProgress;
    public readonly bool HasOutcome;      // 避免 default(RunOutcome) 被误读成 Completed/RunId=0
    public readonly RunOutcome LastOutcome;
    public readonly bool CanStart;
    public readonly bool CanPause;
    public readonly bool CanResume;
    public readonly bool CanAbandon;
    public readonly bool CanReturn;
}
```

请求统一为 `RequestStart()`、`RequestPause(int runId)`、`RequestResume(int runId)`、`RequestSampleComplete(int runId)`、`RequestAbandon(int runId)`、`RequestReturn(int runId)`，返回 `bool`（是否受理）。按钮只提交请求，不直接改状态。

### 5.3 更新顺序

```text
Tick(dt):
  1. _loader.Pump() → 已完成的操作（内部已 Dispose 句柄）→ 转成 LoadResult 入队
  2. 取当前状态可消费、且 RunId 匹配的请求
  3. 若 Running 且 _session 已提交自然结果 → Finished
  4. 若请求/事实允许放弃 → Exiting(Abandoned)
  5. 按当前状态处理 Start/Ready/Failed/Pause/Resume/Return
  6. 若仍在 Running → _session.Advance(dt) → 自然结束则 Finished
  7. 返回下一个状态类型（至多一个）
```

`OnEnter` 只做“值切换 + 请求入队”，UI/资源操作放到下一次 Tick，避免在 `Fsm.ChangeState` 的同步 `OnEnter` 里做重活或抛异常。

### 5.4 加载与身份

- `SampleRunLoader` 内部用 `Dictionary<int, LoadOp>` 记录每个 `RunId` 的 `AssetHandle`、状态和调试延迟；`Pump()` 返回已完成项。
- 完成时先复制 `TextAsset.text`，再 `Dispose()`，再生成 `LoadResult`；失败看 `handle.Status == EOperationStatus.Failed`。
- `Pump()` 对“不再是当前局”的结果只释放句柄，不入队；`Dispose()` 释放所有在途句柄（应用退出路径）。
- 同一局内如需重试加载，用 `generation` 或新的 `RunId`，不要让旧结果写进新会话。

### 5.5 暂停

- 暂停只冻结 `_session.Advance` 和输入；不改 `Time.timeScale`，不调 `RootModule.PauseGame()`。
- 画面表现暂停由 02 的帧驱动/动画参数负责；验收断言 `Time.timeScale == 1`。

### 5.6 关闭顺序

```text
OnQuit()  // Application.quitting 或 AddDestroyListener，幂等
  1. if (_released) return; _released = true;
  2. 关闭输入（窗口先留着，避免清理期间 UI 报空）
  3. _session?.Dispose()      // 停战斗、取消令牌
  4. _loader.Dispose()        // 所有在途句柄
  5. 关闭大厅窗口
  6. DestroyFsm（IsDestroyed 检查）
  7. SingletonSystem.Release()
  8. GameModule.Shutdown()
  9. GameEvent.Shutdown()
 10. RemoveDestroyListener
```

注意 2–6 必须在 7–8 之前；7 之后不要再访问 `GameModule.*`。`Application.quitting` 覆盖 player，`AddDestroyListener` 覆盖 Editor 和异常路径。

### 5.7 UI

- `ProjectBLobbyUI.OnCreate`：绑定按钮、订阅一个 `OnGameSnapshotChanged` int 事件、读当前快照渲染。
- `OnRefresh`：只按快照渲染；按钮可用性由 `GameSnapshot.CanXxx` 决定。
- 按钮：`GameManager.RequestX(snapshot.RunId)`；管理器再按当前状态和 RunId 校验。
- 窗口关闭：`UIWindow.InternalDestroy` 会 `RemoveAllUIEvent`（`UIWindow.cs:427-458`），不需要手工解绑。
- 窗口加载失败：如果采用 P0-3 的改法，`OnCreate` 不会触发，管理器需要收到失败结果并转到 `Lobby` 的失败提示。

### 5.8 文件与命名

- 统一 `namespace GameLogic`；不要用 `namespace GameLogic.Module.GameModule`。
- 目录建议 `Module/GameFlow/`（或执行手册的 `Flow/`），避免与全局类 `GameModule` 同名。
- 首期文件：`GameApp.cs`（改）、`Module/GameFlow/GameManager.cs`、`GameFlowState.cs`、`RunSession.cs`、`SampleRunLoader.cs`、`GameContracts.cs`、`Runtime/UI/ProjectBLobbyUI.cs`。

## 7. 设计思想

1. **状态模式（State）**：把“每个状态的合法输入、副作用、出口”封装起来；进入/退出动作集中处理通用逻辑（gpp 的 enter/exit actions）。01 已经在用，问题不在模式，而在“谁裁决迁移”。
2. **命令模式（Command）**：按钮和异步回报只提交不可变请求（带 `RunId`），不直接改状态；保证“单一写者”，这也是 Boss Room 和 QFramework 的共同做法。
3. **观察者（Observer）**：快照变更只发“失效通知”，UI 主动读快照；事件不携带可变业务对象，避免 UI 持有管理器内部状态。
4. **端口/适配器（Port/Adapter）**：`SampleRunLoader` 是资源端口适配器，`RunSession` 是局端口；`GameManager` 不直接依赖 YooAsset/UIWindow，方便替换和测试。
5. **身份令牌（Epoch/Token）**：`RunId` 是逻辑身份，`CancellationToken` 是生命周期令牌；二者互补。01 只有前者，建议至少把 `RunId` 校验做在“所有”异步消费点，而不是只做在加载完成处。
6. **显式生命周期（Explicit Lifecycle）**：创建、装配、运行、收尾、销毁分开；不依赖 Unity 跨对象的 `OnDestroy` 顺序（可靠的钩子是 `Application.quitting`/`wantsToQuit`，见 UnityCsReference）。
7. **失败是一等公民**：加载失败、窗口失败、清理失败都要有状态出口和可重试路径；不要用“日志 + 静默”代替。
8. **分层**：应用流程（01）、局流程（03）、战斗流程（03 的三状态）各自独立；不要把所有状态塞进一个 FSM。

对应设计原则：SRP（状态/加载/会话/UI 分开）、OCP（新增状态不改旧状态）、DIP（依赖值契约和端口，不依赖具体窗口/资源 API）、KISS（6 个状态够用，不引入 HFSM/行为树）、YAGNI（不做存档、回放、多角色选择）。
