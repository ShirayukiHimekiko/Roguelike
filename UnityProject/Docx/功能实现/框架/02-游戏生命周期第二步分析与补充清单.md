# 游戏生命周期第二步：补充内容分析

2026-11-16 · 分析稿（按 22:43 最新代码）

第一步已经落盘的是“能创建 FSM、能订阅应用事件、能切几个状态”的骨架。第二步先不要急着接固定帧或战斗，先把**生命周期真正闭环**需要的东西补齐。本文按当前代码逐项列缺口、优先级和建议范围。

## 1. 当前实现盘点

| 已有 | 位置 | 说明 |
|---|---|---|
| `GameAppManager` 单例 | `GameAppManager.cs` | 持有 FSM，创建 5 个状态，订阅暂停/退出 |
| 5 个状态 + 基类 | `State/` | `Start → Run`；`Exit → End`；Run/Pause/End 为空 |
| GameApp 接线 | `GameApp.cs:36-41` | `StartGameLogic` 是 `async UniTaskVoid`，`await UniTask.Yield()` 后 `GameAppManager.Instance.Start()` |
| 应用暂停/恢复 | `GameAppManager.cs:66-88` | 直接切 Pause/Run |
| 游戏退出 | `GameAppManager.cs:90-102` | 切 Exit；`ExitGameState.OnEnter` 再切 End |
| 释放 | `GameAppManager.cs:104-128` | 退订、销毁 FSM；不再切 End |
| TEngine 退出事件 | `Utility.Unity` | 新增 `AddOnApplicationQuitListener` |

当前**没有**的：自然结束、Exit 清理后回 Start、单局数据、结果、状态迁移保护、异步启动的释放保护。

## 2. 缺口清单

### P0：不补会出错误或资源泄漏

| # | 缺口 | 证据 | 影响 | 最小补充 |
|---|---|---|---|---|
| P0-1 | 异步启动没有释放保护 | `GameApp.cs:36-41`：`await UniTask.Yield()` 后才 `Instance.Start()`；`ReleaseLogic` 没有取消/`_released` 标记 | 这一帧内退出时，`ReleaseLogic` 先释放，随后 continuation 仍会创建 Manager/FSM，退出后又冒出一个单例 | 加 `_released` 标记或 `CancellationToken`；`ReleaseLogic` 先置位，continuation 检查后直接返回 |
| P0-2 | `OnRelease` 在 `!_isStarted` 时直接 return | `GameAppManager.cs:106-111` | `OnInit` 已创建 FSM、订阅事件；未 `Start()` 就释放时不会退订、不会销毁 FSM | 释放无条件退订并销毁 FSM；`_isStarted` 只控制“是否启动过”，不控制清理 |
| P0-3 | 暂停/恢复不判断当前状态 | `GameAppManager.cs:66-88` | End/Exit 收到暂停/恢复会被切到 Pause/Run，状态被拉回 | 只在 `RunGameState` 接受暂停、只在 `PauseGameState` 接受恢复 |
| P0-4 | `_currentState` 可能返回 null，调用方直接 `.SwitchState` | `GameAppManager.cs:15-28`、`78/85/99` | 异常路径 NRE | 事件回调先判 null，或 `SwitchState` 返回 bool |
| P0-5 | `SwitchState` 的自切换保护只在编辑器生效 | `State/GameAppState.cs:12-18` 用 `#if UNITY_EDITOR` 包住 `GetType()==typeof(TState)` | 真机上同状态切换会重新 `OnLeave/OnEnter`；当前状态 OnEnter 为空所以不炸，但行为与编辑器不一致 | 去掉 `#if`，或明确只在编辑器需要该保护并注释原因 |
| P0-6 | `GameApp.ReleaseLogic` 不显式释放 Manager | `GameApp.cs:43-48` 直接 `SingletonSystem.Release()` | 依赖单例释放顺序；异步启动竞态下更不可控 | 先 `GameAppManager.Instance.Release()`（`IsValid` 判断），再走 `SingletonSystem.Release()` / `GameModule.Shutdown()` |

### P1：生命周期功能缺失

| # | 缺口 | 现状 | 需要补充 |
|---|---|---|---|
| P1-1 | 自然结束不可达 | `RunGameState` 为空；`EndGameState` 只在 `ExitGameState.OnEnter` 里被切到 | 给 Run 一个结束条件（计时/外部 `EndGame()`/战斗结果），进入 End |
| P1-2 | Exit 没有清理与回 Start | `ExitGameState.OnEnter` 只 `ChangeState<EndGameState>`；End 为空 | End 做结果冻结；Exit/End 清理后回 `StartGameState`，支持再开一局 |
| P1-3 | 没有单局数据 | Manager 只有 `_fsm`/`_isStarted` | `RunId`、进度、开始时间、是否已结束 |
| P1-4 | 没有结果与一次性发布 | 无 `RunOutcome` | `Completed/Abandoned/Faulted` + 只发布一次 |
| P1-5 | 没有主动结束/放弃入口 | 只有应用暂停/退出 | `EndGame()` / `AbandonGame()`；与自然结束区分 |
| P1-6 | 应用暂停与玩法暂停混在一起 | 只有 `OnApplicationPause` | 区分“切后台”与“玩家暂停”；是否共用 Pause 状态要先定 |
| P1-7 | 没有故障兜底 | 状态切换异常直接抛出 | `SwitchState`/事件回调 try-catch，转 Exit 或记录后保持稳定 |
| P1-8 | `Start` 日志没有状态名 | `GameAppManager.cs:63` 只打 `fsm started` | 记录启动后实际状态，便于确认 `Start → Run` |

### P2：诊断与维护

| # | 缺口 | 建议 |
|---|---|---|
| P2-1 | 状态进入/离开没有日志 | 至少记录 `RunId`、from/to、原因 |
| P2-2 | 没有手动驱动入口 | 临时调试方法或 GM/Console 调用 `EndGame/Abandon`，否则无法验收 |
| P2-3 | `_isStarted` 在 `_fsm.IsRunning` 检查前置 true | 先判断，或把两个标记合成一个 |
| P2-4 | 单例释放后仍可能被 `Instance` 复活 | 迟到回调不要用 `Instance`；提供 `TryGet` 或只由组合根访问 |
| P2-5 | 没有 Release 顺序保证 | `GameApp.ReleaseLogic` 先 `GameAppManager.Release()`，再 `SingletonSystem.Release()` / `GameModule.Shutdown()` |

## 3. 第二步建议范围

### 推荐：先做生命周期闭环（不接固定帧）

按这个顺序补，范围小且能验收：

1. **异步启动/释放安全**：`GameApp.StartGameLogic` 加 `_released` 或取消令牌；`ReleaseLogic` 先释放 Manager，再走框架清理。
2. **修 P0**：未启动释放的清理、暂停/恢复状态校验、`_currentState` 空判断、自切换保护去掉编辑器条件。
3. **单局数据**：`RunId`、进度、开始/结束标记；Start 进入时初始化，Exit 完成时清理。
4. **自然结束**：Run 的结束条件（先计时或手动 `EndGame()`），进入 End 并冻结结果。
5. **结果**：`RunOutcome`（Completed/Abandoned/Faulted），End 只发布一次。
6. **Exit/End 闭环**：清理后回 `StartGameState`；`AbandonGame()` 走 Exit。
7. **验收**：启动 → 暂停/恢复 → 自然结束 → 返回 → 再开一局；异常路径不 NRE、不复活 Manager。

### 不建议现在做

- 固定帧驱动（原 `02-Project_B固定帧驱动分步执行方案.md`）：需要 Run 有稳定的“每帧推进”消费点；当前 Run 是空类，先接帧没有业务可驱动。
- 战斗模块、UI、样本/资源加载、存档/回放：都依赖生命周期先有结果和 Exit 闭环。

### 如果“第二步”指原 02 固定帧

原 02 需要新增 `FrameManager/FrameCore/FrameClock/FrameTimer/FixedPoint/ClockProbeChannel/FrameProbeWindow`，并修改 `GameApp` 装配。但它至少依赖当前这几项先完成：

| 原 02 依赖 | 当前状态 |
|---|---|
| `GameApp` 启动业务 Manager | **已完成**，但异步启动有释放竞态（P0-1） |
| Run 状态有推进入口 | 未实现，Run 为空 |
| Exit/End 能清理并回大厅 | 未实现，Exit 只切 End |
| 释放顺序稳定 | OnRelease 有未启动早退（P0-2）、GameApp 未显式释放（P0-6） |

所以建议把原 02 放到“生命周期闭环”之后，否则帧驱动没有消费者，验收只能看探针。

## 4. 建议执行顺序

| 步 | 内容 | 完成标志 |
|---|---|---|
| 2.1 | 异步启动/释放安全 + `GameApp` 显式释放 Manager | 启动后 `fsm started`；这一帧退出不会复活 Manager |
| 2.2 | 修 P0-2/3/4/5 | 未启动释放也退订/销毁；End/Exit 不会被暂停/恢复拉回；无 NRE |
| 2.3 | 单局数据 + 自然结束 | Run 能按条件进入 End，`RunId` 递增 |
| 2.4 | 结果 + Exit/End 闭环 | 每局只出现一次结果；清理后回 Start，可再开 |
| 2.5 | 主动放弃/手动结束 | `Abandon/End` 可从允许的状态进入 |
| 2.6 | 日志与验收 | 日志含 from/to、RunId、结果原因 |

## 5. 验收用例

| 用例 | 预期 |
|---|---|
| 启动 | `GameApp.StartGameLogic` 后 `fsm started`，当前 Run |
| 启动帧内退出 | 不创建 Manager/FSM，不出现退出后的 `manager released` 或状态日志 |
| 切后台/回前台 | Run ↔ Pause，且只在合法状态发生 |
| 自然结束 | Run 到条件后进入 End，结果 Completed 只出现一次 |
| 主动放弃 | 从 Run/Pause 进入 Exit，结果 Abandoned，回 Start |
| 再开一局 | Start 可再次进入 Run，`RunId` 不同 |
| 结束/退出时暂停 | End/Exit 不会被暂停/恢复改成 Pause/Run |
| 未启动就释放 | 退订、销毁 FSM，不 NRE |
| player 关闭 | 先切 Exit，再 End，再 `OnRelease` 销毁，不因 FSM 已回收 NRE |
| 重复 Start | 只启动一次，有 ignore 日志 |

## 6. 需要你确认的取舍

1. **第二步范围**：先做“生命周期闭环”，还是直接做原 02 固定帧？
2. **End 的触发**：先用手动 `EndGame()`/计时，还是等战斗结果？
3. **结果模型**：现在只加 `Completed/Abandoned/Faulted`，还是连奖励/结算一起设计？
4. **应用暂停与玩法暂停**：共用 `PauseGameState`，还是只把 `OnApplicationPause` 当作切后台、另设玩法暂停？
5. **异步启动**：`StartGameLogic` 的 `await UniTask.Yield()` 是暂时写法，还是准备长期保留？如果保留，必须配取消/释放保护。

## 7. 结论

第二步真正要补的不是新框架，而是四件事：**异步启动/释放安全、状态安全、单局数据/结果、End/Exit 闭环**。固定帧、战斗、UI 都应排在这四件事之后；否则 FSM 只是一个能被暂停的空壳，没有可验收的生命周期。
