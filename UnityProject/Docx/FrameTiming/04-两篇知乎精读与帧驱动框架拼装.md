# 两篇知乎精读：逻辑帧驱动框架的两种实现与拼装方案

阅读日期：2026-11-14（Asia/Shanghai）。
阅读方式：用户提供的 8 张长截图（6 张文章一、1 张文章二、1 张相关问答）。截图内小字代码可能存在识别误差，凡不确定处标注“待核对原文”。

- 文章一：《Unity动作游戏【二】:如何设计一套逻辑帧驱动框架?》，知乎 @hutian2501。
- 文章二：《Unity3D 逻辑帧驱动框架设计》，知乎 @RYCW_ 猩猩。

## 0. 一句话结论

**文章一是“调度/时间层”的生产级设计，文章二是“固定帧 + 帧定时器”的最小演示。两篇都不含动作帧数据、输入缓冲和取消窗口；真正要落地，需要把文章一的时间层、XMLib.AM 的数据层、自研的输入层拼起来。**

## 1. 文章一拆解（@hutian2501）

### 1.1 它解决的核心问题

文章把游戏世界抽象成一条时间轴：`SceneStep()` 包含“世界更新一次”的全部逻辑，按固定间隔执行，60fps 即每秒 60 次。为了回放，提供 `Global.TimeScale` 调整执行频率（加速/减速/暂停）。

这不是“动画帧驱动”，而是**逻辑时钟 + 调度 + 生命周期**的底座。

### 1.2 五个设计块

**（1）双时间轴**

- Global 时间轴控制整个世界；
- 每个 Unit 有自己的时间轴与 `Unit.TimeScale`；
- Global 影响所有 Unit，Unit 只影响自己；
- 由此实现三种效果：
  - 顿帧：攻击命中后，攻击方停在命中帧，受击方切到受击状态并停在同一帧，通常 0.05s–0.2s；
  - 子弹时间：某单位或全局减速；
  - 时间静止：全局暂停，但可保留部分例外。

这是全文最有价值的设计：**把 hitstop 从“改 `Time.timeScale`”变成“时间轴暂停”，避免表现层和逻辑层一起被拖慢。**

**（2）帧定时任务**

三类任务：

- `OnceTimer`：第 N 帧执行一次；
- `RepeatTimer`：每 N 帧执行一次；
- `OnceWaitTimer`：`async/await` 等待 N 帧，可取消。

实现上：`BTimerAction { id, TimerClass, object, startFrame, frame, Type }`；`BTimerComponent` 用 `SortedDictionary<long, List<long>>` 按到期帧索引，记录 `minFrame` 以跳过空帧；到期后执行，`RepeatTimer` 重新排入下一周期。

**（3）生命周期分层**

`SceneStep()` 内部顺序：

```
LogicUpdate
  → PhysicUpdate（PreStep → Step → PostStep）
    → LateUpdate
```

- `LogicUpdate`：输入检测、角色/场景碰撞检测（Box2DSharp）、技能逻辑；
- `PhysicUpdate`：`World.Step`；Box2D 的 PreStep/PostStep 用于在 Step 前缓存碰撞信息、Step 后再取，避免“位置还没解析完就处理命中”；
- `LateUpdate`：动画、特效等表现层。

命中检测放在 PostStep，是这套设计里第二个值得抄的点：**先让物理把位置解算完，再做判定和伤害。**

**（4）基于 ET 的异步**

项目组基于 ET 框架，选择 `ETTask` 而不是 Coroutine/UniTask：可取消、可等待、异常可传播。`OnceWaitTimer` 就是 `ETTask` + `CancellationToken` 的封装。

**（5）事件与系统扩展**

用 ET 的 `ObjectSystem` / `EventSystem` 扩展生命周期：`FrameLateUpdateSystem`、`IFrameLateUpdate`、`[ObjectSystem]`、按类型索引批量更新。`BTimerManager` 作为单例，统一驱动所有 `BTimerComponent`。

### 1.3 文章一没有覆盖什么

- **没有帧数据/动作机**：没有 StateConfig、FrameConfig、Hitbox/Hurtbox、取消窗口；
- **没有输入缓冲**：只提到“输入检测在 LogicUpdate”，没有缓冲长度、消费时机、与帧对齐；
- **没有确定性/回滚**：`Global.TimeScale` 改的是执行频率，联机场景下不可用；也没有定点数、快照、校验；
- **没有表现层插值**：LateUpdate 只做动画/特效，没有“逻辑帧与渲染帧之间插值”的方案；
- **强绑定 ET**：`Entity/Component/ObjectSystem/ETTask/EventSystem`，直接搬进 TEngine 不能编译，只能搬设计。

## 2. 文章二拆解（@RYCW_ 猩猩）

### 2.1 结构

1. 核心设计思路：固定帧率 + 帧更新接口 + 帧定时器；
2. 核心实现：
   - `FrameController : MonoBehaviour`，`FRAME_RATE = 60`，`CURRENT_FRAME`，`accumulator`；
   - `Update()` 累加 `Time.deltaTime`，`while (accumulator >= 1/60)` 执行 `FrameUpdate()`；
   - `FrameUpdate()` 递增 `CURRENT_FRAME`，遍历 `IFrameUpdate`；
   - `FrameTimerManager`：`SortedDictionary<long, List<Action>>`，按帧号挂回调；
   - `UnitBase` / `UnitManager` / `PlayerController : MonoBehaviour, IFrameUpdate`；
3. 应用示例：移动、攻击；
4. 常见攻防：定时器、帧动画等；
5. 测试工具：`FrameDebugger`（OnGUI 显示帧号、暂停、单步）。

### 2.2 定位

这是一个**入门级最小闭环**：

- 能证明“固定帧 + 帧回调 + 帧定时器”可行；
- 但没有多时间轴、生命周期分层、物理集成、确定性、插值、回滚；
- `Update` 里的 `while` 没有追帧上限，卡顿后可能一次补很多帧；
- 截图范围内没有看到输入缓冲、取消窗口、hitbox 数据。

**它适合用来验证概念，不适合作为生产框架。**

## 4. 与 XMLib.AM / Klotho / TEngine 的关系

### 4.1 分层拼装

```
帧源与调度（文章一）        ← 时间轴、生命周期、帧定时器、双时间轴
  → 动作帧数据（XMLib.AM）  ← State/Frame/Range/Action、逐帧 Hitbox
    → 输入与窗口（自研）     ← 输入缓冲、取消窗口、连招图
      → 确定性/联机（Klotho）← 定点数、快照、回滚、校验
        → 表现层（自研）     ← Animator.Play 进度、插值、特效
```

### 4.2 关键差异

- **XMLib.AM 的 `waitFrameCnt` 是“整机顿帧”**：它只能让当前 ActionMachine 暂停，不能做到“攻击方停、受击方也停，但其他单位继续”。文章一的 `Unit.TimeScale` 粒度更细。
- **Klotho 的 tick 是固定且不可变速的**：文章一的 `Global.TimeScale` 只能用于单机/回放；联机必须固定 tick，用“每渲染帧跑 N 个 tick”而不是改 tick 长度。
- **TEngine 的 `GameModule.Timer` 是秒制**：不能直接拿来当战斗帧时钟；应新增独立模块，避免 UI 计时和战斗计时互相污染。

### 4.3 迁移到 TEngine 的替换表

| 文章一 | TEngine 对应 |
| --- | --- |
| `ETTask` | `UniTask` |
| ET `Entity/Component` | 普通 C# 类 + 模块内聚合 |
| ET `ObjectSystem/EventSystem` | 模块 Update + `GameEvent` / 直接接口 |
| `BTimerManager` 单例 | `GameModule.Frame` 模块 |
| Box2DSharp | 先评估：若只做 hitbox 重叠查询，可不引入 |
| `Global.TimeScale` | 仅单机/回放启用；联机模式禁用 |

## 5. 建议的落地顺序

### M0：帧源与调度（1–2 天）

- `FrameClock`：整数 tick、60Hz、累加器、最大追帧数（如 4）、暂停；
- `FrameScheduler`：每帧固定阶段 `Logic → Physics → Late`；
- `FrameTimer`：Once / Repeat / Wait，按 tick 索引，支持取消。

### M1：双时间轴（2–3 天）

- `TimeAxis`：Global + Unit；
- 规则：Unit 定时器走 Unit 轴，全局定时器走 Global 轴，表现层走 Unscaled；
- 顿帧 = Unit 轴冻结 N tick；慢动作 = scale < 1；时间静止 = Global 暂停 + 白名单。

### M2：动作帧数据（3–5 天）

- 参考 XMLib.AM：`StateConfig → FrameConfig[] → RangeConfig`；
- Luban 表：状态、帧、事件、hitbox、取消窗口；
- 动作执行：帧号 + Enter/Update/Exit，不依赖 Animator 事件。

### M3：输入与窗口（3–5 天）

- 输入缓冲：按下后保留 N 帧，消费即清除；
- 取消窗口：`[startFrame, endFrame]` + 目标状态优先级；
- 连招图：当前状态 + 输入 → 目标状态。

### M4：表现层（2–3 天）

- `Animator.Play(name, layer, normalizedTime)`，`speed = 0`；
- 渲染插值：上一逻辑帧/当前逻辑帧 + alpha；
- 顿帧时表现层可继续播特效，但角色动画冻结。

### M5：可选联机

- 评估 Klotho；固定 tick；定点数；快照/回滚；不要复用 `Global.TimeScale`。

## 6. 风险与待确认

1. **截图代码细节**：`accumulator` 的扣减、`while` 条件在截图中偏小，可能有识别误差，正式实现前需核对原文。
2. **Box2DSharp 是否引入**：如果只做动作游戏的 hitbox 重叠，Unity 的 `Physics.OverlapBox` 足够；引入 Box2D 会增加确定性和调试成本。
3. **单位规模**：每个 Unit 一个 `BTimerComponent` + 定时器字典，同屏几百单位时的内存/遍历成本需要实测。
4. **回放需求**：文章一只做了“变速”，没有输入录制/回放格式；若要回放，需要额外设计。
5. **ET 代码来源与许可**：文章代码基于 ET 框架，直接复制需确认 ET 的许可与版本。

## 7. 四份补充材料的交叉验证

### 7.1 《Unity 逻辑帧与渲染帧分离》（jackylvm，2026-03）

- 核心实现：`LogicFrameManager` 用累加器 + 固定步长；关闭 Unity 自动物理（`Physics.autoSimulation = false`），每个逻辑帧手动 `Physics.Simulate(dt)`；渲染层保存上一逻辑帧快照，用 `interpFactor = accumulatedTime / fixedDelta` 做 `Lerp`。
- 三条铁律：逻辑→渲染只读；渲染→逻辑只发指令；所有状态只由逻辑帧产生。
- 价值：补上了文章一缺的**表现层插值**具体做法，也给出“Unity 物理跟随逻辑帧”的简洁写法。
- 问题：示例代码有笔误（`GetComponent<LogicFrameManager>()`、访问私有字段），不能直接编译；`while` 没有追帧上限；float 时间不可跨平台确定。
- 对项目：插值公式和“单向数据流”可直接用；物理方案二选一（Unity `Physics.Simulate` vs Box2DSharp）。

### 7.2 《ECS 逻辑帧驱动的性能与即时性问题》（CSDN，2024-01）

- 核心：所有 system 由逻辑帧驱动，会带来“帧间资源空闲”和“系统顺序导致的 1 帧延迟”。
- 客户端：系统排序（先记录输入，再网络发送）；服务器：可灵活调帧率、不同系统不同帧率、网络系统脱离逻辑帧；但**客户端必须固定帧率**，否则帧同步复杂度爆炸。
- 价值：提醒“调度器不只是时间，还要管系统顺序”；输入系统必须在网络发送之前，网络接收必须在逻辑之前。
- 对项目：M0 的 Scheduler 要把 Input / Network / Logic / Physics / View 的顺序写死并测试；不要一开始就上“不同系统不同帧率”。

### 7.3 Klotho《SynchronizationDesign.md》

- 确定性是地基：FP64、无 float、Xorshift128+；状态是输入的纯函数。
- 双链：Verified（输入齐、不可变）vs Predicted（猜测、可回滚）；事件分 Regular（可预测、可撤销）与 Synced（验证后一次）。
- 四个域：predict / time / verify / recover；输入延迟、共享 epoch、中位数 frame advantage、自适应延迟、verified render clock（drift 比例控制，0.5–2.0，>10 tick 直接 snap）。
- 回滚：快照环 `MaxRollbackTicks + 2`；同帧多次失配合并到最早 tick；重模拟走同一条预测路径。
- 恢复阶梯：哈希门 → 回滚 → 全量状态重同步 → 校正重置 → 中止。
- 非目标：不做状态复制、不容忍 float、P2P 不做 host 故障转移。
- 对项目：如果未来联机，`Global.TimeScale` 必须禁用；固定 tick + 输入延迟 + 回滚；单机阶段不要引入这套复杂度，但要把“逻辑层不写 float/DateTime/Random”作为纪律保留。

### 7.4 XMLib.AM `ActionMachine.cs`

- 执行顺序：`UpdateState → UpdateGlobalFrame → UpdateState → UpdateFrame`；`globalFrameIndex` 不受顿帧影响，`waitFrameCnt` 只冻结当前 machine。
- `FrameConfig` 每帧挂 attack/body ranges；`StateConfig` 有 animNames / fadeTime / loop / nextState / actions；`ChangeState` 带优先级。
- 缺口：`ChangeAnim` 直接抛 `NotImplementedException`；没有输入缓冲/取消窗口；没有多时间轴。
- 对项目：作为“单位动作机”嵌入文章一的 Unit 时间轴；命中检测放 PostStep，用当前帧 ranges 做查询，而不是在 ActionMachine 内直接结算。

### 7.5 四份材料拼出的最终分层

| 层 | 采用 | 来源 |
| --- | --- | --- |
| 全局帧源 | 整数 tick + 累加器 + 追帧上限 | 文章一 / 文章二 / jackylvm |
| 单位时间轴 | Unit.TimeScale + 顿帧 / 慢动作 / 时停 | 文章一 |
| 调度顺序 | Input → Logic → Physics(Pre/Step/Post) → Late；网络收发在两端 | 文章一 + CSDN ECS |
| 定时器 | Once / Repeat / Wait，按 tick 索引 | 文章一 |
| 动作机 | State / Frame / Range / Action | XMLib.AM |
| 输入/窗口 | 缓冲 + 取消窗口 + 连招 | 自研（CSDN #22 示例） |
| 表现 | 快照 + Lerp + Animator.Play | jackylvm + 文章一 |
| 联机 | 固定 tick + 预测/回滚 + 恢复阶梯 | Klotho |

### 7.6 三个必须提前定的取舍

1. `Global.TimeScale` 只用于单机/回放；联机模式编译期禁用。
2. 物理：Unity `Physics.Simulate`（简单）vs Box2DSharp（可控）——先做 hitbox 查询，不急着引入刚体。
3. 确定性纪律：单机可以用 float，但逻辑层禁止 `DateTime` / `Random` / Unity 物理；为未来留路。

## 8. 结论

- 文章一值得抄的是**双时间轴、生命周期分层、帧定时器**，不是 ET 代码；
- 文章二只适合作为“固定帧”概念验证；
- 完整的帧驱动动作系统 = 文章一的时间层 + XMLib.AM 的数据层 + 自研输入/窗口层 + 可选 Klotho 的联机层；
- 建议先在 TEngine 内做 M0/M1 的最小实现，再决定是否引入 XMLib.AM 的数据模型。
