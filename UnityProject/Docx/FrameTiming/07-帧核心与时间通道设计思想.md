## 0. 一句话

**`FrameCore` 是全局的“时间与调度核心”，`TimeChannel` 是彼此独立的时间通道。** 战斗是第一个通道，UI、过场、服务器后续各占一个通道；每个通道有自己的 tick、缩放、暂停和定时器，互不拖累。

---

## 1. 为什么需要这个核心

没有核心时，常见写法是：

- 逻辑写在 `Update()` 里，帧率一变，行为就变；
- 战斗、UI、过场共用 `Time.timeScale`，一暂停全冻；
- 动画、移动、判定混在 `MonoBehaviour` 里，无法单独测试；
- 卡顿后逻辑一次补很多帧，出现“快进”；
- 表现直接改逻辑状态，插值/回放都做不了。

核心要解决的是“时间怎么分、按什么顺序走”，而不是“战斗怎么打”。

## 2. 核心思想

### 2.1 文章一是主干，其他资料只补它没讲的部分

文章一（hutian2501）给了完整的逻辑帧骨架：

- `SceneStep()` 是逻辑帧；
- `Global.TimeScale` + `Unit.TimeScale`；
- `Once/Repeat/OnceWait` 三类帧定时任务；
- `LogicUpdate → PhysicUpdate(PreStep/Step/PostStep) → LateUpdate`；
- `BTimerComponent` / `BTimerManager` / `BTimerAction` / `BTimerHandler`。

其他资料只作为补丁：

| 来源 | 只补什么 |
| --- | --- |
| jackylvm | `Alpha` 插值、prev/current 表现层 |
| XMLib.AM | 后续动作数据 |
| LittleBee | 未来快照/回滚参考 |
| Klotho | 未来联机固定 tick/FP64 |
| CSDN ECS 文章 | 系统顺序 |

### 2.2 全局核心只懂“时间与顺序”

`FrameCore` 不持有战斗规则、不持有 UI 逻辑、不持有全局 TimeAxis。它只做：

- 注册/排序 `TimeChannel`；
- 每渲染帧把 `deltaTime` 分发给各通道；
- 统一启停/销毁。

### 2.3 每个通道有自己的时间

`TimeChannel` 自己拥有：

- `FrameClock`（tick 率、累加器、Alpha）；
- `Scale` / `Paused`；
- `FrameTimer`；
- 自己的 World/Systems（如果有）。

所以：

- 战斗顿帧不影响 UI；
- UI 暂停不影响战斗；
- 过场减速不影响服务器模拟。

### 2.4 固定 tick 是契约

战斗通道 60Hz；UI 通道可以按渲染帧；过场可以按 Timeline；服务器未来固定 tick。每个通道自己定义，不强制统一。

### 2.5 逻辑与表现分离

逻辑通道只产出数据；表现层用 `Alpha` 插值。通道不知道 View，View 不写通道状态。

### 2.6 顺序是行为的一部分

`FrameCore` 按 `Order` 排序通道；通道内部按 `BattleScheduler` 的顺序执行系统。顺序显式、固定、可审查。

### 2.7 核心不提供游戏规则

动作帧、输入缓冲、Hitbox、伤害、AI、网络都不属于 `FrameCore`；它们是通道之上的层。

### 2.8 全面设计，分步实现

基础框架的“全面”体现在接口和分层：

- `ITimeChannel` 抽象完整；
- 通道注册/排序/暂停契约完整；
- 第一版只实现 `BattleTimeChannel`；
- `UiTimeChannel` / `CutsceneTimeChannel` / `ServerTimeChannel` 先留接口，不实现。

## 3. 设计原则映射

| 原则 | 体现 |
| --- | --- |
| 单一职责 | FrameCore 只管通道；FrameClock 只管 tick；FrameTimer 只管到期；通道只管自己的域 |
| 开闭原则 | 新增域 = 新增 `ITimeChannel`，不改 FrameCore |
| 依赖倒置 | 表现层依赖只读数据，不依赖通道实现 |
| 组合优于继承 | 通道组合 Clock/Timer/Scheduler |
| KISS | 第一版 11 个文件，只实现战斗通道 |
| YAGNI | UI/过场/服务器只留接口，不提前实现 |

## 4. 对象职责

| 对象 | 只做什么 | 不做什么 |
| --- | --- | --- |
| `FrameCore` | 注册/排序/驱动 `ITimeChannel` | 不知道战斗/UI |
| `FrameClock` | 累加时间、产出 tick、暂停/单步、Alpha | 不知道业务 |
| `FrameTimer` | 按 tick 到期执行 Once/Repeat/Wait | 不关心任务内容 |
| `ITimeChannel` | 通道契约：Name/Order/Paused/Scale/Update | 不暴露具体实现 |
| `BattleTimeChannel` | 战斗通道：Clock + TimeAxis + Scheduler + World | 不碰 UI/网络 |
| `BattleTimeAxis` | Global/Unit 缩放、冻结 | 不执行逻辑 |
| `BattleScheduler` | Input → Logic → Physic → Late | 不实现系统 |
| `BattleWorld` | Units + Systems + Tick | 不创建 GameObject |
| `BattleUnit` | 纯数据单位 | 不引用 MonoBehaviour |
| `IBattleSystem` | 一个逻辑单元 | 不持有 View |
| `BattleView` | 读数据、插值、驱动表现 | 不写逻辑 |

## 5. 一帧的语义

```
Update():
  frameCore.Update(Time.deltaTime)      // 按 Order 驱动所有通道

  BattleTimeChannel.Update(delta):
      ticks = clock.Advance(delta)      // 只计算 tick 数
      for i in 0..ticks-1:
          world.Tick()
            clock.Step()                // Tick++
            timeAxis.Tick(units)
            timer.Tick(clock.Tick)
            scheduler.Input()
            scheduler.Logic()
            scheduler.Physic()          // PreStep → Step → PostStep
            scheduler.Late()

  view.Render(battleChannel.Clock.Alpha)  // 每渲染帧一次
```

规则：

- `FrameCore` 不累加时间，只分发 `deltaTime`；
- 每个通道自己决定 tick 率；
- 暂停在通道内处理，不污染其他通道；
- 表现层只读。

---

## 6. 为什么不用这些现成机制

| 机制 | 问题 |
| --- | --- |
| `Update()` 直接写逻辑 | 帧率变，行为变 |
| `FixedUpdate()` | 受 Unity 物理时钟影响，与渲染/暂停/回放耦合 |
| `Time.timeScale` 做全局暂停 | UI、过场、特效一起冻 |
| Coroutine 做帧等待 | 生命周期难控 |
| 秒制 Timer 做战斗冷却 | 逻辑帧与秒制时间漂移 |
| 单一全局 tick | 不同域需要不同 tick，强绑会互相拖累 |

---

## 7. 这个核心刻意不做什么

- 不做动作帧数据、ActionMachine；
- 不做输入缓冲、取消窗口、连招；
- 不做 Hitbox/Hurtbox、伤害；
- 不做 Entitas 接入；
- 不做联机、快照、回滚；
- 不实现 UI/过场/服务器通道；
- 不修改场景、Prefab、ProjectSettings。

### 8.12 适用范围

**FrameCore 可复用**：任何需要“独立时间流”的系统。

**BattleTimeChannel 专用**：顿帧、动作帧、Hitbox、连招、战斗输入。

**UiTimeChannel**：UI 冷却/倒计时，用 Unscaled，不受战斗暂停。

**CutsceneTimeChannel**：过场/教程，自己的 Scale/Pause。

**ServerTimeChannel**：未来服务器固定 tick。

关键：**模式可复用，实例不混用。** UI/过场不要直接读 `BattleTimeAxis`。

| 双时间轴 | `BattleTimeChannel` | Global + Unit | `BattleTimeAxis` | P1 |
| 帧定时器 | `FrameCore` 原语 | 每个通道各自 | `FrameTimer` | P1 |

### 8.14 双时间轴与 FrameTimer 的分工

**双时间轴**只管“推进不推进、推进多快”：

- `GlobalScale`：战斗暂停、回放变速、全局慢动作；
- `UnitScale` / `FreezeTicks`：单位顿帧、单位慢动作、时停白名单。

**FrameTimer** 只管“到点执行”，但要分作用域：

| 计时器 | 挂在哪个轴 | 典型用途 |
| --- | --- | --- |
| `GlobalTimer` | 战斗全局 tick | 技能冷却、Buff 持续时间、AI 思考间隔、关卡事件 |
| `UnitTimer` | 单位自己的 tick | 硬直、无敌帧、动作帧、单位冻结恢复 |
| `ChannelTimer` | 通道自己的 tick | 过场/教程的延迟、UI 冷却 |

规则：

1. **冷却、Buff、AI、关卡事件用 GlobalTimer**：它们不该因为某个单位被顿帧而暂停。
2. **硬直、无敌、动作帧用 UnitTimer**：单位被冻结时，这些计时应该一起停。
3. **顿帧只冻结 UnitTimer 与单位动作/移动**，GlobalTimer 继续走；这是可配置策略，但默认如此。
4. **慢动作**：GlobalScale < 1 时，GlobalTimer 和所有 UnitTimer 一起变慢；UnitScale < 1 只影响该单位。
5. **时间静止**：GlobalScale = 0，GlobalTimer 和 UnitTimer 都停；UI/Cutscene 通道不受影响。

**战斗回放**：

- 记录内容：每 tick 的输入、随机种子、配置版本/哈希、起始状态；
- 回放方式：同一个 `BattleWorld` + `ReplayInputSource`，固定 tick 重跑；
- 单机 float 在同一构建/平台上可复现；跨平台/联机再换定点；
- 回放速度用 `BattleTimeChannel.Scale`，不改变 tick 长度。

**战斗 AI**：

- `AISystem` 每 N tick 思考一次（GlobalTimer 或 tick 计数器）；
- 只写 `IntentComponent`，不直接改位置/状态；
- 单位被冻结时可以继续“想”，但不能执行动作。

**物理**：

- 战斗物理放 `BattleScheduler.Physic` 的 `PreStep/Step/PostStep`，固定 tick；
- `PreStep` 缓存位置/碰撞，`Step` 解算，`PostStep` 做命中检测（文章一的做法）；
- 场景物理如果影响玩法，单独 `PhysicsTimeChannel`；纯表现物理可以走 Unity `FixedUpdate`。

## 10. 验收标准（P1）

- FrameCore 按 Order 驱动通道；
- 战斗通道 60Hz 稳定；
- 暂停只影响战斗通道；
- 单步只让战斗通道走 1 tick；
- Repeat 定时器按 60 tick 触发；
- 冻结只影响指定单位；
- 表现层用 Alpha 插值；
- 删除目录即可回退。

## 11. 风险与边界

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 核心变成上帝类 | 什么都往 FrameCore 塞 | FrameCore 只懂通道；规则进通道 |
| 通道互相依赖 | UI 读战斗时间轴 | 通道之间只走事件/命令 |
| 过早实现多通道 | UI/过场还没需求 | 只留接口，P1 不实现 |
| 单一 tick 率 | 所有通道被 60Hz 绑死 | 每个通道自己定义 tick 率 |
| 暂停语义混乱 | 全局暂停 vs 通道暂停 | 明确：全局暂停 = 所有通道 Paused |
| 系统顺序被改 | 行为悄悄变化 | 顺序集中在一处，改动需评审 |

---

## 12. 结论

1. **`FrameCore` 是全局的，但它只懂“时间与顺序”，不懂战斗/UI。**
2. **`TimeChannel` 是独立时间流；战斗只是第一个通道。**
3. **每个通道有自己的 tick、Scale、Pause、Timer，互不拖累。**
4. **文章一是战斗通道的主干；其他资料只补它没讲的部分。**
5. **全面设计接口，分步实现通道：P1 只做 FrameCore + BattleTimeChannel。**
