## 0. 可信度分层（先看这个）

| 层级 | 来源 | 能证明什么 | 不能证明什么 |

| B | CSDN 原文 | 作者经验、教程步骤、代码片段 | 完整性、正确性（大量 AI 分发） |

## 4. 交叉分析

### 4.1 五类样本，各自解决不同问题

| 类别 | 代表 | 解决什么 | 缺什么 |
| --- | --- | --- | --- |
| A. 帧数据 + 运行时帧机 | XMLib.AM、CombatDesigner | 逐帧数据、判定框、帧事件、状态切换 | 输入缓冲、连招、结算、联机 |
| B. 联机确定性框架 | Klotho、littlebee_libs、UnityLockstep、ET | tick、输入同步、快照、回滚、校验 | 动作帧数据与表现层 |
| C. 技能/动作编辑器 | actioneditor、plato、Joker、ACTSkill | 时间轴编辑、事件轨道、预览 | 运行时执行器与确定性 |
| D. 完整动作游戏 | Darklings、3DActGame、ActionGameTips | 可跑的整体闭环 | 通用性、可维护性 |
| E. 帧计时基础设施 | UniTask、UniRx、R3、各类 Timer | 帧等待、调度、取消 | 战斗语义 |

**没有一个样本同时覆盖 A+B+C+D。** 这说明“帧驱动”不是单一框架，而是四层拼装：

```
帧源/调度（E）
  → 帧数据与状态机（A）
    → 输入/连招/窗口（D 里的手感层）
      → 联机确定性（B）
```

### 4.2 可读源码里反复出现的共识

1. **逻辑帧是唯一权威时钟**：`ActionMachine.LogicUpdate`、Klotho 的 Verified/Predicted 双链、LittleBee 的 tick 校准，都是“先推进逻辑帧，再让表现层采样”。
2. **帧数据必须数据化**：`StateConfig → FrameConfig[]`，每帧挂 `attackRanges/bodyRanges` 和事件；而不是把判定写进 Animator 事件。
3. **动作执行按“帧号 + Enter/Update/Exit”**：`IActionHandler` / `IHoldFrames` 的 begin/end frame，天然表达前摇、判定、后摇。
4. **逻辑与表现解耦**：逻辑只输出动画名和归一化时间（`GetAnimName` / `animStartTime`），View 层用 `Animator.Play(name, layer, t)` 驱动。
5. **顿帧作用在帧推进器上**：`waitFrameCnt` 让整条逻辑暂停，而不是让每个系统自己扣 deltaTime。
6. **确定性靠定点数 + 稳定排序 + 无浮点**：Klotho 的 FP64、FixedMathSharp、UnityLockstep 的 BEPU 定点版都是这个思路。
7. **输入缓冲与取消窗口是手感核心**：但开源框架普遍缺失，需要自研（知乎第 38 条、CSDN 多篇都在讨论这点）。

### 4.3 三个明显的空白

- **“帧数据 schema + 编辑器 + 运行时 + 输入/连招”没有一条龙开源实现。** XMLib 有前三者，后两者要自己补。
- **动作游戏的帧同步资料远少于 MOBA/RTS。** 知乎/CSDN 的帧同步文章大多以 MOBA 为背景，hitbox/取消窗口在联机下的确定性讨论很少。
- **定量参数稀缺。** 前摇几帧、缓冲几毫秒、顿帧几帧，公开文章几乎不给可复用的数值区间。

## 5. 选型建议（结合 TEngine / HybridCLR / Luban / UniTask）

### 5.1 如果只做单机动作帧驱动

**推荐：XMLib.AM 的内核 + 自研输入/连招/结算。**

- 可搬：`MachineConfig / StateConfig / FrameConfig / RangeConfig`、`ActionMachine` 的执行顺序、帧级 Hitbox 编辑器。
- 自研：输入缓冲、取消窗口、连招图、伤害结算、TEngine 模块宿主、Luban 配置管线、Animator 绑定。
- 备选参考：CombatDesigner（同为帧驱动可视化，MIT，87★）。
- 不要直接依赖：EliteBAM（WIP/无许可）、OpenYourEye/FrameSync（demo 级）。

### 5.2 如果要做联机帧同步

**推荐：Klotho（Apache-2.0，Unity 2022.3+，FP64，rollback，文档齐全）。**

- 优点：引擎无关纯 C# 核心、Unity/Godot 适配、P2P/服务器权威两种模式、回放/校验工具、示例 Brawler。
- 成本：需要把战斗逻辑改造成确定性 ECS；与 TEngine 的模块体系要重新分层。
- 备选：littlebee_libs（MIT，轻量，但文档少）；UnityLockstep 已归档，仅作阅读。
- 不推荐：LittleBee 主仓（无 LICENSE）、ET（自定义许可 + 体量大）。

### 5.3 工具链

- 编辑器交互参考 `actioneditor`（GPL，不能商用）、`plato`、`Joker_Unity_SkillEditor`、`ACTSkill`。
- 若只要“看懂别人怎么做”，Ikemen-GO 的 Statedef/AIR/Clsn 是比任何 Unity 教程都硬的帧数据教材。

## 6. 结论

1. “帧驱动”在开源世界被拆成了四层，**没有任何一个仓库能整包搬**；能搬的是 XMLib.AM 这一层的“帧数据 + 执行器”。
2. 高星项目集中在联机确定性（Klotho/LittleBee/UnityLockstep/ET），说明**确定性是行业硬需求**；但单机动作帧数据反而缺少成熟开源。
3. CSDN 与知乎的“资料量”远大于“信息量”：CSDN 大量 AI 分发，知乎正文不可读。**真正的实现依据只能来自源码。**
4. 对本项目：先定“帧数据 schema + 窗口语义 + 表现层契约”，再决定是否 vendor XMLib.AM；联机需求出现时再评估 Klotho，不要两套 ECS 混用。
