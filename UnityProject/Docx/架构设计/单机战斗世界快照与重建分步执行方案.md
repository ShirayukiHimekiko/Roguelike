# 单机战斗世界快照与重建分步执行方案

沿用[单机战斗框架与 ET10 源码完整对比](./单机战斗框架与ET10源码完整对比.md)第 5 节的第一项。基线为 ET master 的 `743c635`。[LSWorld](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lsentity/Scripts/Core/Share/LSWorld.cs)持有世界帧、ID 分配器与随机状态，[LSUpdater](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lsentity/Scripts/Core/Share/LSUpdater.cs)按稳定 ID 调度，[JumpReplay](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lockstep/Scripts/Hotfix/Client/LSClientHelper.cs#L92)从检查点替换世界。本项目以 Entitas Context 实现这些义务，房间仍用同一个 Tick 演算实时与回放。

- [x] **世界实体和固定输入槽分离。** Context 创建时分配局内递增 ID，销毁时解除映射，保存分配器计数。开局玩家实体按名单顺序占用最初的 ID，销毁后该玩家槽仍保留历史输入但无接收实体。提供按世界 ID 查找和按 ID 排序的 Group 拷贝；系统需要稳定顺序时显式使用。伪代码：`OnEntityCreated → ++id → register；OnEntityWillBeDestroyed → unregister`。已落在 `BattleWorld`，不改 Jenny 生成物。
- [x] **保存全部确定性组件和随机状态。** 按稳定 ID 写实体，用固定的录像键注册哪些 Entitas 组件写入、如何按字段恢复，既有四个组件内置。未知组件禁止无声遗漏。确定性组件仅保存值和稳定 ID；逻辑外的实体、Unity 对象、派生索引和订阅留在各自宿主。随机数使用[上游同算法](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.truesync/Scripts/Core/Share/TSRandom.cs)的单种子整数序列，种子随开局数据，序列状态随快照。伪代码：`write(frame, lastId, randomState); foreach id: write(id, registeredComponents)`。已接入 `BattleSnapshotComponents` 和 `Module/Utility/DeterministicRandom`，空局不用随机数时不写入 MT19937 数组。
- [x] **恢复新 Entitas 世界和系统树。** 房间沿用长寿命的系统工厂与组件注册表；结束旧世界、按快照恢复新 Context、挂载新系统，再从检查点的下一待演算帧继续。不使用初始单位重建快照中的实体。系统初始化只重建派生索引与订阅；跨帧影响演算的状态必须进入确定性组件，不能只留在系统私有字段或 Collector 队列。伪代码：`releaseOld(); world = restore(checkpoint); bindSystems(world); authority = checkpoint.Frame - 1; replayThrough(target)`。已由 `BattleRoom.SeekReplay` 调用同一套 `CreateWorld` 和 `ReplayTick`。
- [x] **升级变长检查点的本地录像文件。** V2 增加随机种子和独立检查点长度，外部文件入口校验边界、校验和及帧号与记录对应关系。V1 的快照结构和每帧指纹不同，保留原文件；菜单读取新的 V2 文件，退出新战斗后即可生成。伪代码：`readHeaderAndFrames(); for each checkpoint: readLengthThenBytes(); verifyFrameHash()`。代码已接入 `battle-last-v2.replay`。
- [x] **用独立 Demo 验收连续演算与重建。** 控制两个以上临时实体的生成、销毁、带空洞的 ID、稳定的访问顺序及随机状态。要求第 0、1,200 帧等检查点恢复和多次向前、向后定位后，后续帧 hash、实体出现顺序和最终状态与连续演算一致。已验证旧系统退出、新系统只绑定新 Context。临时玩法及两组验收入口都在 `Tools/BattleFrameworkDemo`，可以整目录删除。

范围为单机战斗框架。网络、自动结算、终局指纹、Player 构建以及全部定点运算的上游逐值对照另行处理。

## 后续接入约定

- 用 `StartBattle` 和 `StartReplay` 的同一个工厂接入系统，工厂入参是新建的 `BattleWorld`。通过 `world.Context` 查询及创建实体；跨恢复边界传世界 ID，重演后重新解析实体。房间、定点时钟、输入封存与 FSM 的推进职责保持原样。
- 使用 `registerSnapshotComponents` 在开局登记 Battle Context 新组件。这一步只定义持久数据，录像键不使用 Jenny 索引。录制和回放必须使用一致的键、字段顺序及系统规则。需要绑定表现时，应使用世界重建后的 ID 和值，不把 Unity 引用写入快照。
- Entitas 仍按系统注册顺序执行。对实体访问顺序敏感的系统用 `GetEntitiesInOrder`。单个查询冻结当次批处理列表；若系统会在批处理中删除后续实体，应先保存 ID，再以 `TryGetEntity` 查当前存活项。跨系统的生成与消费由业务定义阶段。
- V2 文件边界和检查点关联在读取时验证，快照中每种组件由对应的登记方法读取。V1 不会被新版覆盖，也不在新版菜单回放。
