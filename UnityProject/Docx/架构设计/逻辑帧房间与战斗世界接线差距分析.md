## 1. 当前只接到了固定帧回调

当前调用链是 `FsmModule.Update → RunBattleState.OnUpdate → BattleUpdater.Update → ExecuteTick(frame)`。开战时房间创建时钟和更新器。更新器检查下一帧是否到期，写入 `CurrentFrame`，再同步调用外部传入的 `Action<int>`。如果回调只打印帧号，系统就只会打印帧号。战斗状态、当帧输入和房间内的战斗演算尚未进入这条链路。[开战入口](../../Assets/GameScripts/HotFix/GameLogic/Module/BattleModule/BattleModule.cs) · [战斗房间](../../Assets/GameScripts/HotFix/GameLogic/Module/BattleModule/BattleRoom.cs) · [状态轮询](../../Assets/GameScripts/HotFix/GameLogic/Module/BattleModule/State/RunBattleState.cs) · [当前步进器](../../Assets/GameScripts/HotFix/GameLogic/Module/BattleModule/BattleUpdater.cs)

## 2. 对齐帧号、快照和执行顺序

### 帧号的归属

- 上游新房间的 `AuthorityFrame` 和 `PredictionFrame` 初始化为 `-1`，`LSWorld.Frame` 为 `0`。世界的 `Frame` 是**下一次要执行的帧**。执行完第 0 帧后，权威游标为 `0`，世界下一帧是 `1`。
- 本地权威阶段由 `BattleRoom` 持有这一份权威帧号。现有公开 `CurrentFrame` 可映射到它。将来接本地预测时，再引入客户端的预测和确认游标。世界只负责已经从输入推进到了什么状态，维持自己的下一帧编号。
- 上游客户端在递增前判断 `PredictionFrame - AuthorityFrame > 5`。当前差值恰好为 5 时还会执行一帧，因此递增后可能领先 **6 帧**。循环在一次执行并发送输入之后检查约 5 ms 的轮询耗时。若后续选择严格最多领先 5 帧，这一边界与上游固定提交存在可测差异，应单独决定。[Room 初始化][room] · [客户端步进][prediction]

### 一帧的关键顺序

1. 权威推进器计算候选帧的到期时刻。到期后取得这一帧的输入，缺项沿用上一帧，找不到上一帧输入的玩家使用默认输入。然后提交 `AuthorityFrame`。单机输入直接来自本地，松键时主动写零输入。[权威帧输入补齐][authority]
2. `BattleRoom.Tick(frame, inputs)` 将已确定的输入按玩家 ID 写到当局实体。上游快照取在**写完本帧输入、还未执行本帧演算**时，hash 也是该快照序列化字节的 hash。录像只记录已确认输入，帧历史的短期快照和录像的周期快照承担不同用途。[Room 执行与存档][room]
3. `BattleWorld.Tick()` 执行当局 Entitas 系统并清理本帧，然后令世界帧加一。Entitas 要显式固定系统注册顺序；同系统内会影响结果的遍历，用稳定逻辑 ID 定序。迁移 ET 示例时先查清真正参与更新的注册 ID 与玩家 ID 的对应，避免假定这两类 ID 相同。[上游实体调度][world-updater] · [Entitas 生命周期](../../.agents/skills/entitas-dev/references/systems-and-lifecycle.md)

例如开战后执行第 `0` 帧，保存的快照携带第 `0` 帧的输入和演算前状态。世界执行完后，`World.Frame = 1`。要重演第 `0` 帧，应先恢复该快照、覆盖所需输入，再执行第 `0` 帧。项目使用 Entitas 状态快照时，应保存重演所需的 ID、定点原始值、帧号，以及实际启用的随机数与 ID 分配状态。同项目两端对账使用同一种稳定编码和 hash；上游 MemoryPack 序列化字节和跨框架的 hash 对等另行核对。[Room 快照][room] · [LSWorld 字段][world] · [回滚重演][rollback]

## 3. 建议接线

你描述的 `FrameRoom` 职责可以直接落到现有 `BattleRoom`。当局只需要一个房间对象。现有 `BattleUpdater` 演进为本地权威推进器，职责对应 `FrameRunnerServer`。以后有真实客户端预测再引入对应的客户端推进器，两者按各自的时钟与帧号调度，调用同一个房间入口。[当前房间](../../Assets/GameScripts/HotFix/GameLogic/Module/BattleModule/BattleRoom.cs) · [服务端步进][authority] · [客户端步进][prediction]

~~~text
单机
    TEngine FSM 的战斗进行状态
        → 权威推进器检查到期
        → 从本地收集并确定当帧输入
        → BattleRoom.Tick(frame, inputs)
        → BattleWorld.Tick()

未来联机
    服务端权威推进器 → 确定并广播当帧输入 → BattleRoom.Tick(frame, inputs)
    客户端预测推进器 → 合成本地预测输入   → BattleRoom.Tick(frame, inputs)
    收到权威输入有差异 → 恢复对应帧前快照 → 同一 BattleRoom.Tick 重演
~~~

权威推进器以每 50 ms 为计划间隔，在每次宿主轮询中只检查并推进一帧。宿主卡顿时次序保持，实际执行时间会晚于计划到期值。单机直接运行权威推进器即可；本地回环可以在需要模拟客户端发包、确认与回滚时接入，用来检验联机边界。未来客户端预测采用上游同类的独立追帧与时间预算，战斗世界保持同一个执行入口。[固定步长][constants] · [服务端步进][authority] · [客户端确认][confirmation] · [客户端步进][prediction]

## 4. 实施顺序与验收预期

下一次交付的文件级修改、关键伪代码与逐帧验收见[单机权威帧与战斗世界分步实现方案](单机权威帧与战斗世界分步实现方案.md)。

- [ ] **先补 `BattleWorld` 和当局 Entitas。** 房间建立自己的 Context、初始单位与系统树。引入按帧的输入值和单位 ID 映射。现有 `FixedPoint` 补齐示例移动与转向真正使用的依赖。验收以同一初始状态和输入运行若干帧，逐帧核对位置、旋转的定点原始值和世界下一帧编号。[完整迁移方案](单机战斗完整迁移执行方案.md)
- [ ] **把帧回调换成真实房间执行。** 实现 `BattleRoom.Tick(frame, inputs)`，接本地权威输入，`StartBattle` 接收开战数据。验收第 0 帧只演算一次、缺失输入按上一帧或默认值补齐、松键的显式零输入能停下、卡顿一次只补一帧，以及新旧两局世界相互独立。
- [ ] **填齐帧容器与快照。** 随权威输入接入按帧输入槽，再补同帧快照、hash 和恢复。短期环形历史和长期录像分别保存。上游的环形下标会复用，应按已保留的帧段读取，验收时覆盖槽复用、首帧、相邻帧及恢复后过一帧的结果。随后做本地录像与回放。需要快照跳转时补时钟 `Reset`，需要倍速时补沿切换帧重锚的 `ChangeInterval`。[帧容器][buffer] · [时钟][clock] · [Room 的记录顺序][room]
- [ ] **联机阶段接客户端链路。** 确认的权威帧与本地预测帧分开。客户端从最新已知权威帧继承其他玩家输入，再替换自己的当帧输入；接收权威输入时比较预测，若不同恢复该帧快照，重演到已预测位置。远端时钟调整、帧输入发送、哈希比对、快照重连都在调度和房间边界处理，使用相同的 `BattleWorld` 演算。[预测输入][prediction] · [权威确认][confirmation] · [回滚][rollback] · [校时][adjust] · [哈希对账][hash]

下一次实现的交付点是 `战斗进行状态 → 本地权威推进器 → BattleRoom.Tick → BattleWorld.Tick` 能真正消费输入并修改 Entitas 状态。预测和回滚仍列在联机阶段。所有实施项在本文中保持待完成，本文仅做源码审查。
