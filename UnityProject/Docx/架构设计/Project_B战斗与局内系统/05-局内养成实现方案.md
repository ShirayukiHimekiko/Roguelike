## 3. 状态所有权、值输入和输出

| 数据 | 唯一写入者及对外合同 |
| --- | --- |
| 双方 `LevelState(OwnerId, Level, XpInLevel, Revision)`、达成发放记账 | `RunSession` 的成长所有者。`PrepareXpGrant(GrantId, OwnerId, Source, Amount) → LevelChangePlan(LevelDelta, AcceptedXp, Overflow, LevelRewards)`。`GrantId` 由结算因果身份构成，例如 `(RoundNo, OwnerId, BaseRoundXp)`，一个值结果逐级列明解锁、费用增量、入背包的塔、三选一机会。编排持有窗队列和回合流程。 |
| `ShopWindow` 的商店数据、12 `ShopSlot`、`Offer`、锁定和随机计数 | 成长唯一写入。编排给唯一 `WindowId` 和有序窗命令。`Offer(OfferId, SlotKey{Side,Index}, ItemRuleId, ProductValue, Spend, Payout, Lock, State)` 是一次报价值，价格与星级在报价时冻结。窗级 `Revision` 由编排的共同协议发放；同一格刷新生成不同 `OfferId`。`PrepareRefresh` 接收纯值 `OpenShopInput(RoundNo, Levels, UnlockSnapshot, EligibleTargetsSummary, RefreshKind)`；附随机和报价状态更新。`PrepareConsumeOffer` 接收 `WindowId, Revision, RunCommandSequence, OfferId` 及指定目标 ID，返回冻结报价消费计划和交易意图。背包目标实时资格由编排在准备交易时再验证。 |
| 已处理的掉落来源与可领取奖励票据 | 成长提案持 `OrbGrant(DropId, Quality, Status, RewardOption)` 和独立随机状态。`PrepareOrbDrops` 输入本 Tick 已提交的破塔事实与已确认的击败层事实，按 `(BattleId, Tick, DestructionId)` 或 `(RunId, Layer, Cleared)` 去重。`PrepareClaimOrb(DropId)` 返回按奖励表选定的可兑现意图。编排用卡牌、背包、资源或双向选择接收者准备并提交，成功才标记已领取。提案在掉落时固定品质及奖励候选，领取拒绝、重开界面或离线展示不改变结果。 |

双向购买、拆除和三选一由双向选择文档定义具体的 `TransactionIntent`，成长只负责报价消费及升级触发结果。背包界面、商店和法球展示从编排的 DTO 读模型获取，既不读模块 Context，也不写状态。修正锁定、刷新、报价指定目标都带窗身份与命令序。闭窗清理报价及本窗锁，软计数和硬保底保留于本局；跨层的敌人成长新建或继承由敌人归属配置驱动。

## 4. 经验、商店与法球算法

```text
PrepareXpGrant(value, state)
    若 GrantId 已受理，则回送原结果
    把本级经验和本次经验并入事务的成长工作视图
    while 未到封顶且当前经验 >= 本级所需经验:
        扣本级所需经验；Level 加 1；按升级后等级生成回报
    处理封顶后溢出；逐级编码回报来源键
    编排预备发塔、效果、海克斯机会或买经验支出
    全部可提交才提交；按等级和配置回报 ID 稳定交付

PrepareRefresh(input, oldShop)
    保留有资格且锁定的己方未购报价
    按 (Side, SlotIndex) 建待抽格候选，筛本回合、阵营、固定格、解锁与发布约束
    用仍未买且存在合法目标的保留报价判断现有拆除资格
    若到硬保底且没有可用拆除报价，在合法待抽格预留一个拆除报价
    对各待抽格在交易工作视图中完成带版本 RNG 的整数加权抽取
    对卡牌商品依据当前玩家等级和该格仍有合法商品的星级权重抽取
    把空候选显式记录为空格
    更新软计数和保底事件，生成报价身份、修订及随机补丁
    编排预备付费刷新支出或入店事件，全部可提交才写入结果

PrepareClaimOrb(DropId)
    检查资格与未领取状态，取固定法球奖励意图
    编排预备完整收货方；分配或容量失败保留票据
    同事务提交奖励和已领取标记，于收尾发布结果
```

`ShopOfferRule` 候选在各格按 `OfferRuleId` 稳定排序。提案正常抽取允许重复。先按商品行抽；卡牌候选行要求至少一个有效星级，抽中后用当前玩家等级的可用星级相对权重取值。若策划要让所有可售卡牌共享全局星级分布，应使用按格先选“商品类/星级”、再按模板加权的规则，并记录示例分布。软权重 `BaseWeight + StepWeight × MissCount` 使用有上限的整数，单次刷新内所有候选用同一计数快照。实际抽出时清零，符合资格但本次未中时只加一次；设置窗口内所有合法格均被锁时不累计。保底选择涉及固定格限制，保持“可拆且有合法目标”和“仅显示一个拆除选项”的区别。若配置永远无合法格，装载规则失败；若当前无合法拆除目标，报告保底待兑现并保留欠账。保底是否要求有目标、缺目标是否仍视作达成由策划确认。

参照软/硬计数边界示例，设每 3 个有效进店回合必有一次可拆报价。前 2 回合均合格且未命中，第 3 回合入店在合格格挑一个拆除报价。第 2 回合付费刷新若抽得可拆报价，保底从当回合清零。当天后续刷新可以使报价消失，若策划要求“该回合保证可买到”，保底报价须保留至购买或闭店，现阶段保留为设计确认项。重复入店事件去重，付费失败不改变计数、随机状态、报价 ID、余额或界面版本。

| 失败与边界 | 处理 |
| --- | --- |
| 多级经验一次跨过多个里程碑 | 所有跨过的等级按升序发出，三选一机会有独立来源 ID 并按窗序处理。满级买经验无有效成长时提案先拒绝扣款。 |
| 同回合“按等级发塔”与“回合表发塔”命中同种塔 | 保留各来源 ID，编排按配置叠加或互斥。允许同时发放时生成两个持有实例；回合奖励在新塔第一次部署之前写入。 |
| 刷新后旧格点击、同一报价连点、无余额、买方无容量、敌方拆除候选已失效 | 凭窗/修订和 `OfferId` 跨域准备。发现同请求已经处理则返回原结果，真实拒绝时仍保留报价和锁定。 |
| 候选权重总和 0、无合法格、重复来源的法球领取 | 普通无商品的格正常为空，或所有合法候选权重均为 0 时记录空格并不取 RNG；保底仅从当前具备供给资格的候选中选择。必需配置无法满足在规则定稿阶段提示具体行。法球同实例幂等，迟到的旧世界通知凭身份丢弃。 |

## 5. 帧驱动与 Entitas 1.14.1

对接 [项目现行帧方案](../Project_B-帧驱动框架设计方案.md) 的每回合 `BattleWorld`。公共阶段为入帧 → 指令提交 → 效果与属性 → 行动与命中 → 结算 → 收尾。`BattleTick` 仅在攻击期推进，`BattleCommand(BattleId, TargetTick, InputSequence, Payload)` 在对应步消费。成长按提交后的结算事实和准备/商店有序事件工作。举例，行动与命中生成合法破塔结果，结算派生可掉落事实，编排让成长准备票据，再在 `BattleTickBatch` 输出确定的结果；回合经验在结算一次性提交，商店从其结果读取升级后的概率。向塔域的下一轮格位容量和等级值通过开战/部署快照传递。

成长使用 `RunSession` 内的纯值运行状态，以适配 Entitas 1.14.1 的编排和结算系统。若需 ECS 记录，使用正式 Context 的生成组件接口，以独立结果批次保留逐笔身份。成长只消费编排传入的破塔、清层或回合结果，不直接读取战斗 Context。现有插件可复用，正式手写组件和生成物从新业务路径开始，Jenny 的目标 Context、输入程序集与输出路径先挂到新正式程序集，项目 Demo 已从当前工作树移除。Luban 在本局创建前编译不可变值快照，冻结算法、源配置版本以及整数比率的舍入；报价、掉落、牌组洗牌使用独立注册随机流。TEngine `GameEvent` 用于发布已提交的视图变化，资产异步完成只变表现。[Entitas 1.14.1](https://github.com/sschmid/Entitas/releases/tag/1.14.1)

跨域 `Prepare` 仅读权威状态，同所有者多项变动在事务工作视图累积，成功后编排同步 `Commit` 全组写入，再发布结果。提交区间禁止 UI 回调和可恢复异常。复盘摘要包含两方等级、经验、已发来源、报价锁、保底、未领票据与已消耗的随机流位置。故障发生在准备时，放弃当前计划即可重新受理，未知是否提交先按命令或来源身份查询结果。

## 6. 分步实施与验收

- [ ] 表编译和成长状态。目标是用一份不可变表驱动等级和商店，校验 `Threshold > 0`、整数权重范围、等级引用、合法格掩码和商品窗。伪代码 `Snapshot = CompileAndValidate(Tables, RunModifiers)`。验收配置出错指出具体行键，重复开局同表和种子产生同输入状态。
- [ ] 经验、升级及经济入口。目标是一次发放、支持多级与购买一致交易。伪代码见 `PrepareXpGrant`。验收过多阈值逐级发放，评分额外经验根据指定接收方，买经验无余额无变化；重试同结算不重复增加。
- [ ] 商店双侧报价及锁定刷新。目标是保留己方购买前锁定，守住身份与格位限制。伪代码见 `PrepareRefresh`。验收 6+6、符合固定 3/4/5 格、初级例子仅 1 星、金不足不刷新、锁定项目和冻结价格可保留。
- [ ] 软权重和硬保底。目标是同时兑现概率增长和回合次数上限。伪代码 `UpdateSoftOnce(Eligible, Seen); ReserveDueRemoval(AvailableTargets, SideSlots)`。验收初始、未命中累加、任一格出现清零、最后一期临界保底、无合法目标延期、失败刷新不推进。
- [ ] 报价确认、交易路由及等级海克斯机会。目标是报价只有成功交易才可消费。伪代码 `PrepareConsumeOffer -> coordinator.PrepareDelivery/Spend -> CommitAll`。验收新旧报价错位不扣费，自购或喂养接受正确归属；超过两个里程碑或同回合清层产生分开的可追溯机会。三选一双方的实际应用依双向选择方案。
- [ ] 破塔至法球领取、跨层及离局收尾。目标是塔掉落与击败层奖励可分别追溯。伪代码 `PrepareOrbDrops(CommittedFacts); ClaimOnce(DropId)`。验收核心和抵抗塔不进入单塔掉落，合法击败层独立生成层奖励；普通塔按星级候选集，重复领取不重抽，非法容量交付保留领取权，跨层全局回合累加。

本稿的等级曲线、完整商品/奖励表、保底资格与法球边界需策划确认后用于正式验收。
