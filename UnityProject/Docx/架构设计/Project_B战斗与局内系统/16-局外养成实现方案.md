## 3. 模块、数据与节点提交

`GameManager` 编排启动、大厅、选难度、创建和离开整局。独立 `Profile` 模块拥有玩家档案、局外钱包、点亮记录、内容解锁、禁用设置和结算收据。`RunSession` 独占本局记录和统计，`BattleModule` 管具体战斗，结束时由 `RunSession` 汇总成冻结的局末结果。开局由 `GameManager` 向局外取值并编译 `RunSetup`，结束由它向局外交付 `RunOutcome`。局外和局内通过这两个值交接。 [GameManager 与游戏生命周期](14-GameManager与游戏生命周期实现方案.md) · [模块分类与战斗组装](15-模块分类与战斗组装方案.md) · [局内资源](09-资源系统实现方案.md)

现有 `GameApp.Entrance` 调用尚为空的 `StartGameLogic`，`GameModule` 当前暴露资源、UI、场景等框架入口。提案从 `StartGameLogic` 装配 `GameManager`、`Profile` 服务和存储适配器，服务放在热更业务层。框架能力走 `GameModule.XXX`。Profile 写操作通过等待结果的 `UniTask` 端口串行提交，成功后发布 `GameEvent` 刷新视图，`UIWindow` 使用 `AddUIEvent` 订阅。持久数据使用普通值 DTO，档案内保存稳定 ID 与版本。 [GameApp.cs](../../../Assets/GameScripts/HotFix/GameLogic/GameApp.cs) · [GameModule.cs](../../../Assets/GameScripts/HotFix/GameLogic/GameModule.cs)

| 数据 | 内容及所有权 |
| --- | --- |
| `ProfileState` | `ProfileId, SchemaVersion, Revision`，A/B 非负整数余额、按树归属的激活节点集合、已解锁内容 ID、三类禁用集合、必要的待处理局末结算和收据。首期只从配置定位默认角色。禁止在 Profile 中存放战斗组件、Entitas 实体引用、局内金币/经验/荣誉或已经生成的卡实例。 |
| `ProfileLoadout` | `ProfileId, ProfileRevision, ConfigVersion`，默认角色 ID、由节点推导的星级/能力许可、解锁集合、禁用集合、规范化的开局效果。每局从最近一次已提交的 Profile 导出。 |
| 局外配置 | Luban 科技节点、卡牌树和节点、内容解锁条件、禁用基础值与增量、奖励规则版本和参数。角色表继续提供初始角色、初始卡组、资源和技能。适配层在配置可用后编译只读索引，生成文件由 Luban 工程维护。 |
| 派生值 | `剩余禁用配额 = 基础配额 + 已生效节点增量 − 已占用数`，按分类独立计算。星级上限、能力可用性、科技效果、有效配额由节点推导。永久持久数据保留事实来源，避免余额、配额和效果的冗余表示漂移。 |

配置导入校验节点 ID 唯一、所属树明确、前置存在且同属本树、无环、卡牌树恰一个根、科技允许多根、冲突无自指及悬空、合法资源和非负整数成本、效果目标与参数域有效。`层` 是显示/编排字段，前置是激活依据。卡牌冲突首期限定本树，规则编译后双向判定。若节点与其必需祖先互斥，导入即报不可达。效果按稳定节点 ID 和明确的效果规则编译，只允许配置认可的内容解锁、禁用配额、效果修正、星级上限或星级能力，缺叠加规则的同目标数值拒绝发布。角色树现有表主要描述技能战斗参数，未来仍需定义节点前置、冲突、成本与对应技能效果。 [卡牌实现](01-卡牌实现方案.md) · [Luban 规范](../../../.agents/skills/tengine-dev/references/luban-config.md)

档案字段迁移由 `SchemaVersion` 驱动。内容 ID 的改名、移除或前置关系变化使用显式映射或迁移决策，避免已点亮节点被错误套到新增内容。首期保留原档，遇到无法解析且影响开局的节点效果返回具体 ID 供修复。退款与重置另待策划定义。

```text
ActivateNode(ProfileId, ExpectedRevision, NodeId):
    在 Profile 串行写入器中取最新已持久状态与当前配置
    校验大厅写权限和 Revision，再校验节点、树归属、内容开放资格
    检查尚未点亮、前置均满足、没有已激活冲突、A 或 B 余额足额
    生成候选档案，扣全额并记节点
    若明确的配置首次解锁新卡，同次增加解锁事实与该次 B 奖励
    校验候选档案，异步持久提交，然后发布钱包和节点新快照
```

激活的可支付性以扣款前余额判定。本次点亮所触发的 B 奖励应在扣款之后计算。重复请求命中已激活状态或旧版本，返回当前快照，余额只扣一次。UI 的节点状态、价格和余额都是投影，局外服务根据当前表和档案重新判定。战斗开始锁定本局快照，终局持久完成后再开放大厅写入。解绑窗口只取消等待展示，已经进入持久提交的事务继续由档案服务跟踪到终态。

## 4. 禁用、卡牌星级及开局装配

策划同时规定「禁用后不在作战里出现」和「开局牌组等于角色初始卡组」（L47、L191），固定任务或海克斯也可直接给指定卡（L57–63）。首期提案以所有获得途径共享准入规则作为默认，策划需确认初始牌和必给内容的保护范围，以及固定奖励的合法替代。现阶段用配置把待判内容验证成显式错误，避免临时改写奖励、用重复海克斯凑足三项，或静默让禁用项进局。

| 来源与边界 | 首期提案 |
| --- | --- |
| 禁用目标及合法性 | 卡牌按卡定义 ID 禁用，对其所有星级和双方适用。物品、海克斯按各自定义 ID 禁用。塔、BUFF 等有独立定义，禁止仅按数值相同的 ID 跨类型过滤。页签提交单项增删，候选禁用集合满足三类配额后，还要通过至少默认角色及当前所选难度的开局预检。切换难度后重新校验。一个本来就不合法的旧设置允许取消禁用进行恢复。 |
| 固定初始卡组与其他必需内容 | 首期配置为必须完整保留的初始卡标为不可禁用，用于兑现开局牌组等于角色模板的规则。若旧档在新配置中禁用了该卡，返回涉及角色、卡组和卡的 ID，玩家可解除；若初始牌缺定义、星级许可或必需内容保护，提示配置错误。可抽牌数量、最低可用牌组条件由策划确认。 |
| 随机出现与确定授予 | 商店、法球、随机赠送、随机洗练在抽样前过滤，候选按确定顺序进入局内 RNG。任务、海克斯效果、羁绊临时牌、固定商店等指定发放复用同一准入。必给来源的配置应显式声明合法替代或保证目标受保护，缺任何可发放内容时返回内容错误并保留仍可保留的机会。选项副作用随交易和效果准备检查，失败整笔拒绝。装备等物品子类是否受禁用需要由策划明确并由配置归类。 |
| 双方海克斯配对 | `PairDef` 在其配置的回合窗内、配对权重大于零，并且玩家侧和敌人侧均通过解锁、禁用和目标规则时才可抽。至少三个不同配对 ID 可无放回抽取。常规不足时检查配置声明的兜底，兜底同样过滤、去重。开局预检使用固定难度/回合/已知目标约束核可达的必发窗口，结算或等级触发当下再按实时资格验一次。动态条件使运行中可用配对不足时，返回内容错误并保留票据，等待内容修正。 [双向选择实现](10-双向选择系统实现方案.md) |
| 星级与能力 | 基础卡先取得可用星级及默认能力。节点可提升该卡上限，或为某个已允许星级增加能力权限；能力需实例当前有效星级满足才生效。商店报价、初始模板、永久或临时升级、指定授予共用本局许可。正式配置须明确可达星级路径和初始上限。临时越级首期同样校验，上限例外须另行确认。 |

`SetBan(ProfileId, ExpectedRevision, Kind, DefId, IsBanned)` 通过与激活节点相同的提交路径。解禁释放对应占用，配置或旧档导致的超额与冲突可以逐项修复。新增禁用需先演算候选快照，用独立的开局规则校验逻辑检查固定内容和已知必发候选池，再持久化。该校验同时供 `CompileRunSetup` 使用。固定配置如果随新版本变成无法进入一局，进入大厅后显示可定位原因并提供解禁路径。配置导入时还应使用默认无禁用档验证基础池可用，排除发布内容自身无解的情况。

```text
GameManager.StartRun(DifficultyId):
    停止接收大厅写入，等待已接受的 Profile 命令提交
    catalog = 从当前已发布内容取得一份不可变配置快照
    loadout = Profile.CreateLoadout(当前档案的已持久快照, catalog)
    setup = CompileRunSetup(loadout, catalog, DifficultyId, 新 RunId 和本局种子)
    校验默认角色、初始牌组、星级能力、可解析的科技修正和最低候选数量
    校验成功后交给 RunSession 创建本局，失败时回到大厅并出示具体原因
```

`RunSetup` 冻结内容和奖励规则的版本及业务值，在异步场地加载前完成。本局层布局、发牌、刷新、升级和结算使用该批只读值。卡牌域用角色模板创建本次的实例与基准星，效果域在实例获得有效星级时读取能力。商店、双向选择和成长保留各自的随机流与权威处理入口。 [局内养成](05-局内养成实现方案.md)

## 5. 局末统计、奖励与恢复

`RunSession` 在最终已提交事件后冻结 `RunOutcome(ProfileId, RunId, OutcomeDigest, RewardRulesVersion, …)`，包含结果分类、确认的击败敌人数、符合统计规则的累计破塔数、累计持续回合、可计的卡牌升级事实、累计评分以及规则需要的难度等输入。统计基于提交后的事实，破塔按唯一销毁身份、回合按唯一 `RoundId`、升星按唯一升级操作身份去重，批量升星可附事务内条目序号。A 依据固定的本局规则按贡献项和胜负额外项计算。B 使用本局可计升级的增量与胜负额外项。L274 写累计评分用于局末额外奖励，评分累加值及最终映射到哪种局外奖励由策划补齐。首次局外解锁给 B 走节点或其他解锁事务，局末只接本局所得。提案 B 首版按局内已成功的永久升星计入，例如合成成功记一次。临时升星及重复资格、断线或主动退出的奖励等级、A 的结束回合与破塔统计边界由策划确认。未确认的退局原因保持独立，避免被等同于正常战败。

每个 `RunId` 由整局入口生成且不可复用。`OutcomeDigest` 由有版本的规范序列化及稳定顺序计算，包含 Profile、Run、规则版本、终局原因和奖励输入。这个摘要用于核对同一局是否重投了不同内容。Profile 使用本局固定的奖励参数一次算出 `RewardLines`，在持久受理时与必要的冻结统计一起保存。恢复路径直接使用已持久的奖励行，热更之后也保留本局结算金额。待处理条目的键为 `(ProfileId, RunId)`，内容含 `OutcomeDigest`、`RewardRulesVersion`、`RewardLines` 和供展示的结果摘要。

```text
RegisterPendingOutcomeAsync(outcome, 本局固定的奖励规则):
    在 Profile 串行写入器中校验档案、终局身份和规范摘要
    查相同 RunId 的收据与待处理条目
    摘要相同且有收据，返回原收据
    摘要相同且已登记，返回已受理状态
    同 RunId 摘要不同，返回冲突并保持原状态
    新登记时检查待处理槽为空，校验所给奖励规则与 Outcome 版本相符
    按固定规则和已提交统计计算奖励明细并检查玩家余额的取值范围
    原子保存待处理条目并返回已受理

CommitPendingOutcomeAsync(ProfileId, RunId):
    在同一写入器中读取持久待处理条目或已完成收据
    已完成则返回原收据
    无匹配条目则返回未受理，等待原请求重投或显式恢复
    在新快照同时增加 A/B、写入带摘要的收据、移除待处理条目
    异步持久提交成功后发布档案快照和结算结果
```

首期有一个待处理槽，`GameManager` 等待该局持久结算完成再接新局。若另一个 `RunId` 到达，先处理已登记条目，避免覆盖。档案初始化先读取、迁移再重投待处理条目。首个持久点之前的结果只由当前 `GameManager` 暂留并可重试，强杀恢复要求另有本局持久化机制。首个持久点之后，程序可从已受理条目接续；最终提交后响应丢失，从收据取回结果，避免重复加款。胜败界面可先显示已冻结的战斗结果，奖励到帐以持久收据为准。收据按 Profile 保留，每局仅最小摘要和金额。未来若有清理需求，应定义能拒绝旧结果重投的水位或索引协议，再做压缩。

档案存储提案为每个本地 Profile 一个文件提交边界。`ProfileStore` 在目标平台持久目录异步读写，序列化采用明确字段和值类型。适配器写同目录临时文件，在目标平台做文件刷新和已验证的原子替换，提交完成后发布。保存头含 schema、单调递增版本和完整性摘要。读入校验版本、摘要、必填字段与 ID。首次启动确认没有存档时可建默认档。读失败、档案损坏和不支持的版本进入显式恢复状态并冻结写入。回退到上一有效备份属于时间点恢复，可能同时失去较新余额、收据和待结算记录。应显示回退版本并保留原文件，经显式恢复后重新核对该范围的结算事实。异常回退期间暂停自动补发，对账依据缺失时记录未能恢复。替换调用报错且提交结果不明确时，回读持久值核对版本、档案摘要及收据，判明终态再重试，避免旧内存覆盖已成功的新版本。目标平台若无法提供所需文件提交语义，由 `ProfileStore` 选用具备等价事务保证的平台实现，验收覆盖进程中断。首期假定单进程单 Profile 写入，多开或多设备同步需另行确定存储和冲突策略。

## 6. 分步实施与验收

以下实施及验证待用户确认后开展。标记保持待办。

- [ ] **建立 Profile 与配置适配。** 为 A/B 钱包、持久状态和派生视图建立统一边界。导入时构建树索引、查环、校验内容引用。伪代码 `LoadAsync → Migrate → CompileCatalog → GetSnapshot`。验收初始 C/D/E 为 2/2/1，科技多根、卡牌每组单根，悬空前置/冲突祖先/不存在效果在装配时定位到配置行。
- [ ] **接节点和内容解锁。** 所有点击只提交稳定节点身份、版本和命令参数，点亮、扣款和首次解锁奖励同提交。伪代码 `PlanActivation(state, node) → CommitAsync(candidate)`。验收足额点亮、缺前置、余额不足、双向互斥、同一节点连续请求、两个节点争用同一笔余额、关闭 UI 后提交完成等路径。
- [ ] **接禁用和开局快照。** 统一禁用域和星级权限，在 `CompileRunSetup` 核固定初始内容与已知选择窗口，局内发放和抽选复用准入。伪代码 `ValidateCandidateBans → CreateLoadout → CompileRunSetup`。验收三个配额分别满额、解禁归还、科技扩容、初始牌受保护、任务指定禁用卡改走合法替代、临时星级复原和下局使用新快照。配对池正常给出三项，共用同一敌方海克斯的两个配对应同时失去资格，剩两项且兜底耗尽时走明确的拒绝或挂起路径。
- [ ] **接结束结果和持久结算。** 先冻结事实和版本，登记待处理，再提交余额和收据。伪代码 `FreezeOutcome → RegisterPendingOutcomeAsync → CommitPendingOutcomeAsync → ShowReceipt`。验收正常胜负、重复同局同摘要、同局异摘要、两次持久点之前与之后进程终止、替换成功但响应丢失、配置热更后恢复、IO 失败保留可重试状态、损坏档案回退前冻结补发，以及已到账奖励重启后仍一致。
- [ ] **补齐正式内容和平台验证。** 交付配置表当前启用的科技效果、B 的计数政策与奖励数值、初始牌保护集合、所有必发来源的替代规则、难度配置和目标平台存储策略。伪代码 `ValidateCatalogForRequiredWindows → StartRun → FinishRun → ReopenProfile`。验收实际大厅点亮树和设置禁用、开局配置对实局生效、从一局胜负回到大厅再次消费 A/B。
