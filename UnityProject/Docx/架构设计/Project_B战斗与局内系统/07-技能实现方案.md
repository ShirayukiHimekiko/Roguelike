## 1. 策划事实与首个样本

以 2026-11-15 导出的修订 5989 为准。L223–230 规定技能牌可增益单位、减益敌人或直接攻击。强化卡强化玩家。单位、塔和暴露后的核心各自自动攻击，特殊塔攻击可携带效果。L284–294 规定角色有专属能量，能量跨回合和跨层累计。能量充满后，玩家在战斗中按空格释放。原案 L469、L519–529 已给出技能、效果引用关系，仍需定义目标和载荷的运行时语义。 [Project_B 原案](https://my.feishu.cn/wiki/AIEkwlgbqiha8dkcxXSc0oH9nae) · [角色主动技能](../../游戏设计/功能需求/16-角色主动技能.md) · [卡牌类型与效果](../../游戏设计/功能需求/08-卡牌类型与效果.md) · [伤害与攻击结算](../../游戏设计/功能需求/39-伤害与攻击结算.md)

## 3. 所有权及值契约

技能拥有角色能量运行状态、已授予技能的状态、技能使用实例、可选冷却和技能触发序列。卡牌拥有牌区、消耗去向和卡牌实例，资源拥有费用余额与上限。Buff 拥有其持久效果贡献。单位、建筑拥有实体资格和战斗属性。战斗编排拥有本场工作时钟、倒计时、命中和跨域路由。编排器从各域取得值快照并交付 `EffectIntent`，各域内部使用自己独立的配置和状态。 [出牌与费用](../../游戏设计/功能需求/07-出牌与费用.md) · [Entitas 1.14.1 项目规范](../../../.agents/skills/entitas-dev/SKILL.md)

| 拟议值类型 | 建模与时间边界 |
| --- | --- |
| `SkillDefinition` | `SkillDefId`、来源类别、能量阈值与消耗、目标描述、阶段时长、可选冷却、效果条目及固定排序。技能牌可引用同一效果表，以其卡牌提交身份携带载荷。 |
| `EffectDefinition` | `EffectId`、显式操作类型、目标掩码、定点数值和必要的定义引用。建议从「施加 Buff」「直接/范围攻击」「恢复费用」「回合倒计时倍率」四类起步。效果列需明确稳定序号，原案效果字典在内容预处理时转换为确定顺序。 |
| `RunSkillSeed` | `RunId`、`CharacterId`、`SkillDefId`、已提交能量、经确认可跨回合的转换余数。RunSession 按技能所有者保存值，在每场初始化时传回技能。活动实例和场内截止 Tick 随 World 清理。 |
| `SkillCastRequest` | `BattleId`、目标 Tick、输入序、来源身份、`SkillDefId`、目标描述。角色指令来自空格的单次按键边沿。卡牌使用的是已受理 `PlayCard` 内的载荷及其提交 ID，不另外伪造按键。 |
| `SkillCast` | `CastId`、来源、选定目标/地点、开始/活动截止或可选阶段截止 Tick、效果序列游标、是否已提交消耗。角色来源稳定 ID 与场内战斗实体 ID 分型。 |
| `EffectIntent` | `BattleId`、执行 Tick/阶段、根动作身份、效果序号、来源、目标描述、效果载荷。攻击另由编排分配统一 `AttackInstanceId` 及 `SegmentId`。取消与完成输出独立事实。 |
| `EnergyGainInput` | 有序费耗或命中事实。命中保留 `(BattleId, Tick, HitOrdinal)`、有效伤害、受击对象种类、来源归属和破损原因。费用保留正式出牌提交 ID 与实扣值。 |

首期在 `GameLogic` 的每场 `BattleWorld` 中维护独立技能状态。需要实体查询时在正式 `BattleContext` 使用专有组件、缓存 Group 和显式队列，配置在开战前加载冻结。Entitas `ReactiveSystem` 同实体变化会合并，只供表现或衍生读模型刷新。计费、脉冲、命中、完成和取消用带身份的逐条值事件。展示由战斗编排提交后发布，通过 TEngine 通知表现。 [帧驱动方案 §3](../Project_B-帧驱动框架设计方案.md#3-模块所有权与工程接入) · [Entitas 系统与生命周期](../../../.agents/skills/entitas-dev/references/systems-and-lifecycle.md) · [TEngine Luban 配表](../../../.agents/skills/tengine-dev/references/luban-config.md) · [TEngine 事件规范](../../../.agents/skills/tengine-dev/references/event-system.md)

## 4. 状态、提交和帧顺序

首个角色能力为 `已就绪 → 已提交且持续生效 → 已完成或已取消`。资源不足时维持积累状态。即时技能牌从提交产生有限效果序列，本期无需前摇、连段、打断或额外冷却。有实配的延时技能时增加 `准备中 → 再核资格 → 提交 → 活动中 → 恢复`。提交前的取消释放预留，提交后的退款、冷却是否保留和施法者离场后效果是否持续由对应定义确认。选目标可由值规则表达无目标、指定目标或区域。核心保护默认沿用帧方案，只有明确的技能授权能开放对应路径。玩家不能据此直接改写自动单位的索敌。 [英雄核心](../../游戏设计/功能需求/11-英雄核心.md) · [帧驱动方案 §6](../Project_B-帧驱动框架设计方案.md#6-战斗帧序与-hitresolver)

| 阶段 | 顺序与决策点 |
| --- | --- |
| 入帧 | 封存本场输入。结束已到期技能状态，撤销过期能力提供的倒计时倍率和能量锁。关闭已离场来源的资格。 |
| 指令提交 | 按输入序处理，检查战斗状态、来源、能量、冷却、目标和容量。角色请求成功时一次扣能量并登记活动技能。技能牌使用编排协调的出牌提交，同批扣费、锁定载荷并把牌标为结算中，释放手牌槽位且当步不能重复出牌或洗到这张牌。未通过预检时手牌和费用不动。 |
| 效果与属性 | 编排把 Buff 和属性意图送各所有者，聚合本步倒计时倍率。已承诺的数值随定义说明冻结时点，默认技能固定威力使用提交时的载荷，命中防御、存活和保护使用行动后的命中快照。 |
| 行动与命中 | 编排将直接攻击、范围脉冲与普攻收敛到统一 `AttackRequest → HitCandidate → HitResolver`。直接攻击仍检查阵营、目标存活与保护。同一次命中后的反击、追加攻击从下一 Tick 开始。 |
| 结算 | 写回命中、伤害和死亡事实，路由费用回复以及能量事实。后结算所得的能量/费用最快用于下一 Tick 的输入。角色在本 Tick 激活时，该 Tick 结算的塔伤和费耗也受冻结。原案 L178 的牌区转移在本次即时载荷结算后提交，命中结果可以是合法但未命中。多 Tick 卡牌的去向边界待其成为已确认需求时确定。 |
| 收尾 | 先使本场的终止状态对后续输入可见，取消活动 SkillCast、清除其本场时限和未发载荷。按已提交状态导出能量并释放 World。准备和商店窗口只收有序局流程事件，技能时钟与技能发放窗口由需求决定，主动施放只在战斗。 |

基础角色在 Tick `S` 提交技能，取 `R=TickRate`。建议活动资格 `[S, S+15R)`，倒计时和能量锁于有效步读取。恢复发生在各子区间末端 `S+R-1, S+2R-1, …, S+15R-1` 的结算，共 15 次。下一个 Tick 入帧时先结束状态，再审批新输入。战斗提前结束时只保留已结算回复和耗费，未发生脉冲随场销毁。倒计时每 Tick 使用定点速率步进，0.5 按同一固定刻度精确表示。技能直接干预倒计时速率的提案影响帧驱动方案的固定截止设定，需要把原「固定截止 Tick D」扩展成当前 `RemainingRoundTime` 耗尽的可变截止，保留截止所在步完整结算和禁止下一步输入。 [帧驱动方案 §4](../Project_B-帧驱动框架设计方案.md#4-固定步长和时间契约)

```text
提交角色技能(request, battleView)
    预检输入身份、当前阶段、所需能量、目标和输出容量
    使用当前已提交能量扣除该次成本，分配 CastId，登记截止 Tick
    记录冻结能量与倒计时倍率意图，保留待发载荷及其序号

结算角色能量(orderedFacts, currentGlobalRound)
    输入去重后，若本步有能量锁或能量已达上限，丢弃本步新增输入
    对每条合格事实按其种类累计余数，分别使用塔伤阈值或费耗阈值 DivRem
    Energy = min(MaxEnergy, Energy + EarnedEnergy)
    触顶后清理换算余数，避免满条时积攒下一次施放能量

提交技能牌(PlayCardId, cardView, feeView, targetView)
    在出牌原子组内预检卡实例/费用/目标和效果载荷
    同批记录扣款和卡牌进入结算中，提交 `FeeSpent` 和 `CardPlayed` 各一次并登记效果意图
    在结算点应用载荷结果，牌进入定义指定的弃牌区或移除区
```

能量余数建议分别记录塔伤和离散实扣费用。首期讨论口径按有效扣血累计，计算伤害与实际扣血均保留以供更改口径。换回合时按配置决定是否保留余数，新事实使用新回合阈值换算。触顶清余数与冻结期间不累积是提案，须与“持续时间内停止上涨”和技能循环策划一并确认。伤害分数与能量可选择不同字段，但均从同一 `ResolvedHit` 获得。无伤害事件的连带破损以及清场回收不增加伤害能量。

## 5. 失败、验收和实施步骤

- 过期场次、重复输入、非战斗施放、未到能量、目标当步失效等均给出可枚举失败原因。重按键由每笔输入序处理，首笔成功后的同 Tick 后续尝试读到已消费能量或运行中状态。技能牌预检拒绝时保留卡与费用，已提交后因目标在实际命中时失效则走正常未命中规则。
- 检查所有技能/效果引用、时值、来源与目标组合、数值可表示性和结束条件。原案将「触发技能」列为效果项。需要支持时先规定图引用无环，并设置内容可推导的每 Tick 上限，命中产生的新攻击继承因果键并在下一 Tick 执行。内部容量或数据不变量破坏按帧方案终止会话，不发布当步部分结果。
- [ ] **配置和入口**：从 Luban 技能及效果表加载最小定义，接空格指令与卡牌提交载荷。走 `原表 → 值契约校验 → 有序指令`，覆盖失效目标和核心保护，待确认前用标记为测试的内容。
- [ ] **能量**：用实扣费用和合法塔伤输入，按全局回合和比赛 ID 计算。走 `每条结算事实 → 去重 → DivRem → 更新/跨场交接`，覆盖冻结、触顶、重复接收和跨层阈值。
- [ ] **初始角色**：按策划确认的时间语义添加活动状态、倒计时倍率和费用脉冲。走 `提交一次 → N 个有效步 → 结束或撤销`，覆盖节奏数值、脉冲退场、首次提交和终止优先级。
- [ ] **即时技能牌与普攻链路**：编排接 `效果意图 → Buff 修正或 AttackRequest → ResolvedHit → 牌区和能量`，用一张友方增益、一张敌方减益、一张直接打塔和一类带附加效果的自动攻击校正边界。

建议后续验收以已确认参数为准。角色能量跨世界成对交接，输入重复、保护中的核心、无合法目标或资源不足均保留明确结果。相同时序和随机输入下比较技能状态、费耗、能量、伤害、牌区、倒计时和轮次出口。仍须确认「费用无法出牌且无存活单位」条件是否会被可施放技能或活动中的回费推迟，以及超时、核心破碎与恢复脉冲同 Tick 的业务优先级。 [回合准备与终止](../../游戏设计/功能需求/03-回合准备与终止.md) · [出牌与费用](../../游戏设计/功能需求/07-出牌与费用.md)
