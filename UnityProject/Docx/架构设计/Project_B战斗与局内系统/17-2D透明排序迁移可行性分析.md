# 2D 透明排序迁移可行性分析

2026-11-15 · 源码分析

本次以 EG 示例的 `1_FirstRenderUnit` 和 `2_TheDepth~` 为参照，判断普通 Unity Job System 和项目内的 Entitas 1.14.1 能分别承担哪一段，以及怎样在 Roguelike 保留按 Y 遮挡的画面。可行性按参与对象、深度计算、渲染消费三个位置判断。运行画面和性能留待后续实测。

## 示例是怎样让较低的物体盖住较高的物体

1. `1_FirstRenderUnit/FirstRenderUnit.cs:25–55` 为每个单位创建渲染实体，用 Mesh、Material 和 `LocalToWorld` 提交给 Entities Graphics，初始世界 Z 为 0。
2. `2_TheDepth~/TheDepth.cs:48–55` 添加两个标签。`CdEGTag` 是示例自己的查询条件。`DepthSorted_Tag` 交给 Entities Graphics 启用实体深度排序。
3. `2_TheDepth~/EGLib/Systems/SysEG.cs:7–37` 在 Presentation 阶段开头查询有 `CdEGTag` 和 `LocalToWorld` 的实体，调度并完成 `ZOrderJob`。该 Job 在第 15–22 行遍历匹配的矩阵，只做 `position.z = position.y` 并写回平移列 `Value.c3`。每个实例互相独立，处理量随实例数线性增长。实体和数组的排列顺序与这个计算无关。
4. `2_TheDepth~/shader_TheDepth.shader:9–23,76–81` 采用普通 Alpha 混合、`ZWrite Off`、`ZTest Always`，示例输出 Alpha 为 0.5。对应场景使用位于 Z = -10、沿 +Z 看的正交相机。在两者都可见且排序优先级相同的条件下，Y 较大的实例被写到更远的 Z，先画。Y 较小的实例后画，压在前面。同 Y 时示例没有业务级决胜规则。直接映射真实 Z 也会改变近远裁剪关系。

## 在 Roguelike 的落点

项目当前是 Unity 6000.0.69f1、URP 17.0.4。默认管线引用 2D Renderer，资产已保存 `(0, 1, 0)` 轴，`m_TransparencySortMode` 仍是 Default。锁文件已有 Burst 1.8.28、Collections 2.6.2、Mathematics 1.3.2。 [项目版本](../../../ProjectSettings/ProjectVersion.txt) · [2D Renderer](../../../Assets/Settings/Renderer2D.asset) · [锁文件](../../../Packages/packages-lock.json)

Entitas 插件仍在，工作树中的 EntitasDemo 业务代码和生成物已删除，Jenny 和残留的 Editor 示例脚本仍指向 Demo，正式 Battle Context 目前见于设计文档。接入正式系统前要确定实际 Context、程序集、Jenny 生成输出和表现宿主。 [Jenny 配置](../../../Jenny.properties) · [Editor 示例脚本](../../../Assets/Editor/EntitasDemoTest.cs) · [单位实现方案](04-单位实现方案.md)

| 迁移目标 | 可行路径 | 成本与限制 |
| --- | --- | --- |
| 复现战场角色随 Y 交叉换序 | 正式战斗表现用 `SpriteRenderer`，在 2D Renderer 资产中设 Custom Axis `(0, 1, 0)`。参与相互遮挡的单位用一致的 Sorting Layer、Order in Layer 与兼容的材质队列。将 Sprite Sort Point 设为 Pivot，脚底作为锚点。多精灵单位使用 `SortingGroup`，组根节点放在脚底。 | 渲染器根据表现位置逐帧排序。更高优先级的层和 Order 会先分组。项目共用该 Renderer 资产的场景也会受到轴设置影响。 |
| 迁移示例的逐实例计算 | 将渲染位置或矩阵放入复用的 `NativeArray`，用 `IJobParallelFor` 逐下标写深度或输出矩阵，相同输入会得到相同的 `Z = Y` 映射。渲染端用该输出做深度排序或提交。 | 主线程负责采样与提交，预留作业和渲染提交之间的时间，消费或释放缓冲前等待对应句柄。仅计算一个赋值时，搬运、调度和同步成本可能超过收益。 |
| 把表现接入 Entitas | Entitas 在主线程组织位置、显示身份和生命周期。表现消费已提交的战斗位置，按渲染帧插值并更新脚底锚点。也可由主线程表现系统直接遍历缓存 Group 或表现快照，计算并提交深度或排名。选择 Job 路径时，向 Job 传仅含值类型的数据快照，再由主线程提交结果。 | Entitas 的 Group 顺序和 Job 的执行顺序都不能直接决定透明绘制顺序。若以后需要 Burst 核心，先按现有索敌设计的分工评估主包承载 Job、热更层提交值快照，并核对目标构建。 |

[Unity 2D 排序设置](https://docs.unity3d.com/cn/6000.0/Manual/2d-renderer-sorting.html) · [Unity IJobParallelFor](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Unity.Jobs.IJobParallelFor.html) · [HybridCLR 对 Burst 的说明](https://www.hybridclr.cn/en/docs/help/faq) · [四叉树 Job System 的主包与热更边界设计](12-四叉树JobSystem索敌实现方案.md)

建议先用 `Entitas 战斗状态 → 表现插值 → SpriteRenderer / SortingGroup → URP 2D 透明排序`。若必须严格规定同 Y 谁在上，可在同一个需相互遮挡的排序域内，对全部参与者按脚底 Y 降序、稳定表现 ID 决胜，生成后画者更大的 `sortingOrder`。`sortingOrder` 优先于相机距离，单独给少数对象加 Order 会影响它们与其他 Y 的遮挡关系。生成排名时还需核对 `sortingOrder` 的有效范围。 [Renderer.sortingOrder](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Renderer-sortingOrder.html)

## 把效果搭进场景

按 XY 平面的正交俯视战场设置。先搭两单位的最小场景，正式表现接入时复用同一个排序规则。

1. 在 `Renderer2D.asset` 的 Inspector 把 **Transparency Sort Mode** 设为 **Custom Axis**，Axis 取 **(0, 1, 0)**。使用这份 Renderer 资产的相机都会采用这个设置。 [Unity 2D Renderer 排序设置](https://docs.unity3d.com/cn/6000.0/Manual/2d-renderer-sorting.html)
2. 用独立场景放一台正交相机，位置 `(0, 0, -10)`，旋转 `(0, 0, 0)`，Renderer 使用默认的 2D Renderer。项目的 `main.unity` 主相机当前为透视，示例场景使用自己的正交相机。 [main.unity](../../../Assets/Scenes/main.unity)
3. 创建两个不同颜色、约 1×1 世界单位的精灵，两者同用 `Default` Sorting Layer、`Order in Layer = 0` 和同一透明材质。精灵在 Sprite Editor 中把 Pivot 放在脚底，Sprite Renderer 的 **Sprite Sort Point** 选 **Pivot**。多部件单位改用脚底的根节点挂 `SortingGroup`，在组内给身体、武器等设置各自的顺序。需要观察混色时可把两个精灵的颜色 Alpha 都设为 0.5。 [Unity Sprite Sort Point](https://docs.unity3d.com/cn/6000.0/Manual/2d-renderer-sorting.html) · [Unity Sorting Group](https://docs.unity3d.com/cn/6000.0/Manual/sprite/sorting-group/sort-renderers-within-sorting-group.html)
4. 把 A 放到 `(-0.15, -0.15, 0)`，B 放到 `(0.15, 0.15, 0)`。两者重叠时，预期 A 压在 B 前面。只把 A 的 Y 改为 `0.35`，仍有重叠，预期 B 改为在前面。连续移动时，遮挡在脚底 Y 交叉后交换。 [Unity CustomAxis 方向](https://docs.unity3d.com/ja/6000.0/ScriptReference/TransparencySortMode.CustomAxis.html)
5. 正式接入时，从已提交的 Entitas 战斗快照取得位置，由表现层按渲染帧更新单位脚底根节点的世界 XY。单位的渲染 Z 可保持固定，URP 每帧按脚底轴投影排序。地面放固定的背景排序层，需要与单位相互遮挡的树木和建筑用同一排序层及 Order，锚点取各自底部落地点。

以上为实施步骤及预期结果。当前仅更新说明文档。

## 大批透明实例的限制

如果目标还包括无 GameObject 的批量绘制，`Graphics.RenderMeshInstanced` 将一次提交的实例作为整体与场景对象做排序。举例，远处 A、居中 B、近处 A 需要按 A → B → A 绘制。按材质压成 A、B 两组后，A 批次整体无法跨在 B 的两边。可评估支持逐实例排序位置的 `BatchRendererGroup` 或自行保证全局透明顺序的提交方案，并验证当前 URP 2D 路径、Shader、目标图形 API 和裁剪。Entities Graphics 1.0.16 的绘制命令生成代码会在带排序位置时按实例计绘制命令数，迁移时应把命令数纳入比较。 [RenderMeshInstanced](https://docs.unity3d.com/cn/6000.0/ScriptReference/Graphics.RenderMeshInstanced.html) · [BRG 排序位置](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Rendering.BatchDrawCommand-sortingPosition.html) · [Entities Graphics 1.0.16 绘制命令生成](https://github.com/needle-mirror/com.unity.entities.graphics/blob/1.0.16/Unity.Entities.Graphics/DrawCommandGeneration.cs)

后续若要验收，先用两个不同颜色的半透明单位在世界 XY 中交叉，交换脚底 Y 后前后关系应随画面交换。再覆盖同 Y 的产品规则、组合精灵、相邻特效和跨材质交错。性能比较以实际可见单位数下的主线程渲染提交、Job 等待、绘制批次和 GPU 时间为准。本次已做源码阅读与独立复核，未启动 Unity 或运行编译、场景和 Profiler。
