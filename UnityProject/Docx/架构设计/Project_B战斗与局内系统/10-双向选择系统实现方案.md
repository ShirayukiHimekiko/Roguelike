# Project B 特殊的双向选择系统实现方案

## 策划事实与规则待定

[Project_B 原件修订 5989](<D:/缓存/WorkBuddy/2026-11-13-23-19-02/Project_B.md>) L123–157、L244–252、L407–429、L479–485 明确两类选择。

1. **双向商店。** 玩家向和敌人向各 6 格，通过自购买强化、喂养敌方换金币、付金币拆除敌方可移除持有物。店面支持进店刷新、付费刷新、己方未买商品锁定、固定格候选、落选补权重和拆除保底。价格、两侧商品和刷新规则由局内养成生成店面状态，本模块把已核定报价转化为双方交易计划。
2. **海克斯双向三选一。** 一个候选是事先配置的一对海克斯，左右分别给玩家和敌人，玩家只选择一次。触发包括玩家达到 3/7/12/18/24/30 级、击败前四名守方英雄和完成指定任务。法球奖励若发放海克斯，要区分直接给单个、给组合还是给选择次数。原案另有已拥有海克斯的随机/定向洗练，洗练对象、两侧组合约束与替换时机待定。

即时生效且不入背包的敌方商店物品/Buff 与「同一回合可拆」存在适用范围差异。首版建议同店可拆刚入包的待部署塔或已配置为可拆的海克斯，已上场塔及无持有条目的即时效果不进入拆除候选。若策划要求即时效果可撤销，需要保存可拆来源、可逆操作和移除后对已产生结果的规则。已发资源、已销毁实体等既成结果需要单独定义处理，不能用“移除 Buff”概括。

## 模块契约与数据

| 数据 | 约束 |
| --- | --- |
| `TradeQuote` | 局内养成生成的不可变报价，含 WindowId、SlotId、OfferId、Revision、交易类型、目标英雄、价格及奖励。选择系统使用权威报价，不接受 UI 提供价格/载荷。 |
| `HexPairDef` | PairDefId、PairWeight、出现/删除回合、PlayerHexId、EnemyHexId。单项海克斯权重只在单项抽取或洗练规则确定时使用。 |
| `ChoiceTicket` | 局内养成里程碑和战果等转成票据，键为来源事实＋序号。记当前全局回合与计划接收效果的 DefendingHeroId。 |
| `ChoiceSession` | RunId、WindowId、Revision、TicketId、映射到三个稳定 CandidateId 的已生成组合、Pending/Committed/Cancelled 状态。窗口开启时生成一次。 |
| `HexOwnership` | 以 `(ChoiceTicketId, Side)` 标识一次持有，效果来源进一步附 EffectOrdinal。敌方目标使用当前层的英雄实例身份，避免重复获得相同定义时误删，或同一英雄定义再次出现时误延续。背包可投影持有和可拆摘要，Buff 管自身实例。 |
| `SelectionPlan` | 只读准备结果，包含资源、牌组、背包、Buff 或选择自身的值请求及失败原因。战斗编排负责路由和提交。 |

本模块可作为局级纯 C# 服务。商店与海克斯接 RunSession 的 WindowId/Revision/RunCommandSequence，BattleTick 在这些窗口不推进。玩家与敌人效果提交后立即建立各自产物及源记录。下回合常驻效果从局级种子进入 BattleContext，实际 Tick 效果由 Buff 或技能自己的 Entitas 系统推进。UI 消费投影，关闭和重开页面不改变候选及随机游标。版本冲突返回当前结果供界面刷新。 [现行帧驱动方案](../Project_B-帧驱动框架设计方案.md) · [战斗编排](00-战斗编排与集成方案.md)

## 双向交易路径

| 交易 | 局内所有者补丁 |
| --- | --- |
| 自购 | 校验本方未售出报价，资源扣价，卡牌/背包/Buff 添加对应产物，局内养成标记报价已售。 |
| 喂养敌方 | 可配置先扣前置价，再获得金币。敌方塔入敌方待部署背包，敌方即时物品/Buff 生效后记效果来源，局内养成更新报价。 |
| 拆除 | 在最新敌方可拆投影中锁定明确实例及版本。资源扣价，背包移除待部署实例或海克斯选择所有者移除明确持有条目。可拆海克斯仅撤销该 SourceId 的可逆效果，检查作用域和独立叠加来源。禁止基于定义 ID 批量误删。 |

报价筛选区分「软保底」和「硬保底」。软权重记录是完整刷新机会的状态，硬保底以允许交易的连续商店回合计数。达阈值且有合法可拆目标时，局内养成预留至少一格的可拆报价，禁止依赖无限增加权重碰运气。无目标时不产生死商品，保留应补资格，直到下一次合法商店；计数边界由策划确认。交易过程中目标在另一事务消失，按陈旧版本拒绝，金币、报价和效果均不改变。 [局内养成](05-局内养成实现方案.md) · [资源](09-资源系统实现方案.md) · [背包](08-背包实现方案.md)

## 三选一、触发与洗练

1. 战斗模块按已提交的事件发票据。一次升级跨过多个阈值，分别登记一张，按阈值从小到大排队。关卡、等级和任务若同阶段触发，建议用关卡事实、里程碑、任务的固定顺序消费。按来源身份去重。
2. 开窗时过滤两侧定义、有效全局回合范围、解锁、禁用和目标有效性，再按 PairDefId 排序，从权重大于零的候选里无放回抽三个。记录所用配置、候选及随机游标。首期建议 `StartRound ≤ Round < RemoveRound`，有无上界明确编码。若可抽配对池不足三个，使用显式配置的兜底配对表；兜底需过同一合法性筛选。仍不足返回内容错误并保留票据供处理。
3. 旧英雄在击破后离场，撤销属于该英雄实例且无继承配置的来源。建议因击败前四名英雄触发的票据指向下一位英雄，关卡切换后、首轮准备前显示。其他票据按创建时的阶段策略明确接收方。并发票据逐个建窗，每次按当时合法条件建池，切换目标必须显式处理未打开票据。第五名英雄战后按整局结算，专门的击败奖励规则另列。
4. 将所选 PairDef 的两边归属与效果展开为有序补丁。全部合法才写入选中状态。若上一选择的奖励继续发放选择次数，先等当前窗口提交，再生成下一张独立票据，避免可重入。带拒绝的两侧效果在预检阶段一起验证，执行先后不得改变已公布的选项内容。
5. 洗练作为首版双向选择完成后的独立命令。建议初期只开放配置声明可替换的单项，限定同受益方，撤销旧来源的持续效果并准备新一次授予。随机与定向共用合法池，失败保留旧项。是否强制成对洗练、既发一次性奖励的去向、单项权重语义明确后才能配置实物内容。

```text
PrepareChoice(request, session, sideSnapshots)
    verify RunId, WindowId, Revision and Pending state
    pair = session.findCandidate(request.CandidateId)
    verify current beneficiary identity and allowed outcome
    plan = build ordered player and enemy grants from pair
    append own ownership and terminal transition patches
    return plan

ApplySelection(request)
    plan = selection.prepare(valuesFor(request))
    batch = battle.prepareAll(plan, currentOwnerWorkingViews)
    if rejected: publish rejection, keep window and candidate state
    otherwise:
        battle.commit(batch)  // both recipients, consumed ticket, all receipts
```

同一窗口的两次有效而互斥点击按 RunCommandSequence 先后处理。已完成的相同请求幂等返回，第二个不同请求读取已终止窗口并拒绝。若在获批后出现内部异常，交给战斗隔离故障会话，避免一侧已实付且 UI 显示交易成功。

## 分步实施与验收

- [ ] **报价和交易。** 接入一个本方购买、一个喂塔和一个拆塔实例。实现 `报价 → 业务计划 → 多所有者预检 → 两边原子提交`。
- [ ] **窗口与抽样。** 实现配对表、来源票据、固定种子的无放回抽样、来源去重和选择记账。
- [ ] **跨层与效果。** 接入升级和前四层通关票据、常驻效果种子、任务产票和退场清理。验证敌方增益实际作用在指定英雄。
- [ ] **补齐策划待定。** 配置软硬保底、交易费用、选择跳过和洗练；接入法球中对应的海克斯奖励边界并补回归。

| 场景 | 预期 |
| --- | --- |
| 购入一座待部署敌塔，商店刷新可拆且用户购买拆除 | 玩家按两笔交易分别入账；该实例从待部署池移除，准备阶段不会部署它。 |
| 即时 Buff 未入包或塔已部署 | 不提供拆除目标，过时或伪造的拆除请求不扣费。 |
| 连续刷新未出现拆除且到达阈值 | 有合法目标时在规定回合出现；锁定、固定槽及无目标按已配置优先级处理。 |
| 三选一关闭后重开，同窗口重复确认或切到另一个英雄后提交旧请求 | 候选保持；同一票据只结算一次，旧英雄的命令不会发给新英雄。 |
| 玩家效果有空间、敌方效果失去合法接收方 | 整体未提交，双方数据和候选保持。 |
| 一次升级跨两个里程碑且同阶段通过一层 | 独立票据顺序固定，且每张的目标英雄清楚可追溯。 |

需要策划确认选择窗的顺序、选项不足和跳过、首四层过关奖励的敌方接收者、是否允许同一侧海克斯重复出现、即时效果可拆边界和洗练是否成对。当前为设计及待办，未运行 Unity、编译或测试。
