# Project B 敌方 AI 实现方案

状态为实现提案。AI 负责每轮准备窗口内的防守布局规划。塔的自动战斗由建筑系统处理。本方案接入战斗编排、战场占位与局内敌方背包，接口和表名均为拟定。[战斗编排](00-战斗编排与集成方案.md) · [建筑](03-建筑实现方案.md) · [背包](08-背包实现方案.md)

## 策划口径

- 一局面对五位英雄。回合表以跨层累加的全局回合号查表，回合结束可发给敌方建筑；敌人升级表按等级新增开放格数并发建筑。阶段流程为玩家点击准备结束 → 敌人部署或调整建筑 → 部署完毕 → 结束准备。来源为策划原件修订 5989 L7–25、L232–252、L535–553。[Project_B 原案](https://my.feishu.cn/wiki/AIEkwlgbqiha8dkcxXSc0oH9nae) · [需求 02](../../游戏设计/功能需求/02-五层挑战与英雄.md) · [需求 13](../../游戏设计/功能需求/13-敌方AI部署.md)
- 只有已开放的合法格可放塔，容量用尽后本回合无法继续放置。核心使用中心格。核心占位、暴露、抵抗塔复活和破损格释放由建筑与战斗按各自职责处理。准备结束时清除敌方背包中未被部署的建筑。商店赠送塔进入背包，赠送物品或 BUFF 按原案即时生效。来源为原案 L234–252、L368–370。[需求 12](../../游戏设计/功能需求/12-敌方格位与占位.md) · [需求 21](../../游戏设计/功能需求/21-双向购买与拆除.md) · [需求 29](../../游戏设计/功能需求/29-敌方背包.md)
- 五位英雄的初始地图与等级、每级具体开放哪些格、换层敌方背包或成长继承、抵抗塔可否重排、每准备窗口的搬迁上限，以及「最优」偏好仍待策划定稿。等级表只给开放数量，提案由各地图的显式开格顺序映射到具体格 ID，校验累计数量及格 ID 唯一性。背包和世界随当前英雄上下文传入，继承规则由局内持有人执行。

## 外部实现与路线选择

| 原件所见 | 迁移到 Project B 的做法 |
| --- | --- |
| OpenRA 的 `BaseBuilderBotModule` 按生产类别管理建造队列，周期整理待产数量并驱动选定队列。普通 `PlaceBuilding` 命令在提交边界重新寻找生产者和已完成条目、查放置合法性，创建后才结束生产。 [BaseBuilderBotModule.cs L203–218、L302–339](https://github.com/OpenRA/OpenRA/blob/bleed/OpenRA.Mods.Common/Traits/BotModules/BaseBuilderBotModule.cs#L203-L339) · [PlaceBuilding.cs L55–80、L184–215](https://github.com/OpenRA/OpenRA/blob/bleed/OpenRA.Mods.Common/Traits/Player/PlaceBuilding.cs#L184-L215) | 采用规划与提交分开、提交时复验资源与格位的次序。Project B 只在准备窗口规划，背包条目替代连续生产队列；整份移动加放置计划须先联合预检，避免互换、复活格与背包提交相互覆盖。 |
| Mindustry 的 `SpawnGroup.getSpawned` 从波次范围、间隔和基础数量计算投放量；`WaveSpawner.spawnEnemies` 再按规则及可用出生点创建实体。 [SpawnGroup.java L58–75](https://github.com/Anuken/Mindustry/blob/master/core/src/mindustry/game/SpawnGroup.java#L58-L75) · [WaveSpawner.java L58–105](https://github.com/Anuken/Mindustry/blob/master/core/src/mindustry/ai/WaveSpawner.java#L58-L105) | 局内成长按回合、等级和配置产出建筑条目，AI 只在背包已有条目中选择。固定波次和出生点适合发放时机建模，无法解决守阵重排与多格约束。 |
| Supercell 的《部落冲突》官方资料说明 Capital 的阵型编辑与交战生效是分开的，且敌人破坏建筑会扩大进攻部署范围。 [Defending the Capital](https://support.supercell.com/clash-of-clans/en/articles/defending-the-capital-2.html) | 准备结束时锁定最终阵型。评估守势时使用本项目固定围栏下可部署的入口，以及战斗端定义的八方向屏障规则。 |

首期用固定候选评估预算的贪心加有限换位。整个准备窗口显式固定阵型、入包数据和防守目标，可以按布局产生可解释的评分。纯脚本阵型难以响应实际背包和战损；全排列能覆盖组合，但新增建筑与换位的搜索量随格位放大。首期保留可重复的贪心基线，只有已确认的地图与平衡目标显示收益时，再比较定宽束搜索或离线验算。评分参数需要策划审核，运行结果只承诺在已考察候选中的最优。

## 状态、接口与帧边界

| 拥有者 | 权威数据与边界 |
| --- | --- |
| 局内进度与背包 | 本回合开始前处理等级、开放权限、定期发放与背包条目。发放键为 `RunId + HeroLayerId + GrantKind + ConfigRowId + TriggerOrdinal`，可以区分同物品的多份奖励并拦截重复发放。每个可用建筑条目有稳定 `HeldItemId` 和背包版本。 |
| 战斗编排与唯一占位所有者 | 根据局内进度组装布局快照。用同一格位规则检查锁定、中心格、地形、足迹与占用。提交跨所有者事务并推进准备阶段。 |
| 建筑 | 拥有塔的业务 ID、代际、状态、生命、可移动标记与建筑配置。输出只读建筑投影，消费编排转达且经核准的放置、移动和复活。 |
| AI | 窗口内仅有计划输入、候选缓冲、搜索游标和输出。使用同一占位规则的纯函数在局部模拟布局。它的临时格表只供当前评分，真实占位由战场写入。 |

- `DeploymentInput` 提议包含 `RunId, HeroLayerId, RoundId, WindowId, RequestId, ConfigVersion, LayoutVersion, InventoryVersion`，布局拓扑、按 ID 排序的已开放格、核心/抵抗塔保留格、现存塔（`TowerInstanceId`、代际、格位、足迹、能力与移动资格）、可部署库存（条目 ID、塔定义 ID、星级）和只读评分定义。现有塔的复活与治疗先完成预检、锁定预计占位，再由编排交值投影给 AI。
- `DeploymentPlan` 返回相同身份和版本，操作为 `Move(TowerInstanceId, Generation, FromSlot, ToSlot)`、`Place(HeldItemId, ToSlot)`，及诊断原因、基线与所选评分。未放置列表可供预览，最终清理清单由背包所有者按提交结果和冻结后的条目集生成。
- 准备窗口由战斗编排分配 `WindowId`。玩家确认时封存该窗口指令和影响部署的数据，完成本阶段的创建、治疗及复活投影并提交 AI 计划。整批提交包含清除本窗口中余下的建筑条目，随后发送准备完成事实并启动战斗 Tick。重复点击或重复完成回调通过窗口身份与请求 ID 返回已有结果。每个准备窗口只提交一次完成结果。
- 每回合新建 `BattleWorld`，由建筑向编排交付上一回合的值快照。AI 不推进 `BattleTick`。固定工作量搜索如需分片，仍用一个明确运行阶段和固定候选数，宿主帧仅调度片段，帧表现耗时不进入决策。战斗期的公共顺序为入帧 → 指令提交 → 效果与属性 → 行动与命中 → 结算 → 收尾。AI 没有战斗期系统或独立 Context，按需记录可重跑的部署输入和结果；相关战斗实体进入正式 `Battle` Context。[帧驱动设计 §3–6](../Project_B-帧驱动框架设计方案.md) · [Entitas 1.14.1](https://github.com/sschmid/Entitas/releases/tag/1.14.1)

## 规划和提交

准备期运行在战斗开表前。规划可使用回合前已知阵容和效果快照中明确允许 AI 读取的值。首期提案用以下优先级；策划可改变优先级与权重，结果摘要记录评分版本。

| 优先项 | 审核口径 |
| --- | --- |
| 受保护的核心 | 最大化遭攻击入口中最薄方向的屏障深度，再提升受保护方向数量。方向、格子是否构成屏障以及破损、复活状态的判断使用战斗提供的布局规则。 |
| 阻挡与火力覆盖 | 对配置中的有限探测入口序列，预估有效炮塔覆盖和抵抗塔覆盖，重合火力按配置做贡献上限，避免所有强塔扎堆。用配置权重表达英雄偏好。 |
| 光环收益及搬迁 | 按九宫格层数统计受益目标，以整数贡献和显式上限评分。前项相同时优先减少搬迁，最后按操作稳定键比较。 |

所有评分输入、权重用固定刻度值或整数。边界地图、相同评分、空格集和候选预算耗尽均走稳定路径。候选序按库存条目 ID、塔 ID、起点格、终点格排序，同分选字典序最前的合法方案。移动使用相对原布局的最终位置表达，允许交换时在临时格表一次移除参加变更的原占位后检查每个目标足迹。首期建议允许摆新塔和有限移动已确认可移动的存活非核心塔；抵抗塔复活格在保留期间纳入锁定集合，未定的多格移动和换位策略由配置关停。

```text
Plan(window)
    shadow = window.layoutWithReservedCells
    按背包项和合法格稳定枚举，选可放置的最佳一对并写入 shadow
    重复直至无可增加项、用完固定候选预算或已无余量
    按稳定顺序枚举允许的移动或两塔换位
    只接受严格提升评分的联合合法候选并记录最终位置
    返回属于同一准备窗口的规范化操作集和输入版本

CommitPlan(window, plan)    // 战斗编排
    确认准备窗口与两个资源版本仍有效
    预检全部移动、放置、库存扣减、剩余建筑清理与输出容量
    占位、建筑和背包按各自预检通过的批次一次提交
    封存准备完成，移交 Tick 0 的战斗初态
```

无可放置候选时仍可检查允许的换位。放置和移动都无可行操作时产生合法空计划，提交时给出明确结束事实。若版本变化，由编排在窗口仍有效时取得最新快照并有限次重算。重算耗尽时默认报告阶段错误并保留库存。产品明确接受失败降级会清除未部署建筑时，才可用最新且已冻结的快照核准空计划，并按窗口的成功规则清理。非法配置、核心占位缺失、同一条目重复消费、异常写入均报告故障，保留诊断并停止该准备窗口；编排发布成功事实前完成全批校验，若部分写入后故障则结束该故障世界，保留上次已提交的外部值。历史计划或不同层的数据直接拒绝。

## 执行步骤与验收

- [ ] **准备窗口输入。** 补英雄场地配置、每级开放顺序、建筑发放和投影。实现 `已提交的进度与背包 + 上回合建筑快照 → 当前窗口输入`，将成长与规划隔离。
- [ ] **规划器。** 加入合法候选、基线、有限搬迁和可解释评分。实现 `固定次序候选 → 整数评分 → 同分按稳定键选择`。用小棋盘人工枚举对照，再收集真实英雄输入的评分和候选数量。
- [ ] **唯一事务入口。** 做好带版本的预检、格位交易、创建与移动、库存扣减和剩余建筑清理。实现 `预检全部 → 各所有者写入 → 一次发布窗口完成`。
- [ ] **故障与追溯。** 记录输入版本、候选预算、所选操作和阶段结果。实现 `重复完成读取旧结果，过期计划触发有限重算，故障停留在阶段出口`。

| 场景 | 预期 |
| --- | --- |
| 只有一个空格、两份内容相同的塔 | 选中稳定次序中的条目一次，另一份按窗口结束规则清除；核心格和复活保留格保持不变。 |
| 棋盘无可放格或背包无塔，且没有可行的重排 | 结出合法空计划，准备完成只发生一次。若有未部署的建筑，按原案清理该类条目。 |
| 两塔换位或多格同时移动 | 校验联合占位后才提交。地图限制和任一足迹冲突都会使整组候选失效。 |
| 重复准备结束、版本变化或换层后回调 | 无重复扣减、清理或开战。陈旧数据无法提交到新英雄。 |
| 同一输入重跑、改变宿主帧率或重排集合枚举 | 计划、评分、提交顺序及 Tick 0 初态一致。 |
