# Project B 背包实现方案

设计提案 · 2026-11-15。需求依据为 2026-11-15 导出的 [《Project_B》修订 5989](https://my.feishu.cn/wiki/AIEkwlgbqiha8dkcxXSc0oH9nae) L89–121、L234–252、L358–405、L407–429、L475–485、L535–553。仓库 [局内背包](../../游戏设计/功能需求/28-局内背包.md)、[敌方背包](../../游戏设计/功能需求/29-敌方背包.md)、[局内装备](../../游戏设计/功能需求/25-局内装备.md) 可追溯需求分析。装备规则以修订 5989 为准。以下接口与表名均为提案。

## 1. 规则和配置边界

| 策划事实 | 落地方式及待确认项 |
| --- | --- |
| 玩家局内背包展示本局牌组、物品、海克斯和未使用装备。敌方背包持有物品、BUFF、建筑和海克斯。 | 由编排汇总各所有者的版本化视图，背包持有真实物品装备和敌方待部署/待使用实例。牌组及双方海克斯按所有者投影。展示时机、敌包可见程度、容量与各类型跨层策略进入配置。 |
| 每张卡最多一件装备，召唤的所有单位均得到装备效果。两张卡合成时，一件装备继承，两件装备分别入包。获取可来自商店、海克斯、任务和法球。 | 装备状态使用 `ItemInstance` 和 `EquipmentAssignment`。规则表定义可装配卡类型、装备和目标效果；装备保留实例身份。删除或消耗卡后的装备去向待确认，提案为返还背包。更换、拆卸、适用阶段及携带容量待确认。 |
| 商店买给敌方的物品、BUFF 即时生效且不入包。商店买给敌方的塔可在本回合拆除，部署后不能拆。 | 由双向选择和编排根据商品 `DeliveryMode` 路由。入包型生成持有实例；即时型提交效果意图且不生成可拆对象。QA 本回合可拆对已入包且尚未部署的对象成立。即时型是否也应可撤回与只能拆背包内对象有冲突，提案暂按不入包即无背包可拆资格，留给策划确认。 |
| 敌方在准备阶段部署建筑，准备结束清理未部署建筑。 | 部署基于持有塔 ID 及当前场地值快照。背包消费已部署持有实例并清除剩余未部署塔，建筑及占位所有者提交对应结果，以上同属一个准备窗完成事务。非建筑的使用或生效时点待确认。 |
| 双方海克斯是持有内容，购买拆除可能作用于敌方海克斯。所有局内效果离局清空。 | 双向选择唯一管理双方海克斯归属、重置和拆除资格，效果域持实际效果，背包只展示相应值投影。对持续来源撤回有明确持有资格时可要求移除；已触发的一次性后果是否逆转由效果规则确认。 |

配置数据建议采用 `ItemDef(DefId, Kind, Rarity, Unlock, UseTiming, DeliveryMode, Persistence, RemoveRule, Effects[])`、`EquipRule(DefId, AllowedCardKinds, EffectSpec[])` 和 `InventoryRule(Scope, Capacity, StackPolicy, ReturnPolicy)`。提案默认装备按实例持有，展示可以合并同类型行。开放上限和溢出政策先由策划定稿。可替换的交付策略分为正式发放失败可重试、购买先拒绝和必须返还的脱装装备；禁止用 UI 是否有空格代替规则。原案装备每卡一件、双装备合成返还均应能兑现。若后来设置仓位上限，编排在 `Prepare` 中预估退包空间，并提供策划确认过的容量或专用保留策略。

## 3. 运行状态和唯一写入者

| 数据 | 所属及消费 |
| --- | --- |
| `HeldItem(ItemInstanceId, OwnerId, DefId, Kind, DeliverySource, ActiveScope, UseState)` | `RunSession` 的背包所有者。玩家物品和装备，以及敌方普通物品、待激活 BUFF、待部署塔。`OwnerId` 指向本局玩家或具体敌方英雄实例。ID 本局唯一且不复用；同定义不同来源能被明确拆除或去重。 |
| `EquipmentAssignment(CardInstanceId, ItemInstanceId)` 与未装配装备索引 | 背包所有者。约束为一张卡至多一件装备，一件装备至多关联一张卡。未装配状态由所属装备减去关联来投影，避免又存占包件数又存归属。编排向卡牌与战斗提供 `EquipmentBindingValue(CardInstanceId, ItemInstanceId, EffectSpecIds)`。 |
| `PendingTower(HeldItemId, TowerDefId, HeroOwnerId, SourceKey)` | 背包持有的未部署业务项目。建筑域拥有已部署建筑实例及其锚点投影，战斗占位表是格位占用的唯一事实来源。入场结果可带来源 ID 供统计。已经部署的塔不能再按 `HeldItemId` 在背包报价交易中消费。 |
| 本局牌组、双方持有海克斯、激活效果、金币费用 | 卡牌、双向选择、效果与资源域分别拥有。`BackpackView(Revision, OwnDeckView, OwnHeldItems, OwnHexView, FoeHeldItems, FoeHexView)` 由战斗编排按规则组装。背包自身只输出持有 DTO、装备投影和背包项目拆除候选。 |

值请求包括 `GrantItem(SourceKey, OwnerId, DefId, Quantity, DeliveryMode)`、`EquipItem(ItemInstanceId, CardInstanceId, CardEligibilityValue)`、`UnequipItem(CardInstanceId)`、`TransferMergedEquipment(InputCardIds[2], OutputCardId)`、`DetachRemovedCardEquipment(RemovedCardIds, Reason)`、`ConsumePendingTower(HeldItemId, OwnerId)`、`RemoveStoredItem(HeldItemId, OwnerId, AllowedKind)`、`CleanupUndeployedTowers(OwnerId, RoundNo)`。它们带本局身份，窗指令还带 `(WindowId, Revision, RunCommandSequence)`。待部署塔查询返回按稳定 ID 排序的值列表。背包只收到编排验证后的目标卡有效值或可交付的塔结果；自身只能读背包状态。先重复确认卡/塔寿命的一方是其领域所有者，由编排在同一事务使用这些预备结果。

值响应使用 `InventoryPlan(BaseRevision, Deltas, RequiresEffectChanges, PlacementInputs)`、`InventoryApplied(ChangedItemIds, AssignmentChanges, RemovedHeldItemIds)` 或 `InventoryRejected(Reason)`。授权窗拒绝显示库存不足、已部署、目标失效、阶段错误等业务原因。效果域消费可追踪来源描述 `EffectSource(ItemInstanceId, EffectId, TargetStableId, DurationScope)`，展示事件由编排批次发布。海克斯候选拆除或重置持有权时，编排向双向选择取其计划，背包无需生成一个同身份的套壳物品。

## 4. 装备、敌方配送和部署流程

```text
合两张卡或删牌，编排已有合法 DeckEditPlan
    依据 InputCardIds 读取背包拥有的 EquipmentAssignment
    解绑被删/被合成的旧 CardInstanceId
    合成且共一件装备：绑定 OutputCardId
    合成且各有一件装备：解绑后两件均投影为未装配
    删牌或消耗且需返包：解绑后投影为未装配
    在事务工作视图检查一物一槽、容量与相关效果源撤销
    同次提交牌变更、装备变更和必要的资源变更

敌方配送
    StoredItem/StoredBuff/PendingTower：Prepare 新持有实例
    Immediate：效果所有者 Prepare 按来源应用，背包保持原有持有集合
    编排 Prepare 报价与金币收支，全部可接受后 Commit

敌方准备结束
    编排冻结准备窗，取得按 HeldItemId 排序的待部署值和战斗占位快照
    部署策略在同一事务工作视图中选取按固定顺序排列的合法目标格
    对每个合法部署，准备消耗背包塔、创建建筑实例并登记占位
    在背包工作视图中按稳定 ID 准备清理仍未部署的待部署塔
    背包消费、建筑创建、占位登记及剩余清理全部可提交时，同步提交全组计划
    提交快照供新回合 BattleWorld 初始化；不因部署或清理推进 BattleTick
```

装配装备时以 `EquipRule` 决定卡类型资格。期望替换允许时，先规划卸旧/装新和旧装备归属，验证整个变更最终容量再提交。战斗开始时冻结绑定和效果值，召唤效果按（卡牌实例、装备实例、出牌标识、单位序）关联到每个目标单位；重复洗到同张卡时，同回合限次恢复按（回合、卡牌实例、装备实例、效果）记账。装备所有者只供给来源值，数值合并和应用由效果与属性阶段负责。提案装配操作只在授权商店窗开放，避免战中替换既有战斗单位属性；需开放其他阶段时显式补生效范围和旧单位处理。

敌方部署前的拆除以 `(HeroOwnerId, HeldItemId, Kind, RemoveRule)` 核实，另检查当前持有状态和价格。若当前入口来自海克斯投影，由双向选择确认可拆；命中即时效果时必须等策划明确撤回规则才有相应入口。准备部署被关闭或过期时，旧商店命令无法再删除同一物品。部署 AI 无位可放的待部署塔按策划清理；规则载入失败、非法配置、事务失败需要明确失败并保留重试所需值，不能当作无位清空正常库存。

| 失败场景 | 事务结果 |
| --- | --- |
| 同装备两次装配、卡片升星后窗口读到的旧实例、同一目标连续拆除 | 依据版本、窗口及请求 ID 去重。真正过期的目标返回拒绝，不扣资源，不更改原实例。 |
| 合成旧卡合法但装备无法返包，或一件装备因资格变化不能继承 | 提交前拒绝整笔并准确标示冲突。本案如采用“必须返还”的容量策略，应先确保其配置能覆盖双装合成的原案结果。 |
| 买给敌方的 BUFF 已即时生效，立即点拆除；本窗口买给敌方的塔未部署 | 前者缺少可拆持有，拒绝且无费用变动。后者持有检查成功时可在同一商店窗拆掉。 |
| 替换英雄、退出或重开后异步图标才返回 | 值命令以英雄/窗口/运行身份拒绝旧输入。UI 不参与写入，界面关闭时取消订阅并释放自身资源。离局清除持有、绑定及对应局内效果，其他局的实例和全局解锁不会被复用。 |

## 5. 帧、Entitas 1.14.1 和 TEngine 接入

背包优先使用由 `RunSession` 持有的轻量数据与索引，避免让背包跟随每回合 `BattleWorld` 重建。按[现行帧设计](../Project_B-帧驱动框架设计方案.md)连接到战斗编排的阶段：入帧封存输入；指令提交处理装备来源变化或物品使用意图；效果与属性应用装备和道具；行动与命中消费战场属性；结算把掉落事实交给成长/编排；收尾发布 `BattleTickBatch`。攻击期 `BattleCommand(BattleId, TargetTick, InputSequence, Payload)` 只在 BattleTick 消费。准备、商店、领取或过渡以外部事件顺序推进。背包作为所有者由编排同步询问，模块之间不互调或读对方 Context。外部条件和生成随机算法使用不可变 Luban 配置快照，数值反馈使用整数或固定点，枚举按稳定业务键排序。

实体只在有战斗侧匹配需求时引入。塔域使用 Entitas 1.14.1 的正式 Context 和 Jenny 生成组件/Matcher，背包携带 `HeldItemId`，编排从塔域回值取 `BattleEntityId`。生成 API 负责 `AddX/ReplaceX`，准备号或逐笔改动使用显式批次，以稳定 ID 排序。`ReactiveSystem` 可投影一次提交后的变化，逐笔事务使用独立顺序数据。业务新 Context、输入程序集、Jenny 输出及运行时插件引用采用本仓 `entitas-dev` 的 1.14.1 路径，现行工作树的 Demo 已移除。TEngine 界面按值提交请求及订阅提交后事件，文本、贴图、预制件异步加载使用对应资源接口并由窗口释放。[Entitas 1.14.1](https://github.com/sschmid/Entitas/releases/tag/1.14.1)

每笔 `Prepare` 只读真实状态；同所有者多计划用从起始快照构建的事务工作视图合并、校验整批最终约束。全部准备完毕由编排同步 `Commit`，提交区间准备完全部容量、派发槽和必要数据，排除中途可恢复异常与对外回调。第一次发布时各所有者状态已可一致读取。现有 Entitas Group 通知若涉及事务数据，限制在私有索引维护，跨模块/界面通知只消费提交后值结果。

## 6. 分步实施与验收

- [ ] 持有、定义表和读模型。目标是支持两侧物品、装备和塔的稳定身份。伪代码 `GrantBySource(StableSourceKey); ProjectVisibleHeldItems(Owner, Phase)`。验收同定义多件可区分，卡组和海克斯只投影各所属状态，装备出包后未装配列表不再显示。
- [ ] 装备关联与合卡联动。目标是唯一占位和正确返还。伪代码见 §4 的卡变更流程。验收空装合成无装、单装继承、双装都返包；删牌或替换失败会保留原关联和牌；三单位共享有效装备来源。
- [ ] 双向送货与拆除。目标是按配置把 Stored 与 Immediate 分流。伪代码 `PrepareDeliveryMode; PrepareOfferAndWallet; CommitAll`。验收即时 BUFF 效果存在且背包无该实例、未部署同店塔可拆、已部署塔不可拆，失败不扣金币。
- [ ] 敌塔部署及准备清理。目标是待部署到战场的唯一转移。伪代码 `PreparePlacementAndConsumption(HeldItemId, Cell); PrepareCleanupOfRemainder(); CommitAll()`。验收成功部署后只在建筑域有实体，占位表记录其格位，无位塔在同次提交中清除，故障时库存、建筑和格位均保持，重复 `FinishPreparation` 不重复放塔。
- [ ] 完善跨层、演出与清理。目标是不同来源的生命周期和版本能被复盘。伪代码 `PrepareCloseScope(OwnerId, Scope); Commit; PublishView(Revision)`。验收指定跨层物品按表保留、旧敌方持有不落入新英雄、离局清除所有局内装备与效果、重开后旧命令被拒绝。

本稿已列未来实施及验收口径。物品主动使用、跨层继承、拆除即时效果冲突和替换动作的正式内容需策划定稿。
