# 战斗框架与玩法组件解耦执行方案

状态：已确认并实施；运行验收结果见文末。

## 目标与边界

正式单机入口可以启动、结束、录制和回放一个没有玩法实体的房间。框架负责房间、定时推进、玩家输入槽、Entitas 世界、世界 ID、组件快照和重建；接入方负责有哪些单位、初始位姿、谁操控谁、怎样消费输入以及具体演算。临时实现和验收数据都留在 [Tools/BattleFrameworkDemo](../../Tools/BattleFrameworkDemo)，正式代码及 Jenny 的生成输入均不依赖该目录。

[ET 的 RoomSystem](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lockstep/Scripts/Hotfix/Share/RoomSystem.cs#L31) 把输入交给样例单位，再保存帧前状态并更新世界。沿用这个顺序；项目的房间只负责向当前世界接入的逻辑交付封存后的输入。开局与定位继续复用上一阶段已经验证的世界重建机制。

## 当前代码里需要解除的依赖

| 当前文件或数据 | 现状 | 拆分后 |
| --- | --- | --- |
| `BattleWorld` | 根据开局单位表生成实体，把前几个世界 ID 绑到输入槽；每帧主动给这些实体写输入。 | 世界只提供 Entitas Context、帧、实体 ID、随机状态、系统执行与恢复。玩家到实体的绑定由接入方建立并保存。 |
| `BattleStartData`、`BattleUnitStartData`、`BattleUnitState`、`TryGetUnitState` | 开局和查询默认都有单位及位姿。 | 开局数据保存有序玩家 ID 列表、本地玩家 ID 和随机种子。移除框架中的单位开局与状态查询，Demo 自己查它的组件。 |
| `BattleSnapshotComponents` | 内置四个单位组件的编码，直接查生产 `BattleComponentsLookup`。 | 从当前 Context 的组件类型表解析索引，由接入方为需要入快照的组件显式登记稳定键和读写方法。 |
| `BattleRecordingFile` | V2 录像头保存单位 ID 和初始位姿。 | V3 录像头只保存框架的开局数据，初始玩法世界由已有的第 0 帧检查点保存。 |
| Jenny 生成物 | 正式 Battle Context 包含四个样例组件及生成的 Getter、Matcher。 | 保留正式 Battle Context，重新生成其布局，移除样例组件和对应生成 API。 |

## 分步执行

- [x] **1. 按玩家确定输入槽。** 在开局入口验证玩家 ID 和本地玩家归属，房间一次建立 `PlayerId → slot` 映射。删除世界内开局实体数组和按 ID 整数区间恢复玩家实体的逻辑。封存、查询历史与回放只使用房间的玩家槽；实体死亡或换人不需要调整录像输入下标。主场景用空的玩家表启动框架。伪代码：`participants → room slots；frame inputs[slot] → consumer`。
- [x] **2. 提供一处世界接入配置。** 保留现有系统工厂和快照登记，补上实时开局建实体、帧输入交付两个调用点。正式入口默认使用生成的 Battle Context；仅在有接入方提供自己的组件布局时，用它创建的 Entitas `Context<BattleEntity>`。实现上把这些入口集中在一份房间级配置里，不引入玩法基类。输入只以当帧只读视图同步提交，接入方可按玩家 ID 读取；真实改变战斗结果的逻辑在系统执行阶段处理。伪代码：`live: context → register codecs → seed entities → mount systems`，`tick: deliver sealed inputs → capture/hash → execute/cleanup → Frame++`。
- [x] **3. 用检查点还原开局和定位状态。** V3 保存种子、有序玩家 ID、逐帧输入与现有的周期检查点。回放打开时使用第 0 帧检查点，定位时使用不晚于目标帧的最近检查点，均先恢复实体和随机状态，再绑定系统。实时建单位的入口只执行一次；定位或回放不再调它。帧前快照中可能已含本帧输入，输入接入回调必须是可重复的当前值写入，不能在回调里生成实体、消费随机数或累计状态。恢复第 N 帧快照后，房间帧设为 N−1，再从第 N 帧执行。伪代码：`release old → restore checkpoint → bind → AuthorityFrame = N - 1 → replay N..target`。旧 V2 文件保留原位置，菜单读写独立的 V3 文件；本轮不做 V2 自动转换。
- [x] **4. 搬出样例组件并清理生成配置。** 把位姿、玩家与实体关联、当帧实体输入及 Demo 系统挪到 Tools 下的验收脚本，由它定义局部组件布局并注册自己的快照键。当前本地 Entitas DLL 提供 `Context<BattleEntity>` 构造参数和 `contextInfo`，Demo 可以在同一真实 Entitas 运行时中声明自己的槽位；可用的泛型类型仍来自正式工程。用项目现有 Jenny 1.14.1 入口从更新后的生成输入重建正式产物，清掉这四个组件的源文件与生成调用。先检查仅保留已配置 Battle Context 时的生成结果；若出现工具配置问题，按实际输出处理，绝不为了生成空 Context 而保留样例组件占位。伪代码：`Demo private layout → supplied context；Jenny formal context → actual production components`。
- [x] **5. 验收两层边界。** 核对正式脚本及生成输入无 Demo 引用，正式空房间通过就绪、50 ms 步进、退局和 V3 回放。Demo 仍走同一套房间、更新器及快照链路，复验 1,206 帧落盘、检查点 0/1,200 往返、稳定 ID、随机续接及旧系统销毁。增加“同一玩家输入槽先供一个实体使用，旧实体销毁后由新实体接管”的断言，证明输入与世界 ID 已分离。伪代码：`record live → reload V3 → restore at 0/1200 → compare hashes/state and active input target`。

## 确认事项

本轮只调整框架和验收模型的依赖方向。正式玩法之后在 `Runtime/Battle` 接入；方向和按钮作为现有的帧输入值继续使用，实际含义由玩法消费端确定。验收计划不包含联机、独立 Player 构建或定点数学库逐值比对。

已修改房间输入槽、世界装配、录像头和 Demo。Jenny 1.14.1 保持 Game、Battle 两个 Context，正式 Battle 布局为零组件；对应的四个旧组件及生成扩展已通过 Pipeline 清理。
