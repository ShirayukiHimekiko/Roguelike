# 单机战斗框架与 ET10 源码完整对比

2026-11-18 通过 GitHub 读取 `egametang/ET` 的 `refs/heads/master`，提交为 `743c635dd5b0f6f6bab549c0093382c85f3f8307`，与本项目先前锁定的基线一致。锁步包为 `cn.etetet.lockstep` 3.0.2，参考同提交的 `lsentity`、TrueSync 和相关 Core 实现。上游 Unity 版本为 `2022.3.62f3`，本项目为 `6000.0.69f1`。本项目以工作区代码为准，涵盖 `5abd4ad` 之后尚未提交的战斗框架改动。此次按 Git blob 校验了 99 份上游源码和配置文件，使用源码审查及已归档验收记录。 [上游固定提交][et] · [Lockstep 源码树][lockstep] · [当前验收记录](战斗框架文件归位方案.md)

范围为单机权威房间、逻辑帧、输入、确定性世界、快照、录像和进退场。客户端预测、回滚、校时和重连只用来确认单机边界。样例移动、视图、动画、镜头和键位只核对依赖方向，正式规则由项目后续定义。

## 1. 先核对上游的实际运行链

ET 将 Lockstep 标记为预测回滚示例。`MatchCount = 1` 表示示例匹配一名玩家，进场依然经过客户端、服务器房间与开战消息。当前项目的单机房间直接承担服务端权威更新器的角色，本地回放承担录像更新器的角色。把 `MatchCount = 1` 当成上游提供的纯离线模式，会误把服务器协议或客户端预测算进单机首版。 [包清单][package] · [匹配常量][constants] · [匹配到进场][enter-map] · [权威更新][server-updater]

```text
ET 联机示例
服务器建房 → 客户端建房并等待场景准备 → 客户端上报就绪
          → 服务端确定开局单位与起始时刻 → 双端挂各自更新器 → 推进世界

当前单机
StartUI → LocalBattleFlow → BattleModule 建房
        → FSM 等待 isReady → 建 World 并装配系统 → 建时钟 → 第 0 帧
        → 到期封帧 → 写入输入 → 帧前快照和记录 → 世界演算、清理、帧号加一
```

上游实时进场在客户端等待开战消息后初始化世界。上游录像入口先初始化 `LSWorld` 和时钟，再等待场景准备，随后才挂 `LSReplayUpdater`。当前项目实时与回放统一在准备完成后建世界并取时钟锚点，等待耗时不会成为回放需要立即追赶的时间。上游服务端所有玩家就绪后还有一秒等待，这一步用于示例的开战协调。 [客户端进场和录像进场][scene-change] · [服务端建房][server-room] · [就绪消息与开战][server-start] · [项目初始化状态](../../Assets/GameScripts/HotFix/GameLogic/Module/BattleModule/State/InitializeBattleState.cs)

## 2. 房间、帧驱动和世界对照

| 项目 | ET10 当前源码 | 当前项目与差距 |
| --- | --- | --- |
| 房间归属与生命周期 | `Room` 是宿主 Scene 上的组件，持有 `LSWorld`、权威帧、预测帧、时钟、帧历史和录像。更新器是房间组件。 | `BattleRoom` 持有对应的单机对象。TEngine FSM 承担初始化、开始、进行、结束的调度。单机保留 `AuthorityFrame`，`PredictionFrame` 留待联机。 [ET Room][et-room] · [项目房间][local-room] |
| 准备与开帧 | `LSSceneChangeStart` 是可等待的房间准备事件，示例事件内挂资源加载器，加载界面、房间 UI、场景资源位置留有注释。实时用服务端就绪消息开帧。 | `isReady` 已落地，执行的是现有 `main` 的加载状态。到独立战斗场景阶段，再将真实场景加载结果传给 `isReady`。 [ET 场景准备][scene-prepare] · [项目单机流程][local-flow] |
| 某一帧的计划时间 | `FixedTimeCounter` 使用起始毫秒、起始帧和整数步长，默认 50 ms，即 20 Hz。变速先保留切换帧原来的到期时间。 | 公式和变速锚点一致。项目使用进程内单调 `Stopwatch`，帧差先提升为 `long`。上游 `ServerNow()` 带服务器时间偏移。 [上游时钟][clock] · [上游时间源][time] · [项目时钟][local-clock] |
| 权威步进 | `LSServerUpdater` 每次轮询判断 `AuthorityFrame + 1`，到期取输入、递增权威帧、广播，再调用 `Room.Update`。 | `BattleUpdater` 每次实时轮询同样最多推进一帧。封存本地输入后提交权威帧并调用 `BattleRoom.Tick`。广播由本地直接调用取代。 [ET 权威更新][server-updater] · [项目更新器][local-updater] |
| 帧输入和补齐 | `LSInput` 含定点二维方向和整数按钮，`OneFrameInputs` 以玩家 ID 为键。服务端缺输入时沿用前一帧，缺前帧则用默认值。 | `BattleInput` 字段语义一致。使用开局固定单位槽和最新提交覆盖策略，缺输入时沿用最近确认值，初始为默认值。公开的 `SubmitLocalInput` 写当前本地玩家槽。键盘绑定留给正式玩法，Demo 走框架提交入口。 [上游输入][input] · [ET 补帧][server-updater] · [项目帧历史][local-buffer] |
| 环形历史 | `FrameBuffer` 默认 1,200 槽，保存每帧输入、快照字节和 hash。`MaxFrame` 支持未来输入和预测窗口。 | 也是 1,200 槽。按实际帧号标记占用，能拒绝读取遭覆盖的旧帧。只维护当前单机输入和已推进历史。 [ET 帧容器][buffer] · [项目帧历史][local-buffer] |
| 单帧推进顺序 | `Room.Update` 写入 `LSUnit` 输入，实时房间保存帧前 `LSWorld` 快照及录像，再调用 `LSWorld.Update`。世界完成更新后帧号加一。 | 实时与回放共用 `BattleRoom.Tick`。项目写入 Entitas 后取帧前快照，然后系统树 `Execute`、`Cleanup`，最后 `Frame++`。回放也取快照用于项目内对账。 [ET Room.Update][room-system] · [项目房间][local-room] · [项目世界][local-world] |
| 确定性实体 ID 与顺序 | `LSWorld` 保存可序列化的 ID 计数器。`LSUpdater` 将注册更新的实体按 ID 排序，刷新执行集合后逐个调用 `LSUpdate`。 | 现有输入和保存按开局单位槽稳定遍历。Entitas 系统按装配顺序执行，框架没有统一确定性实体 ID 分配，也没有保证各系统的 Group 迭代按业务 ID 排序。后续只对确实依赖顺序的演算明确排序规则。 [ET 世界][world] · [ET 排序更新][world-updater] · [项目世界][local-world] |
| 确定性随机数和运行态 | `LSWorld` 有 `TSRandom` 状态字段和 ID 计数器。序列化包括参与 `ISerializeToEntity` 的子实体和组件，Fiber 与 `SceneType` 排除在快照外。 | `BattleWorld` 当前只编码下一帧和开局固定槽的 ID、位置、旋转、输入。无世界级随机数状态合同。系统树能装配业务系统，现有快照不能恢复新增组件、实体生成与销毁、随机数或会影响演算的系统私有状态。 [ET 世界][world] · [实体序列化][entity-serialize] · [项目世界][local-world] |
| 定点数学 | TrueSync `FP` 用有符号 64 位底层值和 32 位小数。二维归一化先求倒数，再乘各分量。示例移动有固定的乘除顺序、位移阈值和四元数朝向。 | `Utility` 已有同样的 Q32.32 表示。`FixedVector2.Normalized` 经 `/` 运算符也先求倒数再乘分量。定点表示和这些运算路径已有对应，尚无全运算边界及姿态 `RawValue` 的同输入跨实现验收。Demo 使用临时位移，不能作为 ET 示例移动一致性的证明。 [ET 标量][fp] · [ET 二维归一化][vector2] · [ET 示例移动][move] · [项目向量][local-vector] · [验收 Demo][local-demo] |
| 玩法、输入设备与显示 | `LSOperaComponentSystem` 采样 WASD，`LSInputComponentSystem` 控制位置与朝向，View 侧独立绑定单位、插值、动画和镜头。 | 正式入口启动空世界。`createSystems`、`SubmitLocalInput` 和 `TryGetUnitState` 是当前接点。正式玩法与表现保持在 `Runtime/Battle`，临时验收玩法集中在可删除的 Demo。 [ET 输入采样][device-input] · [ET 视图接线][view-init] · [项目开局门面][local-module] |

## 3. 快照、hash、回放与结束对照

| 项目 | ET10 当前源码 | 当前项目与差距 |
| --- | --- | --- |
| 快照时点 | 向单位写入第 N 帧输入后，执行世界之前序列化。快照内 `LSWorld.Frame = N`，表示下一待演算帧。 | 同样保留第 N 帧前的状态语义。现有检查点仅恢复固定单位槽。要继续对标的是快照覆盖范围和恢复后重建演算环境。 [ET 帧前序列化][room-system] · [项目世界][local-world] |
| 恢复方式 | 跳转或回滚销毁原 `LSWorld`，反序列化并替换世界。`MemoryPackHelper` 走初始化回调，替换后执行回滚系统以恢复相关非逻辑对象的引用。 | `RestoreSnapshot` 在原 Context 和原系统树上覆盖四类单位状态，手动清空历史并重演。只有组件值的圆回程已经验收。需定义完整状态恢复、系统重新装配或刷新，以及旧引用如何脱离。 [ET 跳转与回滚][client-helper] · [反序列化回调][deserialize] · [项目房间][local-room] |
| 帧前 hash 用途 | 世界序列化后写入 `FrameBuffer`。客户端发送权威帧 hash，服务端对照自己的 hash。失败时服务端回传帧前世界字节，客户端记录两份世界信息用于诊断。 | 以自身快照字节计算 FNV-1a，并用录像中的帧前 hash 做离线自校验。与 ET 的世界编码、`ByteHelper.Hash` 和网络诊断协议不同。逐帧对账可比较逻辑状态字段，不能跨实现直接比较原始字节和 hash。 [ET 保存与 hash][room-system] · [ET hash 算法][et-hash] · [ET 服务端比对][hash-check] · [ET 客户端诊断][hash-fail] · [项目 hash][local-hash] |
| 录像记录内容 | 包含初始单位、按权威帧追加的输入、周期快照。默认每 1,200 帧保存检查点。`SaveReplay` 可在实时局中导出，样例录像模型没有帧 hash、终局 hash 或结算对象。 | 初始数据、逐帧输入和 1,200 帧检查点已对应。额外保存帧前 hash、文件版本和校验值，使用自有本地格式，退出时写最新版录像。两个录像格式不能互读。 [ET 录像模型][replay] · [ET 保存入口][client-helper] · [项目录像格式][local-replay-file] |
| 回放驱动和倍率 | 使用录制的输入调用同一个 `Room.Update`，按到期时间追帧，每帧后检查 5 ms 预算。倍率循环为 1、2、4、8，并调整整数步长。 | 回放共用世界执行入口，追帧预算和倍率对应。正常播放到末尾后与上游一样停止推进，保留房间供定位或离开。 [ET 回放更新][replay-updater] · [项目更新器][local-updater] |
| 定位与时间锚点 | `JumpReplay` 按检查点索引决定是否替换世界，重设播放时钟，再由播放更新器追向目标。 | 项目每次定位都恢复最近检查点，同步重演至目标帧执行结束，将时钟锚定在该帧。当前行为与 ET 的异步追帧策略不同。需要保留首帧、向后、跨检查点和倍速定位的明确语义。 [ET 跳转][client-helper] · [项目定位][local-room] |
| 离线分歧与终局 | ET 回放路径跳过 `SaveLSWorld`，没有读取录像 hash 或检查最后一帧演算后结果的逻辑。 | 项目额外记录帧前 hash。发现 mismatch 时会标记分歧，但仍执行该帧的 `World.Tick`，随后才停止推进。若保留离线自校验，应单独修正帧前分歧的停止边界。终局 hash 属于项目增强，不能列为 ET 对标缺项。 [ET 回放路径][room-system] · [项目帧执行][local-room] |
| 结束和释放 | 已核对的 Lockstep 包源码及协议没有通用的胜负结算、自动结束或终局封存。场景切换入口移除旧房间，再创建当前房间。 | 项目已有 `EndBattle`、结束状态、世界释放以及 Esc 回菜单并保存。如果后续玩法需要从执行中的系统发起结束，可定义帧末请求和完成通知，这是项目生命周期需求。当前无需推断胜负、奖励或结算协议。 [ET 切换与回收][scene-change] · [ET 协议目录][proto] · [项目结束入口][local-module] · [项目退局][local-flow] |

### 检查点帧号边界

按源码静态推导，上游恢复一个帧号为 N 的帧前快照后，在 `JumpReplay` 里把 `AuthorityFrame` 设为 N。回放更新器随后先加一再读取输入，会从 N+1 的输入继续，而快照世界仍准备演算 N。应把这一点视为上游样例的待实测偏移，避免照抄。当前项目恢复后设 `AuthorityFrame = checkpoint.Frame - 1`，再执行 `N..目标帧`，符合当前快照合同。这个判断只来自代码路径，本次未启动 ET 做运行复现。 [ET 定位][client-helper] · [ET 回放推进][replay-updater] · [项目恢复][local-room]

## 5. 根据对比重新排下一步

后续执行记录：第 1 项已实现并通过 Unity Editor 验收，改动和结果见[单机战斗世界快照与重建分步执行方案](./单机战斗世界快照与重建分步执行方案.md)。本对比表保留调研当时的代码状态。

1. **将现有快照从固定单位槽提升到可恢复的战斗世界。** 先约定开局数据、帧号、稳定业务 ID、必要的确定性组件与局级状态分别由谁导出和重建。只接实际必要状态。世界恢复后重建或刷新 Entitas 系统以及它们持有的运行态索引。用 Demo 中的临时有状态实体测试连续执行和从检查点重演，覆盖实体创建、删除及稳定顺序。正式玩法依然空置。 [ET 世界恢复][client-helper] · [项目当前覆盖范围][local-world]
2. **以 `RawValue` 验收数值和帧边界。** 固定同一组初始数据与输入序列，在 Demo 中对照定点乘除、平方根、归一化和旋转结果。检查第一帧、最后一帧、跨 1,200 帧检查点跳转、倒跳及倍速定位。比较同帧可映射的逻辑状态。该测试只验证迁移后的基础运算和帧顺序。 [TrueSync 标量][fp] · [ET 固定时钟][clock] · [验收 Demo][local-demo]
3. **单独决策项目增强。** 帧末完成入口、终局 hash 属于项目需求。帧前 hash 已发现分歧仍执行该帧，是当前实现中可以明确修正的边界。Player 场景和资源接线有实际配置缺口，可以作为单独交付验收。 [当前帧推进][local-room] · [当前构建场景][local-build]

原执行顺序把帧末结算和终局 hash 当作单机对标重点。对比后，首要差距是世界状态的覆盖范围与恢复后的确定性执行。此次交付为源码对比，运行依据是前次归档的 Editor 测试。对比期间未改战斗代码、录制格式、场景或构建设置，也未重跑 Unity 或 Player。
