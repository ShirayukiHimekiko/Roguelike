# 单机战斗流程与帧演算职责边界

## 当前设计判断

现有代码没有两套帧循环。`LocalBattleFlow.OnLateUpdate` 只处理命令和回放反馈；房间 FSM 才驱动 `BattleUpdater`。问题是当前局的控制权分散：`LocalBattleFlow._room` 决定退出、菜单和本地录像，`BattleModule._currentRoom` 决定能否开局、操作哪个房间以及何时关闭，`BattleRoom` 自己又注册业务命名的四态 FSM。两份引用不是两个 Room，但其建立与清除要由不同全局对象同时维护。特别是应用释放时，`LocalBattleFlow.OnRelease` 只清引用，真正销毁仍靠 `BattleModule.OnRelease`。

`LocalBattleFlow` 继承 `Singleton` 的实际作用是菜单能直接取 `Instance`，并借 `SingletonSystem` 自动收到 LateUpdate 和释放回调。用途成立，但只有一个入口和一局活动战斗时，没有足够理由同时设两个全局战斗对象。ET10 [场景切换流程](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lockstep/Scripts/Hotfix/Client/LSSceneChangeHelper.cs) 把当局 Room 挂在场景根对象上，流程负责准备和替换它；这支持明确所有者的方向，不要求照搬 ET 的结构。

## 推荐的目标边界

| 层 | 继续负责 | 明确移出 |
| --- | --- | --- |
| `Runtime/Battle` | 一个 `BattleFlow` 普通实例持有当前 Room，组织进场、资源就绪、开始、进行和退场；对接菜单、本地录像文件的选择、播放指令和未来的结算 | 不直接演算逻辑世界，不自己做另一套帧时钟 |
| `Module/BattleSimulation`（建议目录名） | `BattleRoom`、`BattleWorld`、时钟、更新器、输入历史、快照与回放机制。每个 Room 管自身演算资源、步进启停与释放 | 不保存全局当前局，不访问菜单和场景，不负责何时开局、结束后切哪里 |
| 现有应用宿主 | 创建和释放 `BattleFlow`，提供入口及退出路径；优先检查 `GameAppManager` 是否合适 | 不把具体战斗流程或规则塞进应用状态机 |

生命周期按对象分两层。Runtime 管**玩家经历的一局**：场景准备、开始、进行、退出和结算。演算层管**Room 的资源和状态**：世界、时钟、更新器、帧序、快照、完成当前 Tick 后停步、释放。四态 FSM 职责迁至 Runtime，仍由 TEngine 的 FSM 模块轮询；进行状态推进当前 Room。若直接让 Runtime 的 FSM 以流程对象为 Owner，即可读取该流程持有的当前 Room，避免为维持旧类型再建一个全局转发门面。

不建议只把 `BattleModule` 改名后原地保留，也不建议把整套 Room/World 和帧算法搬到 Runtime。首选删掉现有模块对活动局的全局管理，让实例操作回到各自所属的 Room，把游戏操作集中在流程层；仅在真实出现第二个调用方时再提取额外服务。

## 若确认实施

具体脚本去向、方法归属、命名、启动和释放顺序见[单机战斗流程与演算模块脚本迁移方案](./单机战斗流程与演算模块脚本迁移方案.md)。

- [ ] **先收口活动局所有权。** 核对 `StartUI`、应用释放和 Demo 的调用点；确定 `BattleFlow` 普通实例的宿主与输入回调接线，去掉 `LocalBattleFlow.Instance` 与 `GameModule.Battle` 双入口。伪代码：`app owns flow; flow creates and owns current room; ui commands flow`。
- [ ] **让 Runtime 管四态流程。** 复用当前 TEngine FSM，迁移场景就绪、开始、运行和退出的编排。Room 对外提供最小的开始步进、轮询及释放接口。伪代码：`ready → room.initialize/start; running → room.poll; exit → room.stop/release`。
- [ ] **归位演算文件并复验。** 保留时钟、输入、录像、快照、回放行为与格式，先跑独立宿主，再跑正式菜单下的退局、回放、重开与应用关闭；自然结束和终局校验等职责边界稳定后再接。伪代码：`baseline → move ownership → rerun same scenarios`。
