# 单机战斗框架剩余工作分步执行方案

日期：2026-11-18。范围：单机框架完善、正式接线与交付。联机、具体玩法、奖励与数值规则均不在本轮实现范围内。

## 执行总览

原清单 01–03 已实现并通过直接编译当前战斗源码的独立宿主验收；不重做定位分批、同区间复用和回放分歧停止。需在 Unity 中复验。原始编号沿用[未完成项清单](./单机战斗框架未完成项清单.md)；已实现的定位行为见[定位执行记录](./单机回放定位与分歧停止执行方案.md)。

| 顺序 | 执行目标 | 对应清单 | 依赖与产出 |
| --- | --- | --- | --- |
| 1 | 建立当前单机闭环的 Unity 验收基线 | 11–12 | 可连通的 Pipeline；留下真实菜单与回放用例结果 |
| 2 | 战斗在一个逻辑帧结束后自然完成 | 04 | 原有 Room/FSM 与单机入口；输出一次完成通知并统一退局 |
| 3 | 增加末帧执行后的确定性校验 | 05 | 第 2 步统一封存点；确定旧录像读取策略和文件版本 |
| 4 | 接正式场景、玩法输入、Entitas 和表现 | 06–10 | 依赖正式场景和玩法设计；可暂缓，不阻塞第 1–3 步 |
| 5 | 验收正式玩法的重演与长局性能 | 13 | 第 4 步已有真实状态负载；此前 Demo 结果只算框架基线 |
| 6 | 接独立 Player 并确认可移除 Demo | 14–15 | 框架开发版可在第 3 步后先测；正式玩法随第 4–5 步再验 |

采用现有链路：`Runtime/Battle` 负责进退场、存读录像和菜单；`Module/BattleModule` 负责 Room、帧驱动、世界与录像合同；`Module/Utility` 放定点等工具；测试系统统一放 `Tools/BattleFrameworkDemo`。保持当局 FSM 驱动、进场就绪和第 0 帧分离。ET10 的 [Room 更新](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lockstep/Scripts/Hotfix/Share/RoomSystem.cs)是输入和帧前快照边界的对照；自然结束与终局 Hash 是本项目补充。按项目规则在修改前确认范围；以下为执行计划，实际完成后才勾选并附结果。

## 第 1 步：Unity 真实闭环与当前回放复验

- [ ] **确认 Editor 可操作。** 按项目 `unity-pipeline` 规范发现当前实例，记录 Editor、场景、编译和 Console 状态。无法连接时保留现有会话，留下失败证据；第 2–3 步可用当前源码的独立宿主继续，不能勾掉 Unity 验收。伪代码：`discover(project); waitForReady(); confirm(main)`。
- [ ] **从正式菜单验收。** 使用 `StartUI → LocalBattleFlow → BattleModule`，记录场景就绪前后首帧、Esc 退局、最新录像落盘、R 读档、Tab 变速、方向键定位和二次开局。正式入口路径与 Demo 分开记录；固定验收专用录像，避免覆盖用户真实录像。伪代码：`start → firstTick → exit → save → replay → seek/speed → exit → restart`。验收：重开从新房间首帧开始，旧局不再推进。
- [ ] **跑定位、错帧、倍率及实际耗时用例。** 复用已有 1,206 帧重建与 40 帧切速入口；若错 Hash 分支的现有断言仅在独立宿主，按需在可移除 Demo 中添加 Unity 入口。伪代码：`seekAcrossCheckpoint → replacePendingTarget → verifyHash; injectWrongHash → verifyStop; runSpeedSequence`。记录数据规模、追帧批次与单次最慢耗时；约 5 ms 是逐 Tick 检查的工作预算，不是硬时限。验收：不跳帧、不重复、不越过目标或末帧，分歧帧不执行。

## 第 2 步：补自然结束与统一退局

当前 `BattleRoom.Tick` 负责提交帧并执行 `BattleWorld.Tick`；后者运行 `Execute → Cleanup → Frame++`。现在已有 `EndBattle` 手动退出，正式入口在 `LocalBattleFlow.ExitAsync` 里回菜单并保存。这里增加“从模拟内请求、在帧结束后完成”的能力，不在框架定义胜负。

- [ ] **加唯一的帧内结束请求。** 候选落点为 `BattleWorld` 与 `BattleRoom`：系统只发出无玩法字段的完成意图，由实时房间在 Tick 返回后读取；同帧多个请求合并。录像重演同样运行玩法系统，但房间以录像帧数为停止依据，回放请求不触发正式退局、存盘或结算。伪代码：`system.requestFinish(); world.execute(); world.cleanup(); world.frame++; room.consumeFinish()`。验收：当前帧完整执行，下一帧不再推进。
- [ ] **停止推进与释放分两个时点。** 由房间在帧末进入既有结束状态，留下当局与末帧信息；由房间所有者在本次 FSM 调用栈退出后统一释放。候选是 `LocalBattleFlow.OnLateUpdate` 在读取键盘前消费完成状态，使自然结束不依赖键盘。完成信息只消费一次，帧执行中不销毁 World/FSM。伪代码：`finishAtTickEnd → markFinished → ownerConsumesOnce → EndBattle`。
- [ ] **自然结束和手动退出走同一收尾流程。** `LocalBattleFlow` 取走当前房间、冻结要保存的实时录像、结束房间，再由外层恢复菜单或交给未来的结算；回放不写入最新实时录像，无已执行帧不产生录像。伪代码：`ending = takeCurrent(); captureRecordingIfLiveAndNonEmpty(); release(ending); returnToMenu(); saveOnce()`。
- [ ] **生命周期回归。** Demo 在指定帧请求结束，验证同一帧后续系统及 Cleanup 执行一次，最终帧只记录一次，下一帧不执行，收尾只触发一次；覆盖无键盘、准备中退局、回放到该帧、立即重开。只在独立宿主测到的项目保持 Unity 验收待办。

## 第 3 步：补末帧执行后的状态校验

现有 V3 保存帧前指纹和每 1,200 帧的检查点；文件整体校验只能检查文件内容，不能证明最后一个 Tick 的结果。末帧 F 的终局指纹取自 **F 执行和清理完成后**，此时 `BattleWorld.Frame == F + 1`；不把它当作 F+1 的帧前历史或检查点。

- [ ] **增加统一封存点。** 在自然结束和有帧的手动退局共用的收尾点、释放 World 前，复用已有确定性快照编码取一次末帧后指纹。回放过程不改写录像，未开帧不封存为有效录像。伪代码：`afterLastTick → seal(frameCount - 1, hash(world)) → release → save`。验收：终局记录和最后输入槽、最后执行帧对应；不为每个 Tick 增加第二次快照。
- [ ] **定文件合同并实现读写。** 建议 V4 新写入终局指纹、保存到新文件名；V3 仍可读取，明确标记“没有终局校验”，新写入不覆盖原 V3；优先读 V4，无 V4 才回读 V3，V4 存在但无效应报告其读取失败。校验在解码入口完成，内部不重复验证。伪代码：`read(version); decodeFramesAndCheckpoints(); if V4 readTerminalHash(); validateAtBoundary()`。验收：V3 固定样本、V4 往返、空/截断/错版本及文件完整性验证。具体版本策略未获确认前不动正式格式。
- [ ] **正常播放和定位到末帧都校验终局。** 在同一个回放帧提交后判断末帧，避免两条路径重复校验。终局不符时保留“末帧已经执行”的事实，单独报告终局不符；原有“帧前分歧不执行该帧”不变。伪代码：`commitReplayTick(F); if F == last && hasTerminalHash: comparePostTickHash()`。验收：正常播放、直接定位末尾、只改最后一帧 Cleanup 结果（所有帧前 Hash 仍一致）的对照用例，以及 V3 无终局校验提示。

## 第 4 步：接真实进场、玩法、输入和表现

前置：用户确认战斗场景方案、第一批 Entitas 数据和操作语义。当前复用 `main`；若正式仍复用，记录该决定，只验收真实就绪条件，不虚设独立场景。ET 的[进场准备事件](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lockstep/Scripts/HotfixView/Client/LSSceneChangeStart_AddComponent.cs)和[表现初始化](https://github.com/egametang/ET/blob/743c635dd5b0f6f6bab549c0093382c85f3f8307/Packages/cn.etetet.lockstep/Scripts/HotfixView/Client/LSSceneInitFinish_Finish.cs)作为阶段划分参考。

- [ ] **接当局场景准备和退出。** `Runtime/Battle` 管真实加载、必要资源就绪与卸载；将就绪状态交给现有 `isReady`，加载取消或失败的返回边界按选定加载流程处理。伪代码：`createRoom(isReady); load(); ready → tick0; endRoom → unload`。验收：无提前 Tick，准备中取消后旧结果不启动新局。
- [ ] **接同一套正式 Entitas 装配。** 在 `Runtime/Battle` 声明开局数据、组件、系统次序及快照编解码，实时和回放复用同一 `BattleWorldSetup`。依赖顺序的实体遍历使用稳定 ID，影响后续演算的状态可被检查点恢复。伪代码：`setup = installRules(init, codecs, systems, applyInputs); startLive(setup); startReplay(setup)`。验收：新旧世界没有共用系统实例，恢复不重新运行开局生成。
- [ ] **接正式玩家输入。** 按玩法定义持续值和一次性操作；采样只在实时局进入 `SubmitLocalInput`，回放从已记录输入执行。伪代码：`sample → mapToFrameInput → submitLocal; replay → recordedInput`。验收：记录中能读到实际确认的输入，回放不被设备操作影响。
- [ ] **接视图、世界重绑及结果输出。** 游戏视图只读逻辑结果、按稳定 ID 管绑定；定位换世界时丢弃旧引用，同区间复用时按实际实体变化同步。自然结束通知进入玩法的结果/结算流程；框架不定义奖励和胜负字段。伪代码：`worldReplaced → rebuildBindings(); render(readState); onLiveFinished → showResult()`。验收：倒跳、跨检查点和退出后均不残留旧视图或订阅。

## 第 5 步：验证实际玩法的确定性和长局规模

- [ ] **对账同一组初始数据与逐帧输入。** 对照连续演算、完整录像重演和跨检查点恢复，比较稳定 ID、组件、随机序列、逐帧及终局指纹；记录首个分歧帧，无需先做逐组件报告工具。伪代码：`live(seed, inputs) == replay(recording) == seekAndReplay(recording)`。验收使用正式玩法装配，不能用空世界代替。
- [ ] **记录实际机器和规模下的开销。** 测 Tick、快照、最长定位轮询、内存和录像体积；记录实体/组件数量、录像长度和运行平台。伪代码：`record(frameCount, entityCount, tick, snapshot, seek, memory, fileSize)`。先交测量结果，再用产品目标决定是否优化，避免为猜测加防御或优化代码。

## 第 6 步：构建独立 Player，确认 Demo 可移除

- [ ] **修正项目实际使用的构建入口。** `ProjectSettings/EditorBuildSettings.asset` 目前指向缺失的 `SampleScene.unity`，实际入口是 `Assets/Scenes/main.unity`；`ReleaseTools` 读取 EditorBuildSettings 场景。执行时先核对生效配置，再通过项目 Unity 操作规范接好场景、YooAsset 资源与 HybridCLR 启动所需产物。伪代码：`resolveBuildScenes → ensure(main) → prepareResourcesAndHotfix → buildDevelopmentPlayer`。
- [ ] **在独立 Player 跑正式入口。** 打开独立开发版，验收菜单、战斗开局、自然与手动退局、录像保存、重启进程后读档、回放定位与变速、重复开局。伪代码：`launch → live → save → relaunch → replay → exit → live`。若正式玩法未接，只记录空战斗框架发版基线，不勾选正式玩法交付。
- [ ] **证明 Demo 可移除。** 回归完成后，使用隔离工作副本或构建上下文验证没有 `Tools/BattleFrameworkDemo` 也能编译、启动并走正式空局入口或已接的玩法入口；当前工作区保留 Demo 供复测，实际删除按交接安排执行。伪代码：`isolatedBuildWithoutDemo → compile → start → smoke`。

## 按需求启用的支线（不阻塞框架交付）

| 支线 | 启用条件、最小步骤和验收 |
| --- | --- |
| 暂停、继续、单步、进度及播完提示 | 先定义实时与回放的暂停语义。暂停不推进，单步只执行一帧，继续时锚定时钟；用现有定位状态和末帧状态提供进度与完成提示。 |
| 多录像、导入导出、历史兼容 | 先定保留和用户交互规则。文件读写集中在录像边界；验收有效文件、明确支持的版本和读取失败提示。第 3 步的 V3 兼容建议不等同于任意历史版本兼容。 |
| 本地逐组件分歧诊断 | 有实际排障需求时加。普通录像只有周期快照和逐帧指纹，应通过对照重演或专门记录收集目标帧的两份状态，按稳定 ID 和组件键比较。 |
| 扩展定点 API | 有首个实际调用需求再选用固定 ET10 对应算法，保留底层表示和舍入合同，在 Demo 比对 RawValue。 |

执行记录每项填写：实际修改、验证环境、输入样本、结果与遗留；无法运行 Unity 时保持相应目标未勾选。不在框架中添加无真实风险依据的防御代码；外部输入只在入口校验，不引入只用一次的通用抽象，不用宽泛异常捕获和多余条件。
