## 永久存档

Profile 是单写者，独立存 `SchemaVersion`、ProfileId、钱包、节点、角色、禁用、永久事实、待奖励行与已交付收据。退出、升级、解锁、奖励和相关扣费均用同一个存储抽象。加载先做版本迁移，旧 ID 按显式映射，解析或校验失败保留现场并提供重试/备份恢复。迁移须与新版本提交一致。

本地存储评审默认需要能持久提交并回读的事务端口。若引入 SQLite，则 `PendingReward → Wallet+Receipt+DeletePending` 是两段持久提交，第二段原子，先确认目标 Player 上的绑定兼容。选项目已有存储也须验证同样契约。一个进程内的事件回执不足以覆盖断电场景。[SQLite 原子提交机制](https://www.sqlite.org/atomiccommit.html)

## 调试重放与中断

| 功能 | 记录和读取 |
| --- | --- |
| 战斗重放 | 记录 Frame/规则/算法版本、RVO2 源快照与参数、目标 Player 环境、种子、确定性顺序、RoundSetup 与已经采纳的 `Tick+InputSequence` 输入。同环境可改变宿主帧分组，比较已执行 Tick 的量化位置和战果 |
| 整局重放 | 再记录 RunSetup、窗口命令、实际接收角色/英雄、版本与每次 RoundResult 摘要，回放目标必须匹配相应内容版本；重放不接局外奖励写端口 |
| 局末恢复 | 已登记待处理按冻结奖励子行恢复，已处理读取收据；仅有内存结果且未持久登记时缺失，不能构造永久奖励 |
| 局中恢复 | 首个完整版本可先支持整局运行到终局并恢复已登记奖励。继续上次未完局需要独立范围确认。本稿留安全检查点设计：在窗口边界冻结局级值、随机流、已消费身份和持久内容版本，重开重新组装 World；战斗内中断需对应 RoundSetup 和完整输入日志才可重建 |

**验收**　同 Player 与运行目标、同 RVO2 版本和配置与有序输入，按不同宿主帧分组重放，比较已执行同 Tick 的位置和战果。RVO2 用浮点求解，跨环境逐位一致尚无验收证据。重放旧版本缺内容时报告并阻止套新规则。档案保存失败不展示到账、重启成功恢复后重复 RunId 只返原回执。
