## 仓库起点与共用约定

- 代码根路径 `Assets/GameScripts/HotFix/GameLogic/ProjectB/` 相对 Unity 项目。拟增加文件保持在 `GameLogic` 首轮程序集，只有纯工具/表另走现有工具工程与 `GameProto`。现有 `GameApp.StartGameLogic()` 为空，`ProcedureStartGame` 收 Launcher UI。Assets 下未发现已经接线的 Project B 运行实现。具备 TEngine、UniTask、YooAsset 和 Entitas DLL，以及少量未接入业务的资源。
- 设计稿职责沿用 `GameManager → RunSession → BattleModule`。`GameManager` 长驻大厅和当前局；`RunSession` 写局状态；战斗按场持有 ECS、时钟通道和命令。暂停走局 FSM，战斗阶段只存战斗三态。业务“退出游戏”指放弃当前局回大厅；关闭应用由外层入口进入同步释放，应用按钮的退出语义另走平台。
- 本册以 [三模块 C#](../../04-Project_B-三模块CSharp实现代码.md) 的 `Fixed64/Point2`、`BattleFeed`、`FrameClock` 为底。`RoundId` 取 `(Guid RunId, int GlobalRoundNo)`，`BattleId` 为本宿主递增 `long`；战斗端单位唯一键 `(long BattleId, long ActorId)`。位置原始刻度 1,000,000/单位，`RawPoint/EntityRef` 只在算法适配处映射。`RandomStream` 由本册的 [卡牌阶段](04-卡牌与五层循环.md#s09) 定义。
- 文档代码段标明整类、替换方法或核心方法。核心方法依赖同阶段的目标契约，命名空间、字段和胶水按相邻表补齐。旧稿包含不同版本片段；采用下表指定的源和调用顺序，避免把两份同名类型一起搬入。
- 正式规则遵循 [决策表](../05-规则决策表.md) 的评审状态。60 Hz、每次最多 4 步、早期固定阵容和灰盒数值用于工程样本。等业务或性能门槛确定后使用正式参数重跑对应场景。
- 早期三条主用例固定为正常完成、用户取消、退出后再进入。每阶段另带一条能揭示该阶段独有错误的反例。阶段验收由实际项目运行完成，现有代码样例与独立文档评审只能说明方案覆盖。

## 如何执行阶段验收

1. 从 `Assets/Scenes/main.unity` 启动并进入大厅。阶段 01–08 走同一调试窗口，阶段 09 开始把手牌和回合间命令接入真实 UI。保留窗口操控用例和可重复输入夹具。
2. 先完成该阶段表内的全部目标。纯逻辑用固定输入通过 Test Framework 或同一领域入口的调试夹具检查。涉及资源、prefab、生命周期和场景的用例走 Editor/开发 Player。获准运行时按项目 Unity Pipeline 规范发现实例和可用命令，待操作到终态后再记结果。
3. 给每项用例记预期与实际，先定位差异再修改对应层。前面阶段的业务入口仍要走通；已有失败和新增失败分别记录。每阶段的实装和验收结果都保留链接或打印值。

## 验收记录格式

每阶段填 `代码提交/路径 · 工程版本/运行环境 · 内容版本/种子 · 操作或输入 · 预期 · 实际值及证据 · 结论`。失败先定位到对应所有者，修复后复验原坏例及正常入口。产品确认和实际运行授权沿用项目 AGENTS。
